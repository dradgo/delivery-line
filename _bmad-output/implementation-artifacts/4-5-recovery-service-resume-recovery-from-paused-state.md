# Story 4.5: `RecoveryService.resume` — Recovery from Paused State

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Workflow Owner who paused a run for investigation (story 4.8) and now wants to continue,
I want `RecoveryService.resume(workflowRunId, actor, idempotencyKey)` that transitions the run from `Paused` back to its prior executing state, re-enqueues runner work via the existing sub-stage-aware re-dispatch, and preserves the pause history for audit,
so that NFR5 (pause when uncertain, require explicit human recovery) is fully wired with a typed resume path — operators can pause + resume rather than only retry.

## Context & Central Reconciliation (READ FIRST)

**This is the FIFTH story of Epic 4 and the FIRST of the "Recovery Service Extensions" slice (4.5–4.9). It is a BACKEND-ONLY application-service story: add a `resume(...)` method to the existing `RecoveryService`, backed by a new `WorkflowCommandService.resumeWorkflow` transition, a new `recovery.resumed` audit event, a `recovery_actions` row (`action_type='resume'`), a `resume_workflow` allowed-action, and re-dispatch of the runner. It has NO REST endpoint (that is story 4.10), NO CLI command (story 4.10 AC6), and NO frontend (story 4.22). Mirror `RecoveryService.retry` (`RecoveryService.java:266-647`) — it is the exact structural template — and `DeveloperTakeoverService` (the sibling non-retry recovery action).**

Two headline problems were investigated exhaustively; the bindings below resolve both. **Read the four Headline Reconciliations before coding — the epic AC text drifts from live code and these bindings win.**

### HEADLINE RECONCILIATIONS

1. **The pause dependency DISSOLVES — resume reads the prior state from the `WORKFLOW_STATE_CHANGED → Paused` event's TYPED `priorState()`, NOT from a nonexistent `workflow.paused` event's `details.priorState`.** Epic AC5 says the prior executing state is read from "the most recent `workflow.paused` event's `details.priorState`". **There is NO `workflow.paused` event type and NO `priorState` detail key in the codebase, and `pause` (story 4.8) is unbuilt (backlog).** But the live mechanism is: EVERY transition emits a `WORKFLOW_STATE_CHANGED` event carrying a **typed** `priorState()`/`resultingState()` on the event row (`WorkflowTransitionService.java:319-336`). This is exactly how `DeveloperTakeoverService` recovers takeover context — it reuses `WORKFLOW_STATE_CHANGED` and reads via `workflowEventReadPort.findLatestTransitionToState(runId, TAKEN_OVER)` rather than minting a `recovery.takenOver` event. **Bind: resume calls `workflowEventReadPort.findLatestTransitionToState(workflowRunId, WorkflowState.PAUSED)` (`WorkflowEventReadPort.java:26-27`, already exists) to get BOTH (a) the prior executing state = `pausedEvent.priorState()` and (b) the `triggering_event_id` = `pausedEvent.publicId()`.** This removes the hard dependency on pause: resume is independently buildable and testable NOW (tests seed a `Paused` run by transitioning `Executing → Paused` through the transition service, which produces the `WORKFLOW_STATE_CHANGED` event resume reads). The only real-world gap is that nothing transitions runs INTO `Paused` until pause (4.8) ships — a benign RUNTIME gap (resume has no runs to act on yet), not a code dependency. Do NOT add a `workflow.paused` event type or a `priorState` detail key. 2. **`resume` is a public method ON `RecoveryService` (epic AC1) — you MUST widen the ArchUnit scope-lock in the SAME change, or the Failsafe build reds.** `RecoveryService` is pinned to EXACTLY two public signatures (`retry` + `describeFailure`) by `RECOVERY_SERVICE_IS_SCOPE_PROTECTED` (`ArchitectureRuleCatalog.java:784-797`, wired at `ArchitectureBoundaryTest.java:195-197`). 3. **NO Flyway migration. `action_type='resume'` and `reviewer_role` already exist in the V1 schema; there is NO `reason_text` column — route the reason through the transition + the event, exactly like retry.** Epic AC2/AC4 want a `recovery_actions` row with `action_type='resume'` and `reviewerRole='workflow_owner'` + a `reasonText`. **The `ck_recovery_actions_action_type` CHECK already permits `resume` (added in `V1__create_workflow_core_tables.sql:287-289`: `in ('retry','rerun','resume','takeover','pause','reconcile')`) and `reviewer_role` is a nullable V1 column with no value-CHECK — so `'workflow_owner'` inserts with NO migration.** There is NO `reason_text` column on `recovery_actions` (not in the table, not on `RecoveryActionWriteCommand`, not on `RecoveryActionSnapshot`). 4. **State machine reality: only `Executing → Paused → Executing` is legal today. Resume targets the recovered `priorState` (`Executing` in practice); `Investigating` resume is DEFERRED (no `Paused→Investigating` edge exists).** Epic AC5/AC6 talk about resuming into "Investigating / Executing". The transition table (`WorkflowTransitionTable.java`) only defines `Executing → Paused` (line 91, the ONLY into-Paused edge) and `Paused → {Executing, TakenOver, Reconciled}` (lines 142-147). So a paused run's `priorState` is ALWAYS `Executing` today, and `Paused → Executing` is legal. **Bind: resume transitions to the recovered `priorState` generically; today that resolves to `Executing`. Do NOT add a `Paused → Investigating` edge (pausing from `Investigating` is a pause-story/4.8 concern — no `Investigating → Paused` edge exists to reach it).** The generic transition + table validation means when pause later supports more source states, resume works unchanged. Re-dispatch (AC6): resuming into `Executing` re-dispatches the EXECUTION-stage runner via the existing sub-stage-aware `WorkflowOrchestrationService.redispatchAfterRetry(runId, correlationId)` (its javadoc explicitly says it "Mirrors the recovery/retry baseline" and NEVER transitions — perfect for resume, which did the transition separately). ## Dev Notes

### Relevant architecture patterns and constraints

- **`RecoveryService.retry` (`:266-647`) is the exact structural template.** Copy its shape: MDC scope → idempotency validate → replay pre-check → current-state guard → locate linking event → REQUIRES_NEW prep tx (transition-via-command-service + append recovery event + insert recovery_actions row) → post-commit dispatch (outside tx) with compensation → `markSucceeded` → return. `resume` differs only in: target state comes from the recovered `priorState` (not hardcoded `Executing`), the linking event is the `→Paused` transition (not the failure event), the event type is `recovery.resumed` (not `recovery.retried`), the `recovery_actions` row carries `reviewerRole='workflow_owner'` (9-arg ctor), and re-dispatch uses `redispatchAfterRetry` (not raw `runnerExecutionQueue.enqueue`).
- **`DeveloperTakeoverService` is the sibling non-retry recovery action** — it shows the two-`REQUIRES_NEW`-template pattern, routing state through `WorkflowCommandService.takeoverWorkflow`, reading transition context via `findLatestTransitionToState`, and reusing `WORKFLOW_STATE_CHANGED` rather than minting an event. Note takeover chose a SEPARATE `@Service` to avoid touching the `RecoveryService` scope-lock; this story instead puts `resume` ON `RecoveryService` per epic AC1 and widens the lock (Reconciliation 2) — an OQ documents the alternative.
- **⚠️ Double-dispatch caution.** `retry` re-dispatches via TWO different mechanisms depending on entry point: the REST/CLI `retry-workflow` path (`WorkflowCommandService.retryWorkflow` → `redispatchAfterRetry` INSIDE the command tx) and the recovery path (`RecoveryService.retry` Step 6 → raw `runnerExecutionQueue.enqueue` OUTSIDE the tx). To avoid replicating a double-dispatch for resume, keep re-dispatch in EXACTLY ONE place: `resumeWorkflow` (the command method) does the transition ONLY, and `RecoveryService.resume` performs the single `redispatchAfterRetry` after the prep tx commits. Do NOT also call redispatch inside `resumeWorkflowInternal`. The REST endpoint (4.10) wires to `RecoveryService.resume`, so re-dispatch stays single-sourced.
- **State machine.** `PAUSED` exists (`WorkflowState.java:40`); `Executing→Paused` (`WorkflowTransitionTable.java:91`) is the ONLY into-Paused edge; `Paused→{Executing,TakenOver,Reconciled}` (`:142-147`). `WorkflowTransitionService.transition` takes no expected-from arg — it reads current state and validates target ∈ allowed-targets, throwing `ILLEGAL_TRANSITION` / `CONCURRENT_TRANSITION_CONFLICT` (optimistic lock). `Paused→Executing` requires no mandatory reason (only `→TakenOver`/`→Reconciled` do). [[gate-action-needs-explicit-current-state-precondition]]: resume's `PAUSED` precondition is enforced by the explicit current-state guard in `RecoveryService.resume` (the transition table alone would let a stray source through since `Executing` is reachable from several states).
- **No Flyway, no new detail key.** `action_type='resume'` + `reviewer_role` are V1; `reason`/`triggeringEventId`/`idempotencyKey`/`correlationId` are allow-listed detail keys. Highest migration is V35 — create none.
- **`RecoveryActionSnapshot` shape** (`RecoveryActionSnapshot.java:27-39`, 11 components): `publicId, internalId, workflowRunPublicId, actionType, triggeringEventPublicId, resultingEventPublicId, actorIdentity, actorType, idempotencyKey, resultStatus, createdAt` (+ `reviewerRole` via the canonical ctor). Tests seed these directly (see `RecoveryLoggingContractTest.recoveryActionSnapshot`).
