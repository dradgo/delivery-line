## Story

As a reviewer,
I want a project-configured second LLM to review a step's output and have its verdict shown alongside my decision,
so that I get a governed second opinion without surrendering human approval authority.

## Context

This is the **execution half** of the per-step advisory reviewer-model capability (Epic 3d, PRD FR64, ADR 0026). Story **3d-1** (`done`) already shipped the durable, gating-capable *home*: the V19 migration (the **`step_reviews`** advisory-verdict table + `projects.reviewer_model_kind`/`reviewer_gating_enabled`), the `ReviewOutcome` (`pass`/`concern`/`fail`) registry, the `reviewer` connector role + `rev_` public-id prefix, and the ahead-of-use `REVIEWER_MODEL_NOT_CONFIGURED` error code. **All of that is dormant** — nothing writes `step_reviews`, nothing resolves a reviewer, nothing surfaces a verdict. 3d-2 makes the feature *run*.

**What 3d-2 does:** when a step's output artifact lands in `WaitingForReview`, fire a **reviewer runner invocation** over that artifact — resolved per-project through `ProjectConnectorResolver` using the per-project reviewer credential — record a `runner_executions` row for it (FR53: the second opinion is itself inspectable), persist the structured verdict into `step_reviews`, and **surface it advisory-only** in a presentational **Reviewer Verdict Panel** beside the existing Decision Bar. The human approve/reject decision is **unchanged and governing**; `reviewer_gating_enabled` is **not** consulted (gating is a future story). No reviewer binding = byte-identical to pre-3d. A reviewer failure degrades gracefully — it **never** strands a run.

**This is the largest story in Epic 3d.** It spans: a new closed-enum runner stage, a reviewer-execution dispatch trigger riding the existing runner queue, a new core-table write seam (`step_reviews`), an agent-side runner review mode, a new read endpoint, and a new frontend panel — plus redaction, provenance/self-review detection, and graceful degradation. Read the **Design Decisions (DD-1…DD-9)** and **Open Questions (OQ-1…OQ-4)** in Dev Notes *before coding* — several architectural forks are genuinely consequential and one (mock-vs-real reviewer) was explicitly pre-flagged by the Epic 3c retro.

**Dependencies:**
- **3d-1** (`done`) — the schema/registry/Project-fields/`step_reviews` table this story writes into and the `REVIEWER_MODEL_NOT_CONFIGURED` code it throws.
- **3c-3** (`done`) — `ProjectConnectorResolver` + `resolveConnectorSecret(project, role)` (the per-project credential decryption seam) + `ConnectorRole.REVIEWER`.
- **3c-7** (`done`) — `ProjectRuntimeConfigResolver.resolveForRun(workflowRunId)` (run → Project binding); 3d-2 adds a reviewer-kind resolver leg here.
- **3.6 / 1.10** — runner log capture + `RedactionPolicyService` (the reviewer's input/output passes the same redaction guarantees).
- **3.17 / 3.17b** — the runner queue + worker pool the reviewer invocation rides.
- **Epic 3b `WaitingForReview` loop** — `onPlanStageSucceeded` / `onPrOutputStageSucceeded` are the trigger seams; the Decision Bar is where the panel slots.

## Acceptance Criteria

> Copied verbatim from the epic (`_bmad-output/planning-artifacts/epic-03d-per-step-execution-control.md`, Story 3d-2). Already BDD-formatted.

1. **Given** a project with a reviewer-model binding, **When** a step produces an output artifact, **Then** a reviewer runner invocation runs over that artifact, resolved through `ProjectConnectorResolver` using the per-project reviewer credential (decrypted in memory only, never logged) — exactly as automated runners resolve their adapters.
2. **Given** the reviewer run, **Then** a `runner_executions` row is recorded for it (so the second opinion is itself inspectable, per FR53) and a `step_reviews` row persists the structured `outcome` + `rationale` + reviewer/producer model identities.
3. **Given** the advisory contract (ADR 0026, D2), **Then** the verdict is **surfaced** to the human reviewer in the `WaitingForReview` Decision Bar via the Reviewer Verdict Panel; it does **not** auto-approve or auto-reject, and the human decision remains the governing approval — `reviewer_gating_enabled` is not consulted.
4. **Given** provenance, **Then** the verdict explicitly records which model produced the step output and which produced the review, so "reviewed by a different LLM" is verifiable and a same-model self-review is detectable (and surfaced as a warning in the panel).
5. **Given** no reviewer binding on a project, **Then** behavior is byte-identical to pre-3d (no reviewer run, no panel) — the feature is strictly opt-in per project.
6. **Given** a reviewer-run failure (provider error, timeout), **Then** it degrades gracefully: the step is **not** blocked, the panel shows a "review unavailable" state with the reason, and the failure is recorded — a failed second opinion never strands a run.
7. **Given** redaction (story 1.10) + the live-stream posture (ADR 0025), **Then** the reviewer's input/output passes the same redaction guarantees as any runner artifact before persistence/egress.
8. **Given** allowed-actions (story 2.14), **Then** the human approve/reject actions are unchanged; the panel is presentational and does not add a governed action in this epic.
9. **Given** tests, **Then** coverage asserts: reviewer run resolves via the per-project reviewer credential, verdict persisted + surfaced advisory-only, human decision unaffected, no-binding parity, graceful degradation on reviewer failure, same-model self-review flagged, redaction on reviewer egress.

## Dev Notes

### What this story is (and is not)

- **Is:** the runtime that resolves a per-project reviewer, runs it as a runner invocation over a `WaitingForReview` artifact, records a `runner_executions` row, persists a `step_reviews` verdict, and surfaces it **advisory-only** in a new presentational panel beside the Decision Bar. Graceful, opt-in, provenance-aware, redacted.
- **Is not:** gating. `reviewer_gating_enabled` stays `false` and is read by **nothing** (ADR 0026 D3). The panel never enables/disables the human's approve/reject. No new `AllowedAction`, no new `WorkflowState`, no change to the human approval semantics. Not spec-stage review (the reviewer targets the **`WaitingForReview`** execution-stage outputs — implementationPlan + prOutput; spec lands in `WaitingForSpecApproval`, out of scope).

### Design Decisions (record in PR + Completion Notes; several have a live Open Question)

- **DD-1 — Reviewer rides the existing runner stack via a new `RunnerStage.REVIEW`.** AC1 ("exactly as automated runners resolve their adapters") + AC2 (a `runner_executions` row) + FR53 (inspectable) make a dedicated, off-to-the-side API call wrong (ADR 0026 Alt-3, rejected). `RunnerStage.REVIEW` is **code-only** (no DB CHECK, no drift gate, no Flyway — verified), so the cost is the 9-site switch fan-out, not a schema cascade. The reviewer-execution orchestration lives in `application` (a dedicated `ReviewerExecutionService` or folded into the existing dispatch trigger + `RunnerBroker` harvest — pick one home and keep `step_reviews` SPI + verdict types out of `adapters`, ArchUnit `ArchitectureBoundaryTest`). **Alternative considered:** a fully separate reviewer pipeline not reusing `RunnerStage` — rejected because `runner_executions.stage` is non-null and reusing the queue/worker/adapter plumbing is far less code.
- **DD-2 — The verdict is a `step_reviews` row, NOT an `artifacts` row; no new `ArtifactType`.** The verdict is advisory metadata *about* an existing artifact, not itself a reviewable artifact. The REVIEW harvest branches **before** `artifactOperationService.recordOperation` and writes `step_reviews` directly. This keeps the artifact lifecycle, `artifacts.type` CHECK, `WaitingForReview` entry semantics, and the frontend `isArtifactView`/`toArtifactView` guard **all untouched** ([[artifactview-variant-field-fanout]]). `allowedArtifactTypesForStage(REVIEW)` = empty set.
- **DD-3 — Verdict transport from the runner: a dedicated `review-result.v1` schema (RECOMMENDED) vs. a `reviewVerdict` variant in `runner-result.v1` (alternative — OQ-2).** `runner-result.v1` only knows `spec`/`implementationPlan`/`prOutput` with `normalizedOutput.outcome ∈ {success, failure}` and `artifactReferences minItems:1` — it cannot natively carry `pass`/`concern`/`fail` + `rationale`. **Recommended default:** add `deliveryline-runner-contracts/.../review-result.v1.schema.json` (`outcome` enum pass/concern/fail, `rationale`, `reviewerModelIdentity`, `summary`) + a `ValidationTarget.REVIEW_RESULT`, and have the review harvest validate the reviewer's `result.json` against it. This keeps `runner-result.v1` + backend `ArtifactType` + the frontend `ArtifactView` union **completely untouched**. **Trap either way:** editing/adding a runner-contracts schema needs `mvn install` of `runner-contracts` (or `-am`) or the backend validates against the **stale `.m2` jar** ([[runner-contracts-schema-stale-in-m2]]). **OQ-2** records the alternative (additive `reviewVerdict` oneOf branch in `runner-result.v1` + `ArtifactType.REVIEW_VERDICT`), which is more uniform but drags in an `artifacts.type` CHECK widening + a backend `ArtifactType` drift leg.
- **DD-4 — Reviewer fires ASYNC + non-blocking on `WaitingForReview` entry.** Enqueued (worker-pool) right after the `WAITING_FOR_REVIEW` transition in `onPlanStageSucceeded`/`onPrOutputStageSucceeded`, **iff** a binding exists. The run is human-reviewable immediately; the verdict appears when ready. This is what makes AC6 (graceful degradation) structurally true — the reviewer is never on the run's critical path. **Alternative considered:** block the transition until the verdict is in — rejected (a slow/failed provider would strand the run, violating AC6).
- **DD-5 — Verdict surfaced via a dedicated `GET …/reviewer-verdict` endpoint + a standalone panel.** Decoupled from the artifact read model (DD-2 rationale) and from allowed-actions (AC8). The endpoint derives `pending`/`available`/`unavailable` server-side from the reviewer `runner_executions` + `step_reviews` rows, so the frontend stays dumb/presentational.
- **DD-6 — Provenance + self-review (AC4).** `producerModelIdentity` derived from the reviewed artifact's producing `runner_executions` (kind + image tag); `reviewerModelIdentity` from the reviewer execution. Equal ⇒ `selfReview` flagged (surfaced as a panel warning, **not** a refusal). Persist both identities on the `step_reviews` row (3d-1 columns `reviewer_model_identity`/`producer_model_identity`).
- **DD-7 — `reviewerModelKind` parsing + `REVIEWER_MODEL_NOT_CONFIGURED`.** 3d-1 stored `reviewer_model_kind` as opaque nullable text (DD-1 there, no DB CHECK) precisely so 3d-2 owns validation. `null`/blank = no reviewer = **parity** (AC5, the hot path — NOT an error). A *set* value that doesn't parse to a known non-manual `RunnerKind`, or a binding with no active reviewer credential, = misconfiguration → graceful-degrade `unavailable` + the `REVIEWER_MODEL_NOT_CONFIGURED` reason (3d-1 registered the code ahead-of-use → this is its first throw site; `ProblemDetailsCoverageFoundationContract` already round-trips it). **OQ-3:** should `reviewer_model_kind` now be CHECK-constrained to the `RunnerKind` set (3d-1 deferred this as OQ-1) — default: keep it opaque, validate at resolve time.
- **DD-8 — Redaction (AC7).** Reviewed-artifact content embedded in the review bundle passes the existing `ContextBundleService` → `RedactionPolicyService.redact(...)` path before egress to the runner; the reviewer's `rationale` passes redaction before `step_reviews` persistence. Reviewer credential: in-memory only, never logged (AC1). The reviewer surface inherits the same localhost-only / persisted-redaction posture as any runner (ADR 0025).
- **DD-9 — No `WorkflowState`, no `AllowedAction`, no `WorkflowEventType` strictly required.** The run stays in `WaitingForReview` throughout; the reviewer is a `runner_executions` lifecycle, not a run-state change. **OQ-4:** whether to emit a `reviewer.verdictRecorded` / `reviewer.reviewFailed` `WorkflowEventType` pair for the timeline (each = two-fixture-sites + byte-identical OpenAPI, [[new-workfloweventtype-fixture-sites]]). Default: **defer** unless the panel/timeline needs an event feed — the verdict endpoint is the read path and `runner_executions` already records the review run.

### Logging Requirements (project-wide standard)

Every story leaves the touched services observable enough to debug a production incident without re-deploying (enforced via Task 9). Unlike 3d-1, **3d-2 has a real runtime surface** — instrument it fully.

- **Framework:** SLF4J + Logback. No `System.out`, no `printStackTrace()`.
- **Where to log (minimum surface):** reviewer dispatch trigger (`INFO` enqueue / `DEBUG` no-binding), config resolution (`INFO` resolved-kind / `WARN` misconfigured), review harvest (`INFO` verdict persisted with outcome+ids / `WARN` reviewer-failed-run-still-reviewable / `INFO` self-review), persistence adapter (`INFO` persisting / `ERROR` unmapped integrity violation).
