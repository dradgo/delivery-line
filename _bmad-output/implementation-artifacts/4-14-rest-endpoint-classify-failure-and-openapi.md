## Story

As a frontend developer (failure-taxonomy classification UI in story 4.24) and CLI user,
I want a REST endpoint `POST /api/v1/workflows/{workflowRunId}/classify-failure` wired to `RecoveryService.classifyFailure` (story 4.9), plus the sibling `deliveryline operator classify-failure` CLI command,
so that a Workflow Owner can apply a governed `FailureTaxonomyValue` to a failed run for cross-run pattern analysis — flowing through the standard mutation conventions (idempotency + Problem Details + OpenAPI) — and the story 4.24 dropdown consumes the typed taxonomy enum from the OpenAPI snapshot.

## Dev Notes

### Relevant architecture patterns and constraints

- **The 4.11 `reconcile` method (`WorkflowController.java:2221-2267`) is the exact structural template** (present in the working tree; committed as of 4.11 merge). Copy: annotations → guard prologue → `requireWorkflowOwnerRole` → `ActorContext` build → service call → rich response `from(runId, result)` → two log lines. Classify is the closest sibling to reconcile for arg shape (a domain field before `idempotencyKey`), diverging in the four ways enumerated in Reconciliation 3 (`reasonText` genuinely optional, NO response state field, five args not six, taxonomy error set).
- **Single-entry-point (service layer).** There is NO `WorkflowCommandService.classifyFailure` — classify performs no transition, so it never joined the `WorkflowCommand` family (story 4.9 R8). The ONLY entry point is `RecoveryService.classifyFailure` — Reconciliation 2. There is no "thin twin" trap here (unlike pause), but there IS the reverse temptation: do not try to route through the command service or invent a transition.
- **`ActorContext` lives in `org.dradgo.application.artifact`**, not `application.recovery`. Its canonical ctor rejects a blank `actorIdentity`/null `actorType` — safe because `localActorIdentityResolver.resolve(...)` falls back to `local-operator` and `ActorType.HUMAN` is hard-coded.
- **RBAC is audit-only.** `requireWorkflowOwnerRole` is a request-shape check; the controller never returns 401/403. The resolved actor identity is stamped on the audit trail. Note `requireWorkflowOwnerRole` throws `INVALID_REVIEWER_ROLE_FOR_ENDPOINT` for a non-blank wrong role; a BLANK `role` is caught by `@NotBlank` bean-validation FIRST as `INVALID_COMMAND_PAYLOAD` (the 4.10 debug-log lesson — split the test accordingly).
- **The `classify_failure` allowed-action is state-gated** to `case FAILED` for `ROLE_WORKFLOW_OWNER` (4.9 R12) — the controller adds NO state check of its own; the `FAILED`-only gate inside the service is the enforcement (`CLASSIFY_NOT_APPLICABLE`). The allowed-actions list is a read-model concern, NOT a service guard.
- **Idempotency: one surface, you touch none of it.** `recovery_actions.idempotency_key` unique key. `RecoveryService.classifyFailure`'s replay pre-check guards `actionType == 'classify_failure'` (`:1740`) — cross-action key reuse is `IDEMPOTENCY_KEY_CONFLICT`, not a false replay. The replay compares the requested `taxonomyValue` against the prior event's `details.taxonomyValue`: equal → replay, different → conflict (story 4.9 R8). The replay pre-check runs BEFORE taxonomy parsing (Reconciliation 8), so a same-key retry that omits `taxonomyValue` still replays. The controller passes the raw header + taxonomy + reason through and lets the service decide.
- **No `WorkflowCommand` permit, no fingerprint arm, no `EXPECTED_PERMITS` edit.** Classify never joined the sealed command hierarchy (4.9 R8). This story adds only REST DTOs, which are not `WorkflowCommand`s.
- **`taxonomyValue` OpenAPI enum vs registry drift.** The inline `allowableValues` on the DTO is a SEPARATE copy of the six wire values from the `FailureTaxonomyValue` enum — there is no compile-time link. 4.9 chose NOT to add an API-placeholder drift leg (it deferred the OpenAPI enum to this story). Keep the six values verbatim from `FailureTaxonomyValue.java:25-30`; a future registry addition/deprecation (governed by ADR 0035) must update this `allowableValues` list too. Consider a focused test asserting the DTO's `allowableValues` set equals `DomainRegistry.failureTaxonomyValues()` to catch future drift (nice-to-have, not blocking).
