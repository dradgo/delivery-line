> **⚠️ READ FIRST — this is the OPERATOR-FACING back half of split. 3f-4 produced the advisory *proposal*; 3f-5 COMMITS it.** On `approve_split` over a current open proposal, `SplitCommitService` performs a **best-effort, non-transactional fan-out** (the 3-18 pattern): per subtask it (a) creates a source sub-ticket where the connector supports it else proceeds **internal-only** linking the child to the parent's ticket, (b) mints a **child run** in the parent's project with `parentRunId` set, (c) records the proposed **dependency edges**; then it decomposes the parent into the **non-terminal `SPLIT`** state and appends the `workflow.split` event **only if ≥1 child was created**. A child with no unmet dependencies dispatches immediately; a dependent child parks in `WaitingForDependencies`.
>
> **3f-5 creates NO new schema, NO new WorkflowState, NO new WorkflowEventType, NO new transition-table edge, and NO new runner contract.** Every substrate it needs already shipped: the `approve_split` action is the *only* new `AllowedAction` (3f-4 deliberately left it out). `SPLIT` (state), `workflow.split` (event + `childRunIds` detail key), `parent_run_id`, the `SPLIT` into-edges from both gates, `run_dependencies` + `WaitingForDependencies`, `split_proposals` (with an `approved` status already in its CHECK), and the subticket capability are all in place. 3f-5 is **pure orchestration** over them — this is the integration story, not a substrate story.
>
> **What 3f-5 does NOT own (forward stories):** the `SPLIT → COMPLETED` **rollup** (parent stays in non-terminal `SPLIT` here — it rolls up only when all descendants complete) is **3f-7**; the **depth cap** / `SPLIT_DEPTH_LIMIT_EXCEEDED` / `complex-ticket-flow.max-split-depth` / deep-split override is **3f-7**; cascade-cancel/cascade-fail of dependents is a documented forward option (not this epic).
>
> **Seven reconciliations the live codebase forces (read ALL before coding):**
>
> 1. **`SplitCommitService.commit` MUST NOT be `@Transactional` (the 3-18 trap, verbatim).** If it were, every per-subtask `@Transactional(REQUIRED)` call (`workflowRunCreatePort.create`, `runDependencyService.declareDependencies`) would JOIN one batch transaction, so a single subtask's rollback-marked `DomainException` would poison the whole fan-out and destroy best-effort. With no ambient transaction each subtask opens its own physical transaction; one subtask's failure rolls back only that subtask. Mirror `WorkflowBatchSubmissionService` (`WorkflowBatchSubmissionService.java:48-53` — the documented "central trap"): top-level method un-annotated; use `TransactionTemplate` with `PROPAGATION_REQUIRES_NEW` for the idempotency reserve/complete, the proposal-status flip, and the parent decomposition. See R1.
> 2. **Fan-out is TWO passes — all child runs first, then all dependency edges — because `run_dependencies` FKs reference sibling child run public_ids.** A dependency edge `(run_id, depends_on_run_id)` has `ON DELETE RESTRICT` FKs to `workflow_runs.public_id` (`V28`); you cannot declare an edge to a prerequisite child that does not exist yet. So: **Pass A** — for each subtask, create the sub-ticket (or internal-only) + mint the child run in `INBOX` with `parentRunId`, building an `ordinal → childRunId` map. **Pass B** — for each child that has prerequisites, `declareDependencies` (parks it in `WaitingForDependencies`); then `dispatchWhenUnblocked` every child (no-dep children dispatch, parked children no-op). Doing edges inside Pass A would FK-fail on forward references. See R2.
> 3. **`declareDependencies` parks dependent children but does NOT dispatch zero-dependency children — you must also call `dispatchWhenUnblocked` per child.** `RunDependencyService.declareDependencies` (`RunDependencyService.java:76`) takes the graph advisory lock, validates acyclicity, persists edges idempotently, and — if prerequisites are unmet and the run is in `INBOX` — parks it. It deliberately does **not** dispatch when prerequisites are already satisfied/absent (that path logs "left unparked"). The actual dispatch is `dispatchWhenUnblocked(runId, correlationId)` (`RunDependencyService.java:167`): `blockedOn.isEmpty()` → `dispatchSpecGeneration` → `DISPATCHED`; unmet + `INBOX` → `PARKED`; otherwise `SKIPPED`. So 3f-5's uniform Pass-B step per child is: `declareDependencies(...)` (only if the subtask has incoming edges) **then** `dispatchWhenUnblocked(...)`. The latter is idempotent and safe to call on an already-parked child (returns `SKIPPED`). See R3.
> 4. **Map the proposal's `dependencies[]{fromOrdinal,toOrdinal}` to `declareDependencies(dependentRunId, [prerequisiteRunIds])` — and PIN THE DIRECTION with a test, because getting it backwards silently inverts execution order with no error.** `declareDependencies(runId, dependsOnRunIds)`: `runId` is the **dependent**, `dependsOnRunIds` are its **prerequisites**. The proposal edge `{fromOrdinal, toOrdinal}` direction is defined by 3f-4's `split-proposal.v1` semantics (the runner prompt: "Task 3 starts after Task 1+2"). **Before coding, confirm against `split-proposal.v1.schema.json` + the 3f-4 runner decomposition prompt which ordinal is the dependent and which is the prerequisite**, then assert the mapping in a focused test (e.g. proposal `{from:3,to:1}` ⇒ run_dependencies row `(child3, child1)` meaning child3 depends on child1). A backwards mapping passes every type check and every smoke test but runs the subtasks in the wrong order — a silent disaster. See R4.
> 5. **The internal-only fallback (no subticket) must STILL link the child run to the parent's ticket — and there is no existing helper, 3f-5 owns it.** `TicketSourceSubticketService.createSubticportIfSupported(...)` returns `CREATED` (child sub-ticket made), `INTERNAL_ONLY_SKIPPED` (connector can't create — `supportsTicketCreation=false`), or `NO_TICKET_SOURCE` (project has no connector). On `CREATED` the child run links to the **new sub-ticket's** `childRef`; on `INTERNAL_ONLY_SKIPPED`/`NO_TICKET_SOURCE` the child run links **internal-only to the parent's own `TicketRef`** (epic AC2/AC7: "linking the child to the parent's ticket"). Establishing that child↔ticket linkage uses the existing `IntegrationLink` seam (story 3-32) — **re-grep `IntegrationLinkService` for the create/associate signature and reuse it; do NOT hand-roll a link row** ([[integration-link-adapter-tx-and-supersede]], [[integration-link-mapper-lazy-proxy-on-worker-thread]]). See R5.
> 6. **The parent decomposition is a guarded, idempotent two-step appended AFTER the fan-out, only when ≥1 child was created; the `workflow.split` event is appended SEPARATELY from the SPLIT transition.** `WorkflowTransitionService.transition(...)` hardcodes `WorkflowEventType.WORKFLOW_STATE_CHANGED` — it does not emit `workflow.split`. So decomposition = (i) flip the proposal `open → approved` (compare-and-set guard), (ii) `transition(parentId, WorkflowState.SPLIT, actor, reason, key)` (legal only from `WaitingForSpecApproval`/`WaitingForReview` — the 3f-2 into-edges), (iii) `workflowEventWritePort.append(new WorkflowEventRecord(..., WorkflowEventType.SPLIT, ..., Map.of(WorkflowEventDetailKeys.CHILD_RUN_IDS, childRunIds)))` carrying the allow-listed `childRunIds`. On replay, the proposal CAS (already `approved`) and the SPLIT into-edge guard (parent already in `SPLIT` → transition rejected) both short-circuit; swallow + return the prior children. **Zero children created ⇒ skip all three steps entirely: parent untouched at its gate, proposal stays `open`, return an explicit aborted outcome (R7).** See R6.
> 7. **Zero-child abort is a RESULT STATE, not a thrown error (consistency with 3-18 best-effort) — no new `DomainErrorCode`.** When every subtask fails, the commit returns a `SplitCommitResponse` with `parentDecomposed=false` + `outcome=ABORTED_NO_CHILDREN` + the per-subtask failure list; HTTP 200/207 (partial), parent and proposal untouched (operator may re-propose or retry). Do **not** add a new three-sites `DomainErrorCode` for this (the epic's "a clear error is returned" is satisfied by the explicit aborted result, mirroring how `WorkflowBatchSubmissionService` reports all-rejected via the result, not an exception). If product later wants a hard 4xx ProblemDetails, that is an additive follow-up. See R7.

## Story

As an operator who approved a split proposal,
I want the system to create the subtasks — as real sub-tickets where possible, otherwise internal-only — wire their dependencies, and decompose the original run,
so that the decomposition is committed as governed child runs with preserved lineage, on a best-effort basis that never half-terminates the parent.

No new gate state; the overlay is additive (existing gate actions intact).

2. **Given** `APPROVE_SPLIT` over a run's current **open** proposal, **Then** `SplitCommitService.commit` runs **best-effort + NON-transactional** (the 3-18 pattern, R1): each subtask is processed so one subtask's failure does not poison the rest; the top-level approve is idempotent under its `Idempotency-Key` (reuse `IdempotencyService.checkAndReserve/complete` in `REQUIRES_NEW`, mirroring `WorkflowBatchSubmissionService`).

3. **Given** per subtask (two passes, R2), **Then** the commit: **(Pass A)** creates a sub-ticket via `TicketSourceSubticketService.createSubticketIfSupported(project, parentTicketRef, draft)` — `CREATED` links the child to the new sub-ticket, `INTERNAL_ONLY_SKIPPED`/`NO_TICKET_SOURCE` links the child **internal-only to the parent's ticket** (R5) — then mints a child run via `workflowRunCreatePort.create(childId, INBOX, parentProjectId, parentRunId)` (3f-2), building an `ordinal → childRunId` map; **(Pass B)** for each child with proposed prerequisites, records the dependency edges via `runDependencyService.declareDependencies(...)` (3f-3) with the edge direction PINNED (R4), then calls `runDependencyService.dispatchWhenUnblocked(childId, correlationId)` for every child (R3).

4. **Given** dependency-gated dispatch, **Then** a child with **no** unmet dependencies dispatches its spec generation immediately (`dispatchWhenUnblocked → DISPATCHED`); a child **with** unmet dependencies is parked in `WaitingForDependencies` (`declareDependencies` parks it; `dispatchWhenUnblocked → SKIPPED`) — e.g. spec=Task1/Task2 dispatch, Task3 (depends on 1+2) parks.

5. **Given** the parent-decomposition guard (R6), **Then** **only if ≥1 child run was created** the commit: flips the proposal `open → approved` (CAS), transitions the parent to **non-terminal** `SPLIT` (`WorkflowState.SPLIT`, "Split"; legal only from the two gates, 3f-2 into-edge), and appends `workflow.split` (`WorkflowEventType.SPLIT`) carrying `childRunIds` via the allow-listed `WorkflowEventDetailKeys.CHILD_RUN_IDS`. The parent later rolls up to `COMPLETED` via 3f-7 (not this story). **If zero children were created, the split aborts: the parent stays at its gate, the proposal stays `open`, and an explicit aborted result is returned — the parent is never left half-decomposed (R7).**

6. **Given** idempotency, **Then** the commit is keyed on parent run + proposal id (`split-commit:<parentRunId>:<proposalId>`) and per-child keyed on parent + ordinal (subticket key `split:<parentRunId>:<proposalId>:<ordinal>`, child-run submit key, and deterministic dependency-declare key) so a replayed approve neither double-creates sub-tickets/children nor double-decomposes the parent. Defense in depth: the top-level `Idempotency-Key`, the proposal-status CAS (`open → approved`), and the `SPLIT` into-edge guard all independently short-circuit a replay.

7. **Given** the result + FE, **Then** the `POST /split/approve` response reports per-subtask outcome (`created` / `internal_only` / `failed`) + `parentDecomposed` + the child run ids; the FE Split Proposal Panel (3f-4) shows the commit result and links parent → children; the new lineage (`parentRunId` + `childRunIds`) renders in the run view (3f-2 read model). `GET /split-proposal` reflects the approved status.

8. **Given** a connector with no creation support, **Then** the whole split still succeeds **internal-only** (children link to the parent ticket) — proving the 3f-1 capability fallback end-to-end.

9. **Given** tests, **Then** a full IT proves request → (re-propose) → **approve** → N children created (mixed sub-ticket + internal-only) with lineage + dependency edges, the dependent child parked while others dispatch, parent → `SPLIT` + `workflow.split`; the **zero-child guard** (all subtasks fail → parent + proposal untouched); idempotent replay (no double children/sub-tickets/decomposition); the **dependency edge direction** pin (R4); `application.*` ≥ 80% line coverage.

### R1 — `SplitCommitService.commit` MUST NOT be `@Transactional`
This is the 3-18 "central trap" verbatim (`WorkflowBatchSubmissionService.java:48-53`). The per-subtask seams (`workflowRunCreatePort.create`, `runDependencyService.declareDependencies`, the transition) are each `@Transactional(REQUIRED)`. ### R2 — Two-pass fan-out (children, then edges)
`run_dependencies(run_id, depends_on_run_id)` has `ON DELETE RESTRICT ON UPDATE CASCADE` FKs to `workflow_runs.public_id` (`V28`). Declaring an edge to a prerequisite child that hasn't been minted yet FK-fails. So Pass A mints every child (building `ordinal → childRunId`), Pass B declares edges + dispatches. Per-subtask Pass-A failures simply drop that ordinal from the map; a Pass-B edge that references a dropped ordinal must be skipped (its prerequisite never got created — log and continue, do not FK-fail the dependent's whole subtask).

### R3 — `declareDependencies` parks; `dispatchWhenUnblocked` dispatches
`RunDependencyService.declareDependencies` (`:76`) takes the graph advisory lock (`pg_advisory_xact_lock`, key `0x52444550` "RDEP"), validates acyclicity (`RUN_DEPENDENCY_CYCLE`), persists edges (`on conflict do nothing`), and parks the run in `WaitingForDependencies` if prerequisites are unmet **and** the run is `INBOX`. It does **not** dispatch the satisfied/zero case. `dispatchWhenUnblocked(runId, correlationId)` (`:167`) is the dispatcher: empty `blockedOn` → `dispatchSpecGeneration` → `DISPATCHED`; unmet + `INBOX` → `PARKED`; else `SKIPPED`. Uniform Pass-B per child: `declareDependencies` only if the subtask has incoming edges, **then** `dispatchWhenUnblocked` for every child. The advisory lock is taken internally by both — **do not** call `lockDependencyGraph()` yourself, but DO stay aware that these are the graph's serialization points ([[story-3f-3-run-dependency-graph-waiting-for-dependencies-reconciliations]]).

### R4 — PIN the dependency edge direction
`declareDependencies(runId, dependsOnRunIds)`: `runId` = dependent, `dependsOnRunIds` = prerequisites. The proposal's `dependencies[]{fromOrdinal,toOrdinal}` direction is set by 3f-4's `split-proposal.v1` + the runner decomposition prompt. **Confirm which ordinal is the dependent before mapping**, then assert it in a test. A backwards mapping (running prerequisites as dependents) type-checks, smoke-tests green, and silently inverts execution order — exactly the class of bug this story-context exists to prevent. Reference: `split-proposal.v1.schema.json`, `SplitDependencyView(fromOrdinal,toOrdinal)`, and the 3f-4 runner prompt.

### R5 — Internal-only child links to the parent's ticket (3f-5 owns the wiring)
`TicketSourceSubticketService.createSubticketIfSupported(Project, TicketRef, SubticketDraft)` returns `TicketSourceSubticketOutcome` (`CREATED` / `INTERNAL_ONLY_SKIPPED` / `NO_TICKET_SOURCE`). On `CREATED` link the child to `result.childRef()`; otherwise link the child internal-only to the **parent's** `TicketRef`. There is no pre-built "link child to parent ticket" helper — reuse `IntegrationLinkService` (3-32). `SubticketDraft` fields: `(parentRunId, proposalId, subtaskId, ordinal, title, description, idempotencyKey)`; idempotency key `split:<parentRunId>:<proposalId>:<ordinal>` (the Linear adapter's marker-scan replay backstop keys off this — same key on replay returns the existing child, `replay=true`). Note the documented residual race in the Linear adapter (crash between issue-create and marker-comment) — acceptable, not 3f-5's to solve.

### R6 — Parent decomposition: guarded, idempotent, event appended separately
Only when `createdCount >= 1`: (i) CAS proposal `open → approved` via `SplitProposalWritePort` — a replay finds it already `approved` and short-circuits; (ii) `workflowTransitionService.transition(parentId, WorkflowState.SPLIT, actor, "approve_split", "split-commit:<parentRunId>:<proposalId>")` — the 3f-2 into-edge from `WaitingForSpecApproval`/`WaitingForReview` is the only legal path; a replay finds the parent already in `SPLIT` and the transition table rejects it (catch/treat as no-op); (iii) `workflowEventWritePort.append(new WorkflowEventRecord(PublicIdPrefixes.WORKFLOW_EVENT.next(), parentId, WorkflowEventType.SPLIT, priorGateState, /*resulting*/ null-or-SPLIT, actorIdentity, actorType, "approve_split", null, false, now, Map.of(WorkflowEventDetailKeys.CHILD_RUN_IDS, childRunIds)))`. The `childRunIds` detail key is already allow-listed (3f-2). Steps (i)-(iii) belong in one `REQUIRES_NEW` tx so a partial decomposition can't strand the parent ([[caught-idempotency-conflict-poisons-shared-tx]] — prevent the conflicting flush, don't catch it after).

### R7 — Zero-child abort is a result state, not an exception
All-subtasks-fail ⇒ `SplitCommitResult{parentDecomposed=false, outcome=ABORTED_NO_CHILDREN, subtasks=[...failed]}`, HTTP 200/207, parent + proposal untouched. This mirrors `WorkflowBatchSubmissionService` reporting all-rejected via the result. No new three-sites `DomainErrorCode` ([[new-domainerrorcode-three-sites]] — avoid the foundation-gate cost when a result state suffices). The operator can re-propose or retry the still-`open` proposal. If product later wants a hard 4xx, that's an additive follow-up (out of scope).
