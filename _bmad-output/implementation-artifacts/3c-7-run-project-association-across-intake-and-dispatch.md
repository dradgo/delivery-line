# Story 3c.7: Run ↔ Project Association across Intake + Dispatch

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **⚠️ READ FIRST — this is the story that makes non-default projects actually take effect.** Story 3c-6 (the "de-risking keystone", `done`) built the **read side + resolver** and proved single-project parity: it seeds a reserved `default` project, backfills every existing run, binds **every new run to the `default` project at create**, and repointed the **one already-isolated** repo-ref seam (`RepositoryWorkspaceService.resolveExpectedRepositoryRef`). It explicitly **stopped there** and handed 3c-7 the rest of the hot path. This story threads `project_id` through **the remaining consumers** so a run scoped to a **non-`default`** project dispatches with **that** project's repository, connectors, and OpenSpec mode. Everything you build on is already merged:
>
> - **`ProjectRuntimeConfigResolver`** (`application.project`, 3c-6) — `Project resolveForRun(String workflowRunId)` (run `project_id` → `findByPublicId`, `default`-slug fallback, `PROJECT_NOT_FOUND` only if even the default is missing), `Optional<String> resolveRepositoryRef(String workflowRunId)` (normalized `owner/repo` via `RepositoryRef.normalizeRepositoryUrl`), `boolean resolveOpenSpecEnabled(String workflowRunId)`. **This is the resolver 3c-7 consumes at every hot-path site.**
> - **`ProjectConnectorResolver`** (`application.project`, 3c-3) — `TicketSourceAdapter resolveTicketSource(Project)`, `RepositoryHostAdapter resolveRepositoryHost(Project)` (both throw `UNSUPPORTED_CONNECTOR_KIND` when no adapter is registered for the project's kind), `void assertRepositoryRefMatchesProject(Project, String repositoryRef)` (project-scoped `LINEAR_GITHUB_REPO_MISMATCH` guard, no-op when the project carries no binding), `Optional<String> resolveConnectorSecret(Project, String role)` (returns empty today → adapters fall back to host-env secrets).
> - **`ProjectStore`** (`application.project`, 3c-6) — `findBySlug`, `findByPublicId`, `insert`, `backfillNullProjectIds`, **`Optional<String> findProjectIdForRun(String runPublicId)`** (the focused run→project_id read the resolver already uses).
> - **`workflow_runs.project_id`** is **already persisted at create** (3c-6 threaded `projectId` through `WorkflowRunCreatePort.create(publicId, initialState, projectId)`; `WorkflowCommandService.submitInternal` resolves `default` and binds it). The column is V17, nullable in schema, backfilled + treated-as-required by the app.
> - **`Project` aggregate** (`domain.project`, 3c-2) — `publicId, name, slug, status, repositoryUrl (nullable, raw), ticketSourceKind (ConnectorKind), repoHostKind (ConnectorKind), openspecEnabled, createdAt, archivedAt`.
> - **Error codes** `PROJECT_NOT_FOUND(404)`, `UNSUPPORTED_CONNECTOR_KIND(400)`, `PROJECT_SLUG_CONFLICT(409)` — **all three already three-sites-registered** (3c-2). **Consume only — do NOT register any new code.**
>
> **The scope boundary (read it twice).** There is still **no Project CRUD REST API (3c-8, `backlog`)** and **no Projects UI (3c-9, `backlog`)**, so today the **only** project that exists at runtime is `default`. 3c-7 does **not** add a way to *create* a non-default project through a product surface — it makes the **wiring** correct so that *when* a non-default project exists (created via 3c-8, or inserted directly by the AC7 integration test), every dispatch path reads **its** config instead of the global. The end-to-end proof is the AC7 integration test that **inserts a non-default project directly** and asserts the run dispatches with that project's repo/connector/OpenSpec. Do **not** pull 3c-8's CRUD or 3c-9's UI forward; do **not** leave any hot-path consumer still reading global config on the per-run path.

## Story

As a backend developer,
I want every run-creation, dispatch, queue, and completion-sync path to resolve and honor the run's Project,
so that a run's repository, connectors, and run options always derive from its Project rather than global config — and a run scoped to a non-`default` project dispatches with that project's settings while a `default`-project run stays byte-identical to pre-3c.

## Acceptance Criteria

> These ACs are **reconciled** against the live codebase. 3c-6 already binds new runs to the `default` project and repointed the repo-ref guard; there is no Project CRUD/UI yet (only `default` exists at runtime); the queue row carries no `project_id`; Linear sync resolves a single profile-gated global adapter. Where the epic 3c-7 wording assumes infrastructure that does not exist yet or work another story owns, the reconciled wording below is authoritative; the rationale is in Dev Notes.

1. **Given** CLI `submit` (and `submit-batch`) and the REST `submit-workflow` intake, **Then** each accepts an **optional explicit project reference** (project slug or `prj_` public id); `WorkflowCommandService.submitInternal` resolves it — **explicit reference → `projectStore.findBySlug`/`findByPublicId`, else `PROJECT_NOT_FOUND`; absent → the `default` project** (the 3c-6 fallback). The resolved `project_id` is bound to the run at create exactly as 3c-6 already wires it. (Routing a run to a project by **ticket-source identity** — "which Linear workspace owns this ticket" — is **deferred**: projects today carry only a connector *kind*, not a per-project ticket-source identity to disambiguate on, so it cannot be resolved without 3c-8's per-project connector config. R1.)

2. **Given** the runner bundle composition (`RunnerBroker.composeQueuedBundle`), **Then** the repository ref it resolves for the bundle/clone is read from **`projectRuntimeConfigResolver.resolveRepositoryRef(workflowRunId)`** (run → Project, `default` fallback) instead of the global `repositoryWorkspaceService.resolveConfiguredRepositoryRef()`. The OpenSpec mode emitted at dispatch is read from **`projectRuntimeConfigResolver.resolveOpenSpecEnabled(workflowRunId)`** (R2). Connector **selection** (ticket-source / repo-host adapter) is resolved per the run's Project via `ProjectConnectorResolver` at the use sites (AC3, AC4) — **no new connector payload is embedded in the context bundle** (the 2 KB/256 KB bundle cap stands; see [[context-bundle-2kb-payload-cap]]).

3. **Given** workspace preparation + repo-host operations, **Then** the clone target uses the project's resolved repository binding (AC2) and the **project-scoped `LINEAR_GITHUB_REPO_MISMATCH` guard** is applied (`RepositoryWorkspaceService.resolveExpectedRepositoryRef` is already repointed by 3c-6; 3c-7 additionally validates the requested ref against the run's Project via `ProjectConnectorResolver.assertRepositoryRefMatchesProject` where a Project is in hand). The resolved **repo-host adapter** is selected via `ProjectConnectorResolver.resolveRepositoryHost(project)` and its `getCapabilities()` is honored unchanged. **Credentials stay on the existing host-env path** (`GITHUB_TOKEN`) — the encrypted per-project credential store is 3c-5 (`in-progress`), not consumed here (R4).

4. **Given** Linear completion sync (`WorkflowOrchestrationService.syncCompletionToLinear(workflowRunId)`, story 3.16), **Then** it resolves the ticket-source adapter via the run's Project — `project = projectRuntimeConfigResolver.resolveForRun(workflowRunId)`, `adapter = projectConnectorResolver.resolveTicketSource(project)` — and honors that adapter's `supportsCommentOnTicket()` capability exactly as today. **TRAP (R3):** the current code skips with `SKIPPED_NO_LINEAR_PROFILE` when **no** ticket-source adapter bean is active (profile-gated `linear-mock|linear-real`). The per-project resolution **must preserve that skip** — a context with no registered adapter for the project's kind resolves to "no adapter available → SKIP", **not** a thrown `UNSUPPORTED_CONNECTOR_KIND`.

5. **Given** the runner queue, **Then** a queued run dispatches with its own project configuration because the worker **re-resolves the project from the run** at dispatch (`workflowRunId` → `project_id` persisted on `workflow_runs` at create by 3c-6 → resolver). **No `project_id` column is added to the queue row / `QueuedRunnerExecution` / `RunnerExecutionSnapshot`, and no Flyway migration is introduced** — the durable run row already "carries" the project; the worker reads it lazily (R5).

6. **Given** audit history + FR63 ("which project a run/ticket/artifact belongs to"), **Then** the run's `project_id` is already durably recorded on `workflow_runs` at create (3c-6); 3c-7 **verifies** it is correct for non-default runs and ensures every dispatch decision is logged with `project.publicId()`. No new audit table, event type, or read-model column is required for this AC (FR63 is answerable by the persisted `workflow_runs.project_id`). (R6.)

7. **Given** tests, **Then** an integration test **inserts a non-default project directly** (repo binding + kinds + OpenSpec differing from the global/default) and asserts a run scoped to it dispatches with **that** project's repository ref, repo-host/ticket-source adapter selection, and OpenSpec env; and a separate parity test asserts a **`default`-project run remains byte-identical to pre-3c** (same repo ref, OpenSpec off ⇒ no `DELIVERYLINE_RUNNER_OPENSPEC` env, same Linear sync behavior). New/changed code on `application.runner` + `application.project` + `application.workflow` meets the standing **≥80% line-coverage** floor.

### R1 — Explicit reference now; ticket-source-identity routing is deferred
AC1's "resolution by ticket-source binding" presumes a project carries an identity you can match a ticket against (e.g. a Linear team/workspace id). The `Project` aggregate carries only `ticketSourceKind` (`linear`) — not *which* Linear instance. With per-project connector **config** (URLs, identities, credentials) landing in 3c-8/3c-5, identity-based routing has nothing to key on yet. So 3c-7 ships the **explicit reference** path (slug or `prj_` id on submit) + keeps the `default` fallback. When 3c-8 adds per-project ticket-source identity, a follow-up can resolve "the project whose ticket-source identity owns this ticket." Note this forward obligation in Completion Notes; do not invent a half-identity scheme now.

### R2 — Resolve-in-broker, pass-via-request (do NOT inject the resolver into the adapter)
`DockerRunnerAdapter` is an `adapters.runner` class. Threading OpenSpec by injecting `ProjectRuntimeConfigResolver` into it would add an adapter→application-service dependency and re-read config on the hot path. The established pattern in this codebase is: the **broker** (application) resolves `repositoryRef`, `linearTicketRef`, `subStage` and **passes them as `RunnerDispatchRequest` fields**; the adapter is a dumb executor. Follow it: add `boolean openspecEnabled` to `RunnerDispatchRequest`, resolve it in `RunnerBroker.executeQueuedDispatch` via `resolveOpenSpecEnabled(workflowRunId)`, and have the adapter emit the env from `request.openspecEnabled()`. This also dodges the [[docker-adapter-ctor-dep-fans-out]] ctor-fan-out trap. The repo-ref for the **bundle** is resolved in the broker the same way (Task 2).

### R3 — Linear sync: preserve `SKIPPED_NO_LINEAR_PROFILE`
`syncCompletionToLinear` runs in many `@SpringBootTest` contexts with **no** linear profile active → `linearAdapterProvider.getIfAvailable()` returns null → `SKIPPED_NO_LINEAR_PROFILE`. If you blindly call `projectConnectorResolver.resolveTicketSource(project)`, a no-adapter context throws `UNSUPPORTED_CONNECTOR_KIND` and reds a swath of orchestration tests. Resolve to an `Optional<TicketSourceAdapter>` that returns empty when no adapter is registered for the project's kind (probe-before-resolve, or a tightly-scoped catch mapped to the skip). This is the single highest-risk regression in the story.

### R4 — Credentials stay host-env (3c-5 is not the secret source yet)
3c-5 (encrypted credential store) is `in-progress`; `ProjectConnectorResolver.resolveConnectorSecret` returns empty today and adapters fall back to the host-env path (`LINEAR_API_TOKEN`/`GITHUB_TOKEN`). 3c-7 **does not** read per-project secrets — it selects the right **adapter** per project but the adapter sources its secret from the host env exactly as before. Do **not** call `resolveConnectorSecret` on the dispatch path; do **not** map `project_credentials`. Forward obligation: when 3c-5 completes, the connector secret resolution flips to the store at the use site, and ciphertext/key material must never reach logs/events/artifacts/exports.

### R5 — The queue does not need a `project_id` column
The worker dequeues `RunnerExecutionSnapshot.workflowRunPublicId()`; `workflow_runs.project_id` is already persisted at create. The worker re-resolves the project from the run at dispatch via `ProjectRuntimeConfigResolver`. Denormalizing `project_id` onto the queue row would add a Flyway migration + a fan-out across `QueuedRunnerExecution`/`RunnerExecutionSnapshot`/`RunnerExecutionRecordPort` for **zero** benefit (the run row is the source of truth and never changes its project). Keep the queue read-only of project.

### R6 — FR63 is already satisfiable
`workflow_runs.project_id` (written at create by 3c-6, FK to `projects.public_id`) answers "which project does this run belong to." Tickets/artifacts are reachable from the run, so FR63 ("which project a run/ticket/artifact belongs to") needs no new structure here. 3c-7's obligation is to (a) ensure the bound id is correct for explicit/non-default intake and (b) log `project.publicId()` at every dispatch decision for traceability.

### R7 — Byte-identical parity is the safety net (mirror 3c-6 AC4)
The `default` project is seeded from exactly the global values (`repos.url`, kinds, openspec flag). So every repoint in this story (`resolveRepositoryRef`, `resolveOpenSpecEnabled`, per-project adapter selection) must return the **same** value the global path returned for a `default`-project run: same `owner/repo`, openspec off ⇒ no env var, same global Linear adapter. The AC7 parity test is the proof; if any default-project behavior drifts, the repoint is wrong. New behavior only manifests for a **non-default** project (which only the AC7 test creates today).
