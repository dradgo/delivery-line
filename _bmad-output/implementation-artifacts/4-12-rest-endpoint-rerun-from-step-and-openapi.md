## Story

As a frontend developer (Decision Bar `recovery_operator` mode in story 4.22) and CLI user,
I want a REST endpoint `POST /api/v1/workflows/{workflowRunId}/rerun-from-step` wired to `RecoveryService.rerunFromStep` (story 4.7) **restricted to safe step boundaries**, plus the sibling `deliveryline operator rerun-from-step` CLI command,
so that rerun-from-step initiation flows through the standard mutation conventions (idempotency + Problem Details + OpenAPI) with explicit `targetStep` validation against the `SafeRerunStep` safe-boundary enum (`investigating` / `executing`).

## Dev Notes

### Relevant architecture patterns and constraints

- **The 4.10 `resume` method (`WorkflowController.java:2083-2160`) is the exact structural template**, in-repo (uncommitted, working tree). Copy: annotations → guard prologue → `requireWorkflowOwnerRole` → `ActorContext` build → service call → rich response `from(runId, result)` → two log lines. `rerun-from-step` differs only in the six ways enumerated in Reconciliation 3 (two body fields, both un-`@NotBlank`, two list response fields, `currentState` REQUIRED, `ILLEGAL_TRANSITION` wrong-state code).
- **Two-endpoint trap (service layer).** `WorkflowCommandService.rerunFromStepWorkflow` (thin, transition-only, called INTERNALLY by the rich service) vs `RecoveryService.rerunFromStep` (rich). 4.12 ships one endpoint wired to the rich path — Reconciliation 2. Wiring the thin path silently skips approval invalidation + audit + runner re-dispatch + the source-state gate.
- **`ActorContext` lives in `org.dradgo.application.artifact`**, not `application.recovery`. Its canonical ctor rejects a blank `actorIdentity`/null `actorType` — safe because `localActorIdentityResolver.resolve(...)` falls back to `local-operator` and `ActorType.HUMAN` is hard-coded.
- **RBAC is audit-only.** `requireWorkflowOwnerRole` is a request-shape check; the controller never returns 401/403. The resolved actor identity is stamped on the audit trail. Note `requireWorkflowOwnerRole` throws `INVALID_REVIEWER_ROLE_FOR_ENDPOINT` for a non-blank wrong role; a BLANK `role` is caught by `@NotBlank` bean-validation FIRST as `INVALID_COMMAND_PAYLOAD` (the 4.10 debug-log lesson — split the test accordingly).
- **The `rerun_from_step` allowed-action is state-gated** to {FAILED, WAITING_FOR_REVIEW} for `ROLE_WORKFLOW_OWNER` (4.7 AC10) — the controller adds NO state check of its own; the `RERUN_SOURCE_STATES` gate inside the service is the enforcement (`ILLEGAL_TRANSITION`). The allowed-actions list is a read-model concern, NOT a service guard (4.7 re-review finding).
- **Idempotency: two surfaces, you touch neither.** `recovery_actions.idempotency_key` unique key (outer) + `executeIdempotent` inside `WorkflowCommandService.rerunFromStepWorkflow` (inner). `RecoveryService.rerunFromStep`'s replay pre-check guards `actionType == rerun` (`:1895`) — cross-action key reuse is `IDEMPOTENCY_KEY_CONFLICT`, not a false replay. The fingerprint treats `targetStep` AND `reasonText` as identity (4.7 re-review patches), so a same-key/different-step or different-reason call is a conflict — the controller passes the raw header + fields through and lets the service decide.
- **No `WorkflowCommand` permit, no fingerprint arm, no `EXPECTED_PERMITS` edit.** `RerunFromStepWorkflowCommand` was already added to the sealed hierarchy by 4.7. This story adds only REST DTOs, which are not `WorkflowCommand`s.

### Logging Requirements (project-wide standard)

- **Framework:** SLF4J + Logback. No `System.out` / `printStackTrace()`.
- **Where to log:** REST entry (`INFO`), REST success (`INFO`), role rejection (`WARN`, inside the shared helper), CLI completion (`INFO`, success + failure with the typed `DomainErrorCode`). The recovery-service log surface is already pinned by 4.7's `RecoveryLoggingContractTest` — do not duplicate it in the adapter.
- **Required context keys:** `correlationId`, `workflowRunId`, `actorIdentity`, `targetStep`, plus `recoveryActionId` + `supersededCount` + `invalidatedApprovalCount` on success. MDC `correlationId` is stamped by `CorrelationIdFilter` (REST) and `pushCorrelation` (CLI).
- **Forbidden:** `reasonText` prose (log its length only), idempotency-key values, secrets, tokens, PII. The `targetStep` value IS loggable (bounded governed enum).
- **Test contract:** `ListAppender` pins on the `WorkflowController` logger for entry/success/rejection.
