# Story 4.16: Artifact Reconciliation — Operator-Driven Repair Actions

Status: ready-for-dev

## Story

As a Workflow Owner reviewing detected drift from story 4.15,
I want operator-triggered repair methods on `ArtifactReconciliationService` (`markOperationFailed`, `markOperationComplete`, `markPayloadUnavailable`, `restoreFromBackup`, `markCorrupted`, `reVerifyChecksum`) plus a REST endpoint `POST /api/v1/artifact-drift/{driftId}/repair` and the sibling `deliveryline operator artifact-repair` CLI command to invoke them,
so that AR14 (artifact reconciliation deeper than the story 1.12 skeleton) is fully realized — operators resolve detected drift through explicit, auditable decisions (NFR19: no silent overwrite).

## Context & Central Reconciliation (READ FIRST)

**This is the REPAIR half of the Epic-4 artifact-reconciliation split (detection = 4.15 `done`/`review`, operator-driven repair = 4.16 THIS story, lineage/fork governance = 4.16a — a SEPARATE `backlog` story you MUST NOT build here).** Story 4.15 already shipped and is on-branch (see [[story-4-15-artifact-drift-detection]]): the `artifact_drift_detected` table (**V45** — `resolved_at`/`resolved_by_action_id` columns + `fk_artifact_drift_detected_recovery_actions` FK already exist, **nullable + unwritten, waiting for you**), the `DriftCategory` persisted enum, the `adr_` `PublicIdPrefixes.ARTIFACT_DRIFT_DETECTED` prefix, the `WorkflowEventType.ARTIFACT_DRIFT_DETECTED` event, the drift write/read ports (`ArtifactDriftWritePort.recordIfAbsent` + `ArtifactDriftReadPort.listUnresolved`/`countUnresolvedByCategory`), the `listUnresolvedDrift(DriftFilter) → List<DriftSummary>` read surface on `ArtifactReconciliationService`, and the computed `RepairActionHint`. **You consume all of that; you build the WRITE/repair path on top of it.**

**⚠️ THIS IS A RICH STORY, NOT A PURE ADAPTER.** Unlike the 4.10–4.14 REST slice (where 4.5–4.9 had already built the whole application/domain half and the endpoints were pure wiring), **4.16 builds BOTH halves**: (1) the operator-repair application logic on `ArtifactReconciliationService`, (2) new drift persistence methods (resolve + single-row lookup), (3) `ArtifactStatus.corrupted` + a migration widening two CHECKs, (4) four new `DomainErrorCode`s, (5) a NEW `artifact.driftRepaired` event, (6) a NEW non-workflow-scoped `ArtifactDriftController`, and (7) the CLI command + equivalence tests. Budget accordingly — this is closer in size to a 4.7/4.8 recovery story than to a 4.14 adapter story.

### Relevant architecture patterns and constraints

- **Repair-vs-detection split (build on 4.15).** Story 4.15 shipped detection-only: the `artifact_drift_detected` table (V45), drift ports, `DriftCategory`, `RepairActionHint`, `adr_` prefix, `ARTIFACT_DRIFT_DETECTED` event, and `listUnresolvedDrift`. 4.16 is the WRITE/repair half. Read `ArtifactReconciliationService.java` end-to-end first — the `PROPAGATION_REQUIRES_NEW` per-item `TransactionTemplate`, per-tick `UUID` correlationId, `ActorContext.SYSTEM`, `ArtifactEventPort.append(ArtifactEventRecord)`, and `MdcKeys.beginScope/endScope` idioms are the ones you extend. The service already injects `ArtifactDriftReadPort` (nullable in the test-only ctor); you add the write/resolve port + recovery-action port + approval service.
- **The `classifyFailure` recovery-action precedent (mirror for the write + idempotency).** `RecoveryService.classifyFailure` (story 4.9) is the single-tx, `succeeded`-on-INSERT, replay-first precedent: replay pre-check with an `action_type` guard BEFORE input validation; detail payload built as a `LinkedHashMap` on the RESULTING event (there is NO `recovery_actions.details` column); the event's `evt_` id set as `resulting_event_id`. Reuse `RecoveryActionRecordPort.insert(RecoveryActionWriteCommand)` (9-arg: `workflowRunPublicId, actionType, triggeringEventPublicId, resultingEventPublicId, actorIdentity, actorType, idempotencyKey, resultStatus, reviewerRole`) + `findByIdempotencyKey` for replay.
- **Idempotency is NOT the transition key.** `Idempotency-Key` uniqueness on `recovery_actions` + the `action_type`/run guard is the dedupe surface ([[transition-idempotencykey-is-not-a-dedupe-key]]); a caught conflict must not poison the shared tx ([[caught-idempotency-conflict-poisons-shared-tx]]) — but here the whole repair is one `REQUIRES_NEW` unit and the `recovery_actions` unique index + the replay pre-check do the work.

It flips the current approved leaf of the type (`invalidated_at`/`invalidated_reason`); there is no by-artifact-version finder (OQ-3).

### Logging Requirements (project-wide standard)

Every story is expected to leave the touched services observable enough to debug a production incident without re-deploying (enforced via the "Logging instrumentation" task).

- **Framework:** SLF4J + Logback. No `System.out`, no `printStackTrace()`.
- **Where to log (minimum surface for this story):**
  - `repairArtifactDrift` → `INFO` on entry (`driftId`, `repairAction`) + `INFO` on exit (result, `resolved`); `WARN` on replay (`replayed=true`).
  - Each typed repair → `INFO` "artifact repair applied" with `driftId`/`artifactId`/`operationId`, `repairAction`, `driftCategory`, per-tick `correlationId`.
  - Approval invalidation → `WARN` "approval invalidated by repair" with the `apr_` id + reason token.
  - `reVerifyChecksum` still-mismatched → `WARN` "re-verify checksum still mismatched — drift left unresolved".
  - `restoreFromBackup` stub → `WARN` "restore-from-backup not yet supported" (until backup integration).
  - REST controller → `INFO` received/success with sanitized reason (LENGTH only).
- **Required context keys** (MDC or params): `correlationId`, `workflowRunId`, `idempotencyKey`, `actorIdentity`, `driftId`, `artifactId`/`operationId`, `repairAction`.
- **Forbidden:** payload bytes, checksum contents beyond short hex, secrets/PII. Never log the artifact payload read for re-hashing.
- **Test contract:** pin the `INFO`-on-repair + `WARN`-on-approval-invalidation + `WARN`-on-reVerify-mismatch lines with a list-appender / `OutputCaptureExtension`; assert the idempotent replay emits NO second event.
