## Story

As an operator,
I want CPU-only Java/TypeScript linters to run before the LLM review, and critical findings to halt for my approval or a fix,
so that I never spend review tokens on code that fails static analysis — and critical findings are a governed gate, not an advisory note.

## 🧭 ARCHITECTURE DECISIONS — read before coding (these are firm; they simplify the epic AC wording)

**Decision 1 — LINT runs BACKEND-SIDE, exactly like BUILD (inherits the 3h-1 ADR-0030 amendment).** There is **no shell-command execution mode in the runner** — both entrypoints always invoke the LLM CLI. 3h-1 already established the backend-side execution model (ProcessBuilder in the materialized host workspace via `BuildCommandPort`). LINT reuses that model verbatim: a `LintStageService` runs the configured linters through the **existing `BuildCommandPort`** in the PR_OUTPUT execution's host workspace dir, records a `runner_executions` row with `stage = 'lint'`, and captures raw output through `RunnerLogCaptureService`. No Docker dispatch, no runner image, no `runner.mjs` change, no mock scenario.
[Source: 3h-1 story §"Architecture Decision"; docs/adr/0030 (amended by 3h-1); runners/codex/entrypoint.sh:676]

**Decision 2 — REUSE `BuildCommandPort`; do NOT invent a `LintCommandPort`.** `BuildCommandPort.run(Path repoDir, String command, Duration timeout)` is already a generic "run one shell command in a workspace, non-zero-exit-is-the-signal" port (`application/runner/workspace/spi/BuildCommandPort.java`). LINT needs to run **multiple** commands (`lintCommands`, Java + TypeScript), so `LintStageService` **loops** over the configured commands calling `buildCommandPort.run(...)` per command, **fail-fast on the first command whose exit signals critical findings**, aggregating captured output. The port + `ProcessBuildCommandAdapter` need **zero changes**. (A future neutral rename to `WorkspaceCommandPort` is a documented forward option — do **not** do it here; it would churn just-merged 3h-1 code for no functional gain.)
[Source: agent research — BuildCommandPort single-command signature; ProcessBuildCommandAdapter `sh -c`]

**Decision 3 — NO new `FailureCategory`; the lint fix loop NEVER auto-FAILs the run.** This is the key divergence from BUILD. BUILD's loop is *automatic* and escalates to `FAILED(RUNNER_BUILD_FAILED)` at cap. The **lint fix loop is operator-driven** (`request_lint_fix` is a manual REST action, fired once per press) and, per epic Cross-Cutting Notes ("the lint loop re-runs LINT after each fix" — no cap→FAILED clause), it re-runs LINT and re-parks; it does **not** transition the run to `FAILED`. Therefore:
- **No `RUNNER_LINT_FAILED`**, no `WorkflowTransitionTable.ALLOWED_RUNNER_FAILURE_CATEGORIES` edit, no `RunnerBroker.priorResultReceived` duplicate-switch arm, no `TransitionTableCrossProductFoundationContract` failure-category mirror. (This deletes a whole slice of the 3h-1-style fan-out.)
- The **LINT `runner_executions` row** is recorded `FAILED` with the **existing** `FailureCategory.RUNNER_NON_ZERO_EXIT` when critical findings are present (so the `lint.findings` feedback-by-reference query mirrors `build.failure`), and `COMPLETED` when only non-critical findings / clean.
- The **escalation marker** (`markEscalationOnce`, shared) is flipped once when `lint_fix_loop_count` reaches the cap — as an **operator-visibility flag only**; the run stays parked at `WaitingForLintApproval`. There is no infinite-loop risk because every iteration requires a manual `request_lint_fix`.
[Source: epic-03h Cross-Cutting Notes "Build and CI failures escalate on cap; the lint loop re-runs LINT after each fix"; agent research — RUNNER_NON_ZERO_EXIT is BUILD-row's non-zero category]

**Decision 4 — The LINT gate parks the WHOLE delivery tail; refactor 3h-1's seam to be RESUMABLE.** The lint gate sits at the **same point** BUILD's success-continuation sits — it wraps the **same** `completeExecutionTailAndAdvance` tail (captureAndPush + `WaitingForReview` + `enqueueReviewerIfConfigured`). On **critical** findings the tail is **not run** (no push, no review — the whole point). On `approve_lint` (fired later via REST) the tail must resume — **but the in-memory continuation lambda is gone by then.** So:
- **Move the PR-output validate/enrich/`recordCompleted(PR_OUTPUT)` ahead of the build+lint gates** (shrinking `completeExecutionTailAndAdvance` to just `captureAndPush` + `WaitingForReview` transition + `enqueueReviewerIfConfigured`). This resolves the concern 3h-1 explicitly flagged ("If an invariant forbids [deferring recordCompleted], move recordCompleted ahead of the build trigger and shrink the extracted seam") and makes the tail **re-derivable from `(runId)` alone**.
- Extract a lean, idempotent **`resumeDeliveryTailFromGate(runId, actor)`** seam (re-derives the PR_OUTPUT rex + workspace, runs the shrunk tail). Call it from (a) the in-memory LINT-pass / build-pass continuation **and** (b) the later `approve_lint` action. Same seam, two callers.

This is the single hardest part of the story — get the resume seam right and everything else is mechanical mirroring of 3h-1.
[Source: 3h-1 story §"Design decisions worth review" (deferred recordCompleted flag); RunnerBroker.completeExecutionTailAndAdvance 2241-2388; WorkflowOrchestrationService.onPrOutputStageSucceeded 997-1085]

**Decision 5 — Persist findings as `jsonb` on `runner_executions`; NOT a new table, NOT `step_reviews`.** Epic AC6 says "extend the `step_reviews` payload or a lint-findings store — chosen in the story to avoid a new table where the verdict store suffices." Research proved **`step_reviews` does not suffice**: it has a hard `outcome ∈ {pass,concern,fail}` CHECK, **no** payload column, and a **mandatory** composite FK to an `artifacts` row — a severity-classified findings array has no home there. Honoring the epic's "avoid a new table" preference, persist the classified findings as a **nullable `lint_findings jsonb` column on the existing LINT `runner_executions` row** (consistent with how `runner_executions` already carries stage-specific token + raw-output columns). No new table, entity, mapper, or repository — the LINT rex already exists and is read through the existing runner-execution read model.
[Source: agent research — V19 step_reviews shape (outcome CHECK + artifact FK, no payload col); runner_executions token/raw_output column precedent]

## Context — why this story exists (read before coding)

After 3h-1, the tail (when build is enabled) is `INVESTIGATION → EXECUTION(pr_output) → BUILD → completeExecutionTailAndAdvance(captureAndPush + WaitingForReview + REVIEW)`. There is still **no static-analysis signal** — broken-lint code flows straight to the (token-costly) LLM reviewer and to push.

This story inserts a cheap **CPU lint gate between BUILD and REVIEW**. When a governed project configures linters, they run backend-side after a successful build; the output is **severity-classified** (critical = linter `error`; non-critical = `warning`/`info`). A **critical** finding parks the run in a new non-terminal `WaitingForLintApproval` state **before any LLM review or push**, surfacing two operator actions: `approve_lint` (dismiss → proceed to review) and `request_lint_fix` (feed findings back to the implementation runner, re-run the chain). Non-critical findings are attached as advisory and the tail proceeds unchanged. It delivers **FR76**.
[Source: epic-03h Story 3h-2 + Cross-Cutting Notes]

## Acceptance Criteria

1. **`RunnerStage.LINT("lint")` added (code-only, additive).** A new `LINT("lint")` enum value is added to `RunnerStage` **between BUILD and REVIEW**. `runner_executions.stage` is un-CHECKed `text`, so `lint` needs **no Flyway migration and no CHECK** (the BUILD/REVIEW precedent). **Every exhaustive `switch (stage)` consumer gains an explicit LINT arm** (compile-enforced — see Dev Notes §"Fan-out"). A LINT execution is a `runner_executions` row reusing the 3.6 raw-output capture + the 3d-5 per-step step/log view. `RegistryContractTest` + `FlywaySchemaContractTest` stay green **with no stage-value edit** (the stage set auto-derives from `.values()`); add a `RunnerStageLintParsingTest` (clone `RunnerStageBuildParsingTest`) for parse round-trip.

2. **Per-project config `lintCommands` + `lint-stage.enabled` (default DISABLED).** `Project` + `ProjectRuntimeConfigResolver` gain `lintCommands` (`List<String>`, nullable/empty allowed) + `lintStageEnabled` (`boolean`), seeded from `application.yml` via a new `RunnerProperties.LintStage(boolean enabled, List<String> commands, Duration timeout)` nested record (mirror `BuildStage`). **Default disabled.** A project with no lint config (or `lint-stage.enabled=false`, or empty `lintCommands`) **skips LINT entirely** — byte-identical to pre-3h-2 parity. Config threads the full per-project stack (entity, mapper, Create/Update DTOs+commands, `ProjectManagementService`, `ProjectController.createFingerprint` **and** the archive/unarchive status-only paths, `ProjectResponse`, `DefaultProjectSeeder`, OpenAPI regen). Resolution is worker-thread-safe (`Project` is a detached record).

3. **Tail ordering — LINT after BUILD, before REVIEW; severity-classified.** When enabled, LINT runs **after** a successful BUILD (or directly after PR_OUTPUT ingest when BUILD is disabled) and **before** `completeExecutionTailAndAdvance` (i.e. before push + REVIEW). Its aggregated output is parsed into a **severity-classified result**: `critical` (linter `error`) vs `non-critical` (`warning`/`info`). The classified findings are persisted as `lint_findings` jsonb on the LINT rex row (Decision 5).

4. **Critical finding → park in new non-terminal `WAITING_FOR_LINT_APPROVAL` state.** On a **critical** finding the run transitions `EXECUTING → WAITING_FOR_LINT_APPROVAL("WaitingForLintApproval")` — a new **non-terminal** `WorkflowState` (registry + `current_state`/`prior_state`/`resulting_state` CHECK widening via next-free Flyway head V34 + `WorkflowTransitionTable` edges + `TransitionTableCrossProductFoundationContract` mirror + `FlywaySchemaContractTest` `requiredStates` + API-schema placeholder + OpenAPI regen) — **before any LLM REVIEW or push runs.** **Non-critical** findings are attached as advisory and the tail proceeds to REVIEW without parking.

5. **Two new `AllowedAction`s for the gate role.** Add `APPROVE_LINT("approve_lint")` and `REQUEST_LINT_FIX("request_lint_fix")` (enum + frontend placeholder JSON + `WorkflowInspectionService.baseActionMatrix` `case WAITING_FOR_LINT_APPROVAL`; **no OpenAPI change** — `actions` is `type:string`). Surfaced for the **`workflow_owner`** gate role only ([recovery-bar-wrong-allowed-actions-role]: operator gate actions gate on `workflow_owner`); other roles get `VIEW_ONLY` (+ log/usage views). `APPROVE_LINT` dismisses the gate and runs the resumable delivery tail (Decision 4) → proceeds to REVIEW. `REQUEST_LINT_FIX` re-dispatches the EXECUTION runner with the lint findings as a redaction-policed `priorFeedbackReferences` input (`kind:"lint.findings"`), bumps `lint_fix_loop_count`, flips the shared escalation marker once at cap (visibility only — **no** FAILED transition, Decision 3), and transitions back to `EXECUTING`; the re-dispatched run re-runs BUILD→LINT through the existing chain.

6. **Persistence + serving.** The severity-classified findings are persisted (`lint_findings` jsonb on the LINT rex, Decision 5; redaction posture honored — nothing secret in findings) and **served** for the FE lint panel (3h-6) via a new read leg: `GET /api/v1/workflows/{workflowRunId}/lint-findings` → `WorkflowInspectionService.getLintFindings(...)` → `LintFindingsResponse` (mirror the reviewer-verdict read leg), with server-derived `state ∈ {none, advisory, gated}`.

7. **Parity.** A run whose project has LINT disabled, or whose lint produced only non-critical findings, **never** enters `WaitingForLintApproval` and proceeds exactly as pre-3h-2 (BUILD→tail unchanged). A LINT execution records **zero** token/provider usage (backend-side, no LLM — asserted, mirroring 3h-1 AC6).

8. **Tests.** Coverage asserts: LINT stage registry + parse round-trip + the compile `switch` arms; `WaitingForLintApproval` state + the 2 actions drift (registry/CHECK/state-machine/API-schema-placeholder/OpenAPI/pin); **critical finding parks BEFORE REVIEW/push**; `approve_lint` resumes the tail → push + REVIEW; `request_lint_fix` bumps `lint_fix_loop_count` + emits `lint.findings` ref + re-dispatches EXECUTION + re-runs LINT; **non-critical stays advisory (no park)**; **disabled-project parity** (LINT skipped, tail byte-identical); **zero-token** (LINT rex token columns NULL, no provider row); the resumable-tail seam idempotent (replayed `approve_lint` neither double-pushes nor double-enqueues review). `application.*` ≥ 80% line coverage. ArchUnit via **Failsafe** (not Surefire).

## Dev Notes

### Canonical 3h-0 consume-note (from ADR 0032 — fold verbatim)

> **The lint fix-loop + async LINT execution MUST consume the 3h-0 shared replay-safe afterCommit helper (`AfterCommitSideEffectRunner`) — do NOT re-derive `REQUIRES_NEW` + advisory-lock + swallow/log + idempotent re-invoke inline.**

Helper API (`application/workflow/AfterCommitSideEffectRunner.java`):
```java
void runAfterCommit(String label, String contextId, Runnable sideEffect); // Layer A — fire after current tx COMMITS
void runInNewTransaction(String label, String contextId, Runnable work);  // Layer B — REQUIRES_NEW; advisory lock FIRST inside `work`
```
Compose A over B for the async boundary. The helper never calls `transition()` — state mutation stays inside your callback lambda (keeps `only_workflow_transition_service_may_mutate_workflow_state` intact). `BuildStageService` (`:157,191,212,219`) is the working precedent.
[Source: docs/adr/0032-replay-safe-aftercommit-helper.md:38-40; AfterCommitSideEffectRunner.java:81,111]

### The single best implementation template — mirror `BuildStageService` end-to-end

`application/workflow/BuildStageService.java` is the structural twin. Read it in full and clone the shape:

The in-memory `() -> completeExecutionTailAndAdvance(...)` continuation is **gone** when `approve_lint` arrives later via REST. Make the tail re-derivable from `(runId)`:

**Key design decisions (some diverge from the story's literal wording — all documented in ADR 0030 amendment):**
- **Decision 4 (resumable tail) — implemented WITHOUT restructuring 3h-1's `completeExecutionTailAndAdvance`.** The story proposed moving PR-output validate/enrich/`recordCompleted` ahead of the gates and shrinking the tail. That refactor is entangled (validate/enrich depends on the in-memory `pushOutcome` from captureAndPush) and high-risk against just-merged 3h-1 delivery code. Instead: the **pass path** reuses the full existing tail verbatim (`onLintPassTail = completeExecutionTailAndAdvance`); only the **approve_lint path** uses a fresh, re-derivable `RunnerBroker.resumeDeliveryTailFromGate(runId, correlationId)` (resolve the producing PR_OUTPUT rex → idempotent captureAndPush + finalize → `WorkflowOrchestrationService.onLintApproved` → WaitingForReview + reviewer enqueue). Lower blast radius, same ACs. **Trade-off:** the approve_lint resume skips the parsed-dependent PR-output drift/enrich re-check (best-effort, logged) — acceptable since the runner already produced valid output that passed lint after fix.
- **Park finalizes the producing PR_OUTPUT rex** (mirrors 3h-1's `finalizeProducingExecution`) so it is never timeout-reaped as RUNNER_TIMEOUT during a long operator-approval wait.
- **Broker wires the lint gate via optional SETTER injection** (`ObjectProvider<LintStageService>`) rather than a ctor param — avoids fanning out the broker's ~5 test ctors (the `WorkflowInspectionService` optional-setter precedent).
- **Classifier** = exit-code baseline for criticality (any lint command exit ≠ 0 ⇒ critical) + a tolerant per-line severity-keyword enricher for the panel (garbled lines skipped, never a crash; an `error` keyword on a clean exit is downgraded to `warning` so panel severity never contradicts the exit-code gate).
- No new `FailureCategory` (LINT row uses existing `RUNNER_NON_ZERO_EXIT`); no OpenAPI change for the two actions (`actions` is `type:string`); findings persisted as `lint_findings` jsonb on the LINT rex (String + `@JdbcTypeCode(SqlTypes.JSON)`, `RunnerExecutionSnapshot` gained a 27-arg back-compat overload so the 29 snapshot ctor sites are untouched).
