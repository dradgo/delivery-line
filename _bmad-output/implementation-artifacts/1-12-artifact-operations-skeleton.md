# Story 1.12: Artifact Operations Skeleton

Status: done

<!-- Note: Validation is optional. Run `bmad-create-story:validate` for a quality check before `bmad-dev-story`. -->

## Story

As a foundation developer,
I want `ArtifactService`, `ArtifactOperationService`, and `LocalArtifactStore` implementing transactional outbox-style artifact operations with explicit availability gating,
so that artifact payloads can be written outside the database while metadata is transactionally recorded, lineage is preserved across revisions, and only `available` artifacts with verified checksums become approval-eligible.

## Acceptance Criteria

1. **Given** the `application.artifact` package, **Then** `ArtifactService`, `ArtifactOperationService`, and `ArtifactReconciliationService` exist with methods: `createDraft(workflowRunId, artifactType, payloadRef, actorContext)`, `recordOperation(operation)`, `markAvailable(artifactId, checksum, storageRef, actorContext)`, `markFailed(artifactId, failureCategory, reason)`, `newVersion(parentArtifactId, payloadRef, actorContext)`, `isApprovalEligible(artifactId)`. The `actorContext` parameter is a typed `ActorContext` value object carrying `actorIdentity`, `actorType`, and optional `correlationId`; service signatures must not fall back to system literals when no actor is supplied.
2. **Given** the `artifacts` table (from story 1.3), **Then** each row carries: internal numeric `id` (`bigserial` PK), governed `public_id` (`art_` prefix), `workflow_run_id`, `artifact_type` (from registry), `version` (monotonic within the `(workflow_run_id, artifact_type)` lineage owned by this story), `parent_artifact_id` (nullable; lineage root has null and later versions point to the immediately superseded version), `created_at`, `archived_at`, `classification`, `storage_ref`, `checksum_algorithm`, `checksum_value`, `status` (`pending|available|failed|late_or_stale`), `linked_event_id`.
3. **Given** an artifact-operation command handled by `ArtifactOperationService.recordOperation(...)`, **When** it is processed, **Then** the command carries at least `workflowRunId`, `artifactType`, `operationType`, `idempotencyKey`, `payloadRef`, `payloadContent` (the bytes the file adapter is expected to write), `actorIdentity`, `actorType`, `correlationId`, and optional `runnerExecutionId`; and inside one PostgreSQL transaction: (a) the matching `workflow_events` row is appended; (b) the draft/resolved artifact row is inserted or loaded; (c) an `artifact_operations` row is inserted with `operation_type` (`create|update|replace`), `status=pending`, `idempotency_key`, `artifact_id`, `workflow_run_id`, `linked_event_id`; (d) the commit returns control to the caller which performs the file write outside the DB transaction.
4. **Given** a successful file write, **When** `markAvailable(artifactId, checksum, storageRef)` is called, **Then** the artifact status transitions to `available`, the `artifact_operations` row is marked `complete`, and a follow-up `artifact.available` event is appended in one transaction. **When** the artifact is already `available` (for `markAvailable`) or `failed` (for `markFailed`) and no pending operation row exists, the method returns the prior result without re-emitting events (idempotent replay path, D9).
5. **Given** a file-write failure or crash, **When** detected via `ArtifactReconciliationService`, **Then** the skeleton implementation queries `artifact_operations` for stale `pending` rows and flags `failed_orphan`; surfacing through CLI diagnostics belongs to story 1.18 and deeper reconciliation belongs to Epic 4.
6. **Given** approval-eligibility gating, **When** `isApprovalEligible(artifactId)` is called, **Then** it returns true only if `status=available`, `checksum_value` is present, `storage_ref` resolves to a readable payload, and `archived_at IS NULL`.
7. **Given** artifact versioning, **When** `newVersion(lineageMemberArtifactId, payloadRef)` is called, **Then** the service continues only the active lineage for that `(workflow_run_id, artifact_type)` pair and creates the next version on that lineage; the parent payload is never overwritten in place. If the requested operation would require creating a second lineage, healing an ambiguous lineage, or choosing between multiple possible parents after partial failure or replay, the service fails closed with `ARTIFACT_OPERATION_INTENT_CONFLICT`; explicit repair or fork decisions belong to Epic 4 recovery work.
8. **Given** `LocalArtifactStore` in `adapters.files`, **When** writing a payload, **Then** the path resolves to `{DELIVERYLINE_HOME}/artifacts/{workflowRunId}/{artifactId}/v{version}/{filename}` relative to the configured home directory, and `storage_ref` never stores an absolute machine-specific path.
9. **Given** idempotency on artifact operations, **Then** duplicate submissions replay only when the prior outcome can be reconstructed unambiguously for the same workflow run, artifact type, and operation intent. When replay would otherwise create a new artifact, attach to the wrong lineage, or convert a prior failed outcome into an apparent success, the service returns `ARTIFACT_OPERATION_INTENT_CONFLICT` and requires later explicit recovery handling instead of silently guessing.
10. **Given** a late runner result arriving after its associated `runner_executions` row timed out, **When** `recordOperation(...)` is called with a `runnerExecutionId`, **Then** the artifact is recorded as `late_or_stale` and workflow state is not auto-advanced. If no `runnerExecutionId` is present, the normal non-runner artifact flow applies.
11. **Given** the test suite, **Then** it covers interrupted artifact operations, missing payloads, duplicate commands, concurrent version creation, stale callbacks, and orphan-operation reconciliation.

**Scope guardrail:** Story `1.12` owns artifact intent persistence, availability gating, late/stale/orphan detection, and deterministic replay where the outcome is unambiguous. It does **not** own operator-driven artifact lineage repair, explicit fork governance, or deep reconciliation of ambiguous artifact history. Those behaviors are planned follow-up recovery work.

## Dev Notes

This story is the foundation slice for governed artifact persistence and filesystem-backed payload storage. It should create the seam that later runner, approval, recovery, and export stories build on. It should not attempt to deliver the full recovery loop from Epic 4.

**Current repo state**

- `deliveryline-backend/src/main/resources/db/migration/V1__create_workflow_core_tables.sql` already defines `artifacts` and `artifact_operations`, including the status enums and the unique constraint on (`idempotency_key`, `operation_type`, `artifact_id`).
- `artifacts.id` and `artifact_operations.id` are internal numeric primary keys; governed external identifiers live in `public_id` columns (`art_...` and `op_...` respectively).
- `deliveryline-backend/src/main/java/org/dradgo/domain/registry/` already contains `ArtifactType`, `ArtifactStatus`, `ArtifactOperationStatus`, `FailureCategory`, `DataClassification`, and `PersistedRegistryValues`.
- `deliveryline-backend/src/main/java/org/dradgo/application/artifact/` does not exist yet.
- `deliveryline-backend/src/main/java/org/dradgo/adapters/files/` does not exist yet.
- Story 1.11 already introduced the application-owned SPI plus persistence-adapter pattern and added an ArchUnit scaffold that will treat `ArtifactOperationService` as the only allowed caller of `LocalArtifactStore.write(...)`.

**Scope discipline**

- Reuse the schema from story 1.3. Do not add a new migration unless implementation reveals a concrete schema mismatch with the accepted contract.
- Do not build the CLI diagnostic flow in this story. Story 1.18 owns the user-facing baseline recovery/diagnostic command path.
- Do not build deep reconciliation or repair actions here. Epic 4 owns reconcile/repair workflows; this story only establishes the stale-pending detection seam and status transitions needed later.
- Do not let adapters or controllers write files directly. File writes must stay behind `ArtifactOperationService`.
- Do not auto-advance workflow state from a late runner callback. This story records the artifact outcome; recovery decisions stay separate.
- Do not introduce multiple independent lineages of the same `artifact_type` inside one `workflow_run_id` in this story. The active contract is one lineage per `(workflow_run_id, artifact_type)`.

**Implementation guardrails**

- Keep the DB transaction and file I/O separated exactly as the architecture requires: persist artifact intent, operation state, and workflow event first; perform the actual file write only after that transaction returns.
- Application services should talk to application-owned ports only. JPA entities and repositories must stay inside `adapters.persistence`.
- Keep entity/application translation explicit through mapper classes under `adapters.persistence.mapper`.
- `isApprovalEligible(...)` must validate both persisted metadata and real payload readability. A database row with `status=available` but no readable file or checksum is not eligible.
- `storage_ref` should be a logical persisted locator, not an absolute host path. Resolve it against configured `DELIVERYLINE_HOME` inside the file adapter.
- Preserve lineage on version creation. Never overwrite the parent artifact payload in place.
- Duplicate artifact-operation submissions should replay prior governed outcomes wherever possible instead of creating duplicate rows or silently diverging state.
- `ArtifactOperationService` is the only approval-eligible artifact ingress path. `ArtifactService` owns read-side eligibility and lineage logic; `ArtifactReconciliationService` owns stale-pending/orphan detection only.
- `deliveryline.home` is the Spring-bound property for artifact storage root, backed by `DELIVERYLINE_HOME`. `storage_ref` stores only the logical path beneath that root.
