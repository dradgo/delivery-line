# Story 4.1: CLI Operator Inspection — `deliveryline operator status`

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Workflow Owner monitoring system health across many runs,
I want `deliveryline operator status [--state failed|stalled|orphaned|takenover|overridden] [--since duration] [--format text|json] [--limit N]` showing all runs in non-happy states across all workflows with diagnostic summaries,
so that I can spot patterns (e.g., 3 runs stuck on the same runner kind in the last hour) without opening each run individually — extending story 1.15's per-run `status` command into a fleet view.

## Context & Central Reconciliation (READ FIRST)

**This is the FIRST story of Epic 4 (Failure Handling, Recovery & Reconciliation). It is a pure READ-ONLY fleet-view inspection layer.** You add ONE typed read method to the existing `WorkflowInspectionService`, expose it through ONE new Spring Shell command in a NEW `operator` command group, and add ONE new read seam (SPI port + persistence-adapter query) because the fleet row cannot be served from `workflow_runs` alone. **You do NOT touch any write path, any transition, the `RecoveryService`, the queue, or any runner logic.** No REST endpoint in this story (the operator UI queue is story 4.2; audit query REST is 4.3; the recovery REST endpoints are 4.10–4.14).

This story is the CLI analogue of **story 3.19** (`deliveryline workers status`) — read it (`3-19-queue-inspection-and-worker-status-and-queue-size-monitoring.md`) for the house discipline: typed view records nested in `WorkflowInspectionService`, a new SPI read method with a native aggregate, a `@CommandGroup` CLI adapter that only parses + delegates + renders, ANSI gated on TTY, a `schemas/cli/*.v1.schema.json` JSON contract, and an ArchUnit boundary rule. The single biggest new thing here is that **the five `--state` filter tokens are NOT `WorkflowState` values** — see Reconciliation 1.

### HEADLINE RECONCILIATIONS (epic AC text drifts from live code — these bindings win)

1. **THE CENTRAL TRAP — the five `--state` tokens (`failed|stalled|orphaned|takenover|overridden`) are an OPERATOR-STATE vocabulary, NOT the `WorkflowState` registry.** `WorkflowState` (`domain/registry/WorkflowState.java`) has exactly: `Inbox, Planned, Investigating, WaitingForSpecApproval, Executing, WaitingForReview, Split, WaitingForManualExecution, WaitingForDependencies, Completed, Failed, Paused, TakenOver, Reconciled`. There is **no `Stalled`, `Orphaned`, or `Overridden` state** and no `isNonHappy()`/`isTerminal()` helper on the enum. So AC3's phrasing "*`--state` accepts comma-separated values from `WorkflowState` registry*" is **imprecise and does not win** — the tokens are a distinct 5-value operator vocabulary, each mapping to a DERIVED query predicate (Reconciliation 5). Define a plain `OperatorRunState` enum (see Dev Notes) — a `failed,stalled,orphaned,takenover,overridden` vocabulary, NOT a `WorkflowState`. [Source: deliveryline-backend/src/main/java/org/dradgo/domain/registry/WorkflowState.java:5-32]

2. **The typed view records MUST live in `application.workflow` (nested in `WorkflowInspectionService`), NOT in `application.workflow.spi` and NOT in `application.runner`.** The ArchUnit rule `REST_CONTROLLERS_STAY_THIN_…` / the CLI boundary forbid `adapters.cli` (and `adapters.rest`) from depending on `org.dradgo.application.workflow.spi..` or `…application.runner..` or persistence. The CLI command imports `OperatorRunSummary` / `OperatorRunRow` / `OperatorRunFilter` / `OperatorRunState`, so those must be **nested public records/enum inside `WorkflowInspectionService`** (`org.dradgo.application.workflow`), exactly like the existing `WorkflowStatusView` / `RunnerQueueStatus` / `WorkerStatus`. The SPI-layer row/aggregate snapshots (`OperatorRunRowSnapshot`, `OperatorRunAggregate`) stay in `application.workflow.spi` and are NEVER imported by the CLI. [Source: 3-19 Reconciliation 1; ArchitectureRuleCatalog REST/CLI boundary rule]

3. **The fleet "operator run row" cannot be read from `workflow_runs` alone — it is a JOIN/derivation.** `workflow_runs` is deliberately thin: only `runId` (`public_id`), `currentState` (`current_state`), `escalationMarker` (`escalation_marker_set`), `archived_at`, `project_id`, `parent_run_id` are columns on the run. The rest of `OperatorRunRow` comes from other tables: `failureCategory` + `actorIdentity` + `lastTransitionAt` from `workflow_events` (latest / latest-`Failed` event), `oldestEventAt` = `MIN(workflow_events.created_at)` per run, `linkedTicketRef` / `linkedPrRef` from typed `integration_links` rows (`integration_type='linear'` / `='github_pr'`, `archived_at IS NULL AND sync_status<>'superseded'`). You must add a new read seam (SPI port + `adapters.persistence` native/JPQL impl) — the existing `WorkflowRunReadPort.listRuns(state, includeArchived, limit, projectId)` filters by a SINGLE `WorkflowState` ordered by `created_at` only (no multi-state, no failure-category, no time-window, no transition-time ordering). Do NOT try to bend `listRuns`; add a dedicated operator query. [Source: WorkflowRunEntity.java; WorkflowRunRepository.listRunsFiltered; WorkflowEventRepository.findLatestFailureEvent/findLatestByWorkflowRunPublicId; IntegrationLinkService.findActiveLinearTicketLink/findActiveGitHubPrLink]

4. **`oldestEntryAt` is `OffsetDateTime`, not `Instant`.** The epic AC1 types it `Instant?`. The codebase standardizes on `java.time.OffsetDateTime` in every view record / snapshot / port (`Instant` does not appear in `WorkflowInspectionService` at all). Use `OffsetDateTime` and compute age server-side in SQL (`now() − min(...)`) per the `RunnerQueueCounts.oldestQueuedAgeSeconds` precedent — do not read a JVM clock. [Source: WorkflowInspectionService view records; RunnerQueueCounts]

5. **Each `--state` token maps to a DERIVED predicate; the histograms count by the run's ACTUAL `WorkflowState` / `FailureCategory`.** Binding predicate table (a run matches the filter if it satisfies ANY selected token's predicate — the matched set is the UNION, deduped by `runId`):
   | token | predicate |
   |---|---|
   | `failed` | `current_state = 'Failed'` |
   | `orphaned` | `current_state = 'Failed'` **AND** latest `Failed`-transition `failure_category = 'orphan'` (`FailureCategory.ORPHAN` exists) — a diagnostic refinement of `failed` |
   | `takenover` | `current_state = 'TakenOver'` |
   | `stalled` | `current_state IN ('Investigating','Executing','WaitingForManualExecution')` **AND** `lastTransitionAt < now() − stallWindow` (no recent activity) |
   | `overridden` | **PROVISIONAL (OQ-1)** — latest `workflow_events.intervention_marker = true` AND `current_state` is non-terminal (operator manually forced the run's current position). See Open Questions. |
   `byState: Map<WorkflowState,Integer>` counts the matched runs by their **actual** `WorkflowState` (so an orphaned run counts under `Failed`); `byFailureCategory: Map<FailureCategory,Integer>` is populated only when the state filter includes `failed` or `orphaned`. Both histograms + `total` + `oldestEntryAt` reflect the **FULL matching set**, independent of `--limit` (which caps only the `runs[]` rows). [Source: FailureCategory.java:19 ORPHAN; WorkflowEventEntity.intervention_marker]

6. **`--since 1h|24h|7d` is NOT ISO-8601 `Duration.parse`.** `Duration.parse("1h")` throws — it needs `PT1H`. The existing `deliveryline history --since` takes an absolute `OffsetDateTime`, not a relative token, so there is no reusable parser. Add a small relative-duration parser (`(\d+)(m|h|d|w)` → `Duration`) in the service; invalid values → `INVALID_COMMAND_PAYLOAD` with `details{since, supportedFormats}` (Reconciliation 7). [Source: docs/cli/workflow-commands.md `history --since`]

7. **No new `DomainErrorCode`, no new `WorkflowEventType`, no new `AllowedAction`, no Flyway migration (for correctness).** Reads-only. Reuse the existing `INVALID_COMMAND_PAYLOAD` (already thrown by `normalizeFormat`/`unsupportedFormat`) for a bad `--state` token, bad `--since`, bad `--format`, or out-of-range `--limit` (`details` carries the offending value + the allowed set). AC8's "*register in the service's `@Tag` set so allowed-actions can expose `view_operator_status`*" is a **misnomer** — the real mechanism is the `AllowedAction` registry + `getAllowedActions` matrix, and AC8 itself defers `view_operator_status` to "*E5+ role-based access*". In E4's deferred-RBAC posture the command is invocable by any local user, so **do NOT add an `AllowedAction` value** — that would trip the [[new-domainerrorcode-three-sites]]-style registry-drift fan-out for zero E4 benefit. [Source: 3-19 Reconciliation 8; AllowedAction.java; epics.md Story 2.14 AC2]

8. **AC6's "backed by the indexes added in stories 1.3 + 3.6 + 3.17" is partly wrong — 3.6/3.17 indexes are on `runner_executions`, not the tables you query.** Your query rides the story-1.3 (V1) indexes: `idx_workflow_runs_current_state_created_at` (state filter + ordering) and `idx_workflow_events_workflow_run_id_created_at` (per-run latest/oldest/latest-failed event lookup). There is currently **NO index on `workflow_events.failure_category`** and no "runs by last-transition-time" index. **No new migration is required for correctness.** Add a `V34` index ONLY as a contingency if the AC6 1000-run perf test misses the 5s target (see Task 4). If you do add a migration, mind the cross-branch Flyway collision trap ([[flyway-v31-cross-branch-collision]]) — highest on-disk is V33, but sibling in-flight story **3h-2 already claims V34**, so take the next free number (likely **V35**) and confirm against the current branch before authoring. [Source: V1__create_workflow_core_tables.sql indexes; agent DB map]

9. **Non-color signifier = bracketed / UPPERCASE text labels, NOT emoji/Unicode glyphs.** AC4 says "icons + state labels". The repo's established color-independent convention (story 2.3 AC5) is **bracketed text labels** — see `WorkflowCommands.renderProviderUsageWindow` (`"[" + label + ": " + value + "]"`, explicitly commented "*color-independent … never color*") and `DoctorReportRenderer` (`overall: PASS|WARN|FAIL`). There are **no emoji anywhere in the CLI package.** Realize the "icon" as a leading UPPERCASE state token (e.g. `[FAILED]`, `[STALLED]`, `[ORPHANED]`, `[TAKENOVER]`, `[OVERRIDDEN]`) so meaning survives with color stripped. Sanitize every free-form field (`reason`, ids, actor) through the existing `escapeForText` (escapes `\`, CR, LF, TAB) for grep/awk safety. [Source: WorkflowCommandOutputs.escapeForText:401-410; WorkflowCommands.renderProviderUsageWindow:2888-2968]

10. **This is Spring Shell 4.0.2 (the `org.springframework.shell.core.command.annotation` package), and the `operator` group does not exist yet.** Mirror `WorkerCommands` EXACTLY (it is the precedent for a net-new group): a `@Component @CommandGroup(name="operator", description="…", prefix="deliveryline")` class with a `@Command(name="status")` method returning `String`, `exitStatusExceptionMapper = WorkflowCliExitStatusExceptionMapper.BEAN_NAME`. The `prefix` supplies the leading token and the group `name` segments the path → registered as **`deliveryline operator status`**. Pin the exact registered name with a `*CommandRegistrationIT` (both `WorkerCommands` and `WorkflowCommands` expose a `status` method under the same prefix, so verify Shell 4.0.2 composes the group name into the path as expected). [Source: WorkerCommands.java; WorkflowCliCommandRegistrationIT.java; root pom.xml spring-shell.version 4.0.2]

## Dev Notes

### Relevant architecture patterns and constraints

- **The read seam.** `WorkflowInspectionService` (`org.dradgo.application.workflow`, `@Service`) is the single application read service; it never mutates, and every public method is `@Transactional(readOnly = true)`. It composes application-owned SPI ports (interfaces in `…workflow.spi` / `…runner.spi`; impls in `adapters.persistence`) returning intentionally-lossy snapshot records — **no JPA/EntityManager/native query in the service itself**. Mirror `getStatus` (WorkflowInspectionService.java:1337) for structure and `getRunnerQueueStatus` (:776) for a native-aggregate read + nested view records; mirror `listRuns` (:1506) for the clamp-limit multi-run convention (`MAX_LIST_PAGE_SIZE`, `Math.min(Math.max(limit,1), …)`). Your operator caps are distinct: default 100, max 500.
- **View-record conventions.** Nested `public record`s inside `WorkflowInspectionService`. Nullability = plain nullable reference fields documented in Javadoc (NOT `Optional`, NOT `@Nullable`); primitives where always present; enums stored either as the `WorkflowState` enum (like `WorkflowStatusView.currentState`) or the `.value()` wire string — pick `WorkflowState` for `OperatorRunRow.currentState` + the `byState` key so callers can format either way. Timestamps are `OffsetDateTime`. Numeric "not reported" is `null`, never coalesced to 0. Append new fields at the END of a record + add a convenience constructor if you ever widen one.
- **Count aggregation.** No existing `Map<Enum,Integer>` surface — the precedent is a flat scalar `long`-FILTER record (`RunnerQueueCounts`, one native SELECT). For 4.1 the epic explicitly asks for two histograms; build `EnumMap<WorkflowState,Integer>` / `EnumMap<FailureCategory,Integer>` in the SERVICE from `(enum_string, count)` rows returned by the port (the idiomatic in-repo map is `EnumMap`, used in `WorkflowTransitionTable`/`RunnerProperties`). Histograms cover the FULL matching set; `runs[]` is the `--limit`-capped page — two separate port calls.
- **The `--state` vocabulary + predicates (Reconciliation 1/5).** `OperatorRunState` is a plain application enum, not a `domain.registry.RegistryValue` — so it needs NO drift test / placeholder-manifest / `RegistryContractTest` entry (avoid the [[new-domainerrorcode-three-sites]]-style fan-out). Predicates per Reconciliation 5; `failed`⊇`orphaned` (orphaned is `failed` + `failure_category='orphan'`); `stalled` is the only purely time-derived one (active state + stale `lastTransitionAt`); `overridden` is provisional (OQ-1).
- **Data model (Reconciliation 3).** `workflow_runs` columns available: `public_id`, `current_state`, `escalation_marker_set`, `archived_at`, `project_id`, `parent_run_id`. Everything else joins: `workflow_events` (`event_type`, `resulting_state`, `actor_identity`, `actor_type`, `failure_category` (nullable, only on the `Failed` transition), `intervention_marker`, `created_at`) via `idx_workflow_events_workflow_run_id_created_at`; `integration_links` (`integration_type ∈ {linear, github_pr}`, `external_ref`, `archived_at`, `sync_status`) via `idx_integration_links_run_id_type_created_at`. A run can carry BOTH a `linear` and a `github_pr` link — resolve them TYPED, not "first active link" ([[integration-link-adapter-tx-and-supersede]]).
- **CLI (Spring Shell 4.0.2).** Imports from `org.springframework.shell.core.command.annotation` (`@Command`, `@CommandGroup`, `@Argument`, `@Option`). Command methods return `String`. `WorkerCommands` is the exact precedent for a NEW group (`@CommandGroup(name="operator", prefix="deliveryline")`). ANSI via `ESC=Character.toString((char)27)` constants in `WorkflowCommandOutputs` — no Spring `AnsiOutput`; gate on `!json && interactivity.isInteractive()` (`CliInteractivityDetector` = `System.console()!=null`). JSON via `writeJson` (`ObjectMapper` with `WRITE_DATES_AS_TIMESTAMPS` disabled). The renderer must NOT be a `*Commands`-named class (ArchUnit forces `@CommandGroup` on those) — put render methods on `WorkflowCommandOutputs`.
- **Completion log (AC7).** `WorkflowCommands` emits `workflow command completed correlationId=… commandName=… workflowRunId=… outcome=success|failure:CODE durationMs=…` via `emitSuccess`/`emitFailure` after a `pushCorrelation` scope. There is no runId here — emit `commandName='operator status'`, the resolved filter (`states`, `since`, `limit`), and `resultCount=total`. Redact/sanitize any user-supplied value with `MdcKeys.sanitizeForLog` before logging (CR/LF injection guard).
- **No REST, no write, no `RecoveryService`.** The `RECOVERY_SERVICE_IS_SCOPE_PROTECTED` ArchUnit rule is untouched by this story (4.1 adds nothing to `RecoveryService`; that lift is story 4.28). No new `WorkflowState`/`WorkflowEventType`/`DomainErrorCode`/`AllowedAction`/Flyway (Reconciliation 7/8).

### Logging Requirements (project-wide standard)

Every story is expected to leave the touched services observable enough to debug a production incident without re-deploying. This is enforced via the "Logging instrumentation" task above.

- **Framework:** SLF4J + Logback (Spring Boot default). No `System.out`, no `printStackTrace()`. (CLI stdout is the command's returned `String`, not a logger.)
- **Where to log (minimum surface for this story):**
  - `getOperatorRunSummary` → `INFO` on entry with the resolved filter (`states`, `sinceCutoff`, `limit`) + `INFO` on success with `total`/`returnedRows`/`durationMs`; `DEBUG` for the two port-query calls (hot path — operator may poll).
  - Bad `--state`/`--since`/`--limit` → `WARN` at the `INVALID_COMMAND_PAYLOAD` raise site with the offending value (sanitized).
  - CLI `operator status` → the structured completion log line (AC7) at `INFO` (success) / `WARN` or `INFO` (typed failure) — mirror `WorkflowCommands.status`.
- **Required context keys** (MDC or params): `correlationId`, plus the filter summary; per-row ids only at `DEBUG` if a row is individually logged.
- **Forbidden in log output:** payload bytes, secrets/tokens, raw PII; sanitize user-supplied `--state`/`--since` before logging.
- **Test contract:** pin the completion-log line + the `WARN`-on-invalid-filter line with `OutputCaptureExtension`.
