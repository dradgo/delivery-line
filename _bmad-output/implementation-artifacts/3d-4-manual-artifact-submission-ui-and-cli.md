# Story 3d.4: Manual-Artifact Submission (UI + CLI) into the Same Validation/Review Pipeline

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **⚠️ READ FIRST — this is the submission half of the manual-execution feature and the largest 3d story alongside 3d-2. It is NOT a thin REST wrapper.** Story 3d-3 built the **dispatch-side park**: a `manual`-kind step writes its redacted runner-contracts **input bundle**, records an `awaiting_manual` `runner_executions` row, appends `manual.executionRequested`, and parks the run in `WaitingForManualExecution` — **no container, no queue, no workspace materialized**. 3d-4 builds the **operator submission path**: (1) a REST `GET` + CLI to retrieve the parked bundle, (2) a governed `POST /api/v1/workflows/{workflowRunId}/manual-artifact` (+ CLI) that runs the **same runner-contracts output validation** an automated runner's output would, finalizes the parked `awaiting_manual` row, appends `manual.artifactSubmitted`, and transitions the run **out** of `WaitingForManualExecution` into the stage-appropriate post-step state (`WaitingForReview` / `WaitingForSpecApproval`), and (3) the UI **Manual Execution Surface**.
>
> **Five things the live codebase forces you to reconcile (read all five before coding — full detail in Dev Notes R1–R10):**
>
> 1. **`awaiting_manual → completed` is ILLEGAL today.** `RunnerExecutionStateMachine.ALLOWED` (deliveryline-backend/src/main/java/org/dradgo/application/runner/RunnerExecutionStateMachine.java:74-76) maps `AWAITING_MANUAL → {CANCELLED_FOR_TAKEOVER}` **only**. 3d-3 left it that way deliberately (it only needed the takeover edge). 3d-4 **must widen** the rule to `AWAITING_MANUAL → {COMPLETED, CANCELLED_FOR_TAKEOVER}` so a submitted manual artifact can finalize the row via `executionService.recordCompleted(...)`. This is an **in-code map change, NOT a Flyway migration** — the DB `ck_runner_executions_status` CHECK (V20) already lists both `awaiting_manual` and `completed`, and `completed` is already terminal/`completed_at`-bearing. (R1.)
> 2. **You CANNOT blindly reuse `RunnerBroker.onResult`.** Two collisions (R2): (a) `onResult`'s invalid-validation branch (`handleFailedValidation → recordFailed → driveWorkflowFailed`) drives the **run to Failed** — but AC5 requires an invalid manual artifact to leave the run **in `WaitingForManualExecution`, resubmittable, with no state change**. (b) `onResult`'s success path runs **workspace-coupled** post-processing — the story-3.5 post-execution secret scan (`runnerSecretScanService.scanWorkspace`, RunnerBroker.java:1585-1588) and, for the EXECUTION pr-output sub-stage, `RepositoryWorkspaceService.captureAndPush` — both of which assume a materialized workspace. **A manual park launches no container and materializes no workspace**, so those steps would fail or misbehave. The submission path must reuse the **validation + artifact-ingest + review-loop entry** but **skip the workspace-coupled steps**.
> 3. **Bundle retrieval is artifact-keyed today; a parked run has no artifact yet.** The existing read (`WorkflowInspectionService.getContextBundleForArtifact(artifactId)`, WorkflowInspectionService.java:1337) resolves the bundle **from an artifact** → its producing runner-execution. A parked run has produced **no artifact**. The `GET .../manual-bundle` path needs a **new run-scoped read**: resolve the run's `awaiting_manual` `runner_executions` row → `runnerScratchStore.tryReadContextBundle(runnerExecutionId)`. The persisted bytes are **already redacted** (`composeAndWriteManualBundle` wrote `composed.bundle().redactedPayload()`, RunnerBroker.java:1112), so the GET just serves them. (R3.)
> 4. **`ACTION_NOT_ALLOWED` is NOT a DomainErrorCode in this codebase.** The epic AC6 lists it, but `grep` finds it only in tests/epics — there is no such enum constant. Allowed-action "wrong state" is expressed via **state-specific codes** (the `RETRY_NOT_APPLICABLE` precedent, RecoveryService.java:352). So the new `MANUAL_EXECUTION_NOT_APPLICABLE` plays that role (run not in `WaitingForManualExecution`). **Do NOT add a generic `ACTION_NOT_ALLOWED`** — it would be an unused three-sites fan-out (R5). RBAC is audit-only (WorkflowController javadoc, WorkflowController.java:68) — the endpoint never returns 401/403; state-applicability + allowed-action *advertisement* is the gate.
> 5. **The plumbing 3d-4 consumes already exists from 3d-3 — don't re-add it.** `OBTAIN_MANUAL_BUNDLE` + `SUBMIT_MANUAL_ARTIFACT` allowed actions are registered + surfaced in the `WAITING_FOR_MANUAL_EXECUTION` matrix case (workflow_owner); the OUT transition edges (`WaitingForManualExecution → {WaitingForReview, WaitingForSpecApproval, Failed, TakenOver, Reconciled}`) are in `WorkflowTransitionTable`; `RunnerExecutionEventPersistenceAdapter.ALLOWED_EVENT_TYPES` already lists `MANUAL_EXECUTION_REQUESTED`. 3d-4 **adds** only `MANUAL_ARTIFACT_SUBMITTED` to that allow-list + the two fixture sites.

## Story

As an operator,
I want to download the emitted context bundle, run the agent myself, and submit the resulting artifact,
so that a manually-produced artifact re-enters the same validation and review pipeline as an automated runner's output — without a separate, weaker validation path.

## Acceptance Criteria

> Reconciled against the live codebase (Dev Notes R1–R10). Where the epic wording assumes infrastructure that does not exist (`ACTION_NOT_ALLOWED` code; a single reusable `onResult` that works from `WaitingForManualExecution`; an artifact-keyed bundle read), the reconciled wording below is authoritative.

1. **Given** a run in `WaitingForManualExecution`, **Then** `GET /api/v1/workflows/{workflowRunId}/manual-bundle` (+ a CLI command) returns the **already-redacted** runner-contracts input bundle for the parked step — resolved **run-scoped** by finding the run's `awaiting_manual` `runner_executions` row and reading `RunnerScratchStore.tryReadContextBundle(runnerExecutionId)`. The endpoint is gated by run-state applicability (run not parked ⇒ `MANUAL_EXECUTION_NOT_APPLICABLE`), is read-only/idempotent (**no `Idempotency-Key`**), and surfaces a typed `bundleNotPersisted`/unavailable state (scratch is not durable) rather than a 500 when the file has been evicted. The action is advertised by the `OBTAIN_MANUAL_BUNDLE` allowed action (registered in 3d-3).

2. **Given** the governed submission endpoint `POST /api/v1/workflows/{workflowRunId}/manual-artifact` (+ CLI, story 1.7 parity), **Then** it accepts the operator-produced artifact (a runner-result-shaped payload) and runs the **same runner-contracts output validation** an automated runner's output would — the **same `ContractValidator.validate(ValidationTarget.RUNNER_RESULT, payloadBytes, validationContext)`** call the broker uses in `onResult` (no validation bypass, no parallel weaker schema), and the same stage→artifact-type rule (`allowedArtifactTypesForStage`: INVESTIGATION⇒`spec`, EXECUTION⇒`implementationPlan`/`prOutput`).

3. **Given** mandatory `Idempotency-Key` + optional `X-Actor-Identity` headers (stories 1.9 / 2.13), **Then** the submission follows the standard controller conventions exactly as `accept-implementation`/`reject-implementation` do (missing/blank key ⇒ `MISSING_IDEMPOTENCY_KEY`; multi-valued header rejection); a replay with the **same key + same fingerprint** replays the prior result, a **different fingerprint** raises `IDEMPOTENCY_KEY_CONFLICT`. The idempotency fingerprint includes the submitted artifact bytes.

4. **Given** a **valid** submission, **Then in one transaction**: the parked `awaiting_manual` `runner_executions` row is finalized to terminal `completed` (`recordCompleted`, requiring the R1 state-machine widening), the operator artifact is ingested + marked available via the **same** `ArtifactOperationService.recordOperation` + availability-promotion path the broker uses, a `manual.artifactSubmitted` event is appended **with the operator identity**, and the run transitions **out** of `WaitingForManualExecution` into the **stage-appropriate** post-step state — INVESTIGATION ⇒ `WaitingForSpecApproval`, EXECUTION ⇒ `WaitingForReview` — reading the stage from the parked row. The post-step transition reuses the existing orchestration auto-advance callbacks (`onSpecStageSucceeded` / `onPlanStageSucceeded` / `onPrOutputStageSucceeded`), which are **legal from `WaitingForManualExecution`** because 3d-3 declared the OUT edges.

5. **Given** an **invalid** artifact (fails output-contract validation, or wrong artifact type for the stage), **Then** a typed Problem Details (`RUNNER_OUTPUT_VALIDATION_FAILED`, or `RUNNER_ARTIFACT_TYPE_MISMATCH`) is returned and the run **stays in `WaitingForManualExecution`** (resubmittable): **no** `runner_executions` finalization, **no** artifact ingest, **no** transition, **no** event — validation happens **before** any state change, so a failed submission is a pure no-op on persisted state. (This is the explicit divergence from `onResult`, whose failed-validation branch drives the run to Failed — R2.)

6. **Given** Problem Details (story 1.8), **Then** typed errors cover at least: `MANUAL_EXECUTION_NOT_APPLICABLE` (**new**, run not in `WaitingForManualExecution`; the wrong-state gate — plays the epic's `ACTION_NOT_ALLOWED` role), `RUNNER_OUTPUT_VALIDATION_FAILED` (existing), `RUNNER_ARTIFACT_TYPE_MISMATCH` (existing), `IDEMPOTENCY_KEY_CONFLICT` + `MISSING_IDEMPOTENCY_KEY` (existing), `RUN_NOT_FOUND` (existing). Contract tests assert `code`+`status`, never human text. **Only one new code** (`MANUAL_EXECUTION_NOT_APPLICABLE`) is added (three-sites: enum + `ProblemDetailsCatalog` + `registry-api-schema-placeholders.json`); **do NOT** add `ACTION_NOT_ALLOWED` (R5).

7. **Given** the UI **Manual Execution Surface**, **Then** for a parked run it renders within the run-detail view (`routes/workflows/$workflowRunId/index.tsx`), offers download **and** copy of the bundle + a submit affordance (file upload or paste), shows validation/Problem-Details errors inline, announces submit start/result via a live region, is keyboard-operable with explicit labels (WCAG 2.1 AA; axe **zero** `wcag2aa` violations), and is gated on the backend-reported `allowedActions` (`obtain_manual_bundle` / `submit_manual_artifact`) via `useAllowedActions` — **never** on a client-derived role (the `no-role-based-action-gating` eslint rule).

8. **Given** OpenAPI + drift check (story 1.21), **Then** the new `GET`/`POST` endpoints + request/response DTOs appear in the regenerated `openapi.json` snapshot **and** the frontend client is regenerated (`npm run generate-api` → `schema.d.ts`) in the **same** change — otherwise `check:api` cascades the format/foundation/runner-contract gates red ([[openapi-regen-frontend-client-drift-cascade]]).

9. **Given** tests, **Then** coverage asserts: happy-path submission transitions out + appends `manual.artifactSubmitted` (operator identity) + finalizes the `awaiting_manual` row to `completed` (all one tx); invalid artifact rejected with the run **unchanged + resubmittable**; idempotent replay (same fingerprint) + conflict (different fingerprint); CLI/REST equivalence for both bundle-get and submit; the downstream review loop (`WaitingForReview` accept/reject) sees the manual artifact **identically** to an automated one (an end-to-end park→submit→review IT); bundle retrieval serves the persisted redacted bytes (and degrades when evicted); `MANUAL_EXECUTION_NOT_APPLICABLE` for a non-parked run; the `AWAITING_MANUAL → COMPLETED` state-machine edge is legal and `AWAITING_MANUAL → COMPLETED` was illegal before; new/changed `application.*` code meets the standing **≥80% line-coverage** floor; axe a11y on the Manual Execution Surface.

### R1 — `awaiting_manual → completed` is the net-new state-machine edge
3d-3 added `AWAITING_MANUAL` to `RunnerExecutionStateMachine` with **only** the `→ CANCELLED_FOR_TAKEOVER` edge (it parked rows; takeover cancels them). 3d-4 is the first code that **finalizes** a parked row, so it must add `AWAITING_MANUAL → COMPLETED`. The DB side is already satisfied: `ck_runner_executions_status` (V20) lists `awaiting_manual` and `completed`, and `completed` is the terminal status `markCompleted` stamps `completed_at` on (kept inside `ck_runner_executions_completed_correlation`). So this is a one-line `EnumSet` change + a guard test — **no Flyway**. Do **not** add `RUNNING`/`PENDING` targets (a manual row never runs in a container) and do **not** add `FAILED` (an invalid submission stays resubmittable — AC5 — and there is no manual crash signal).

### R2 — Reuse the validation + ingest *core*, not `onResult` wholesale (the architectural crux)
`onResult` is the battle-tested automated path, but it is wrong to call directly for a manual submission for two independent reasons:
- **Failure semantics diverge.** `onResult` treats an invalid result as a **terminal failure** of the run (`handleFailedValidation → driveWorkflowFailed`). AC5 demands the opposite: an invalid manual artifact leaves the run **parked + resubmittable**. So validation must run **before** any state mutation, and a failure must be a pure no-op + typed Problem Details.
- **Workspace coupling.** A manual park launches **no container** and prepares **no workspace** (3d-3 only composed + wrote the bundle). `onResult`'s success path runs the post-execution **secret scan** over the workspace (RunnerBroker.java:1585-1588) and, for EXECUTION pr-output, **`captureAndPush`** (git) — both meaningless/failing without a workspace.

The clean design: `ManualArtifactSubmissionService` owns the **applicability + validation + idempotency** gate (no state change on failure), then delegates the **ingest + complete + advance** to a new `RunnerBroker.ingestManualResult` that reuses the same `artifactOperationService` / `executionService.recordCompleted` / orchestration-auto-advance collaborators as `handleSuccess` but **skips** the workspace-coupled steps. The post-step transition is **free** — `onSpecStageSucceeded`/`onPlanStageSucceeded`/`onPrOutputStageSucceeded` transition into `WaitingForSpecApproval`/`WaitingForReview`, and 3d-3 already made those edges legal **from** `WaitingForManualExecution`. Keep the ingest logic in the broker (one place), not duplicated in the service.

### R3 — Run-scoped bundle read (not artifact-scoped)
`getContextBundleForArtifact(artifactId)` walks artifact → producing runner-execution → bundle. A parked run has produced no artifact. `getManualBundle(workflowRunId)` instead resolves the run's **active `awaiting_manual` row** (there is exactly one parked execution per parked run) and reads its persisted, **already-redacted** bundle bytes from the scratch store. Mirror the existing method's `available`/`unavailable(reason)` discipline (scratch is not durable — return a typed `bundleNotPersisted` state, never a 500). The persisted bundle is the authoritative redaction (ADR 0025 posture, same as 3d-5's finished-log read) — never recompose.

### R4 — `manual.artifactSubmitted` is the only new event type; one new error code
3d-3 already added `MANUAL_EXECUTION_REQUESTED` (+ both fixtures + the event-persistence allow-list). 3d-4 adds the **submission** twin `MANUAL_ARTIFACT_SUBMITTED`: enum + the two fixture sites + (if appended through `RunnerExecutionEventPersistenceAdapter`) its `ALLOWED_EVENT_TYPES`. Carry **operator** identity (not SYSTEM) — AC4. OpenAPI stays byte-identical for the event (free-string `eventType`); the **only** `openapi.json` change is Task 6's endpoints/DTOs. One new `DomainErrorCode` (`MANUAL_EXECUTION_NOT_APPLICABLE`) — everything else (`RUN_NOT_FOUND`, `IDEMPOTENCY_KEY_CONFLICT`, `MISSING_IDEMPOTENCY_KEY`, `RUNNER_OUTPUT_VALIDATION_FAILED`, `RUNNER_ARTIFACT_TYPE_MISMATCH`) already exists in `DomainErrorCode` + `ProblemDetailsCatalog`.

### R5 — Allowed-action gating is state-applicability, not RBAC
The controller never returns 401/403 (RBAC is audit-only, WorkflowController.java:68). The "gate" is: (a) the action matrix already advertises `OBTAIN_MANUAL_BUNDLE`/`SUBMIT_MANUAL_ARTIFACT` for a `WaitingForManualExecution` run to `workflow_owner` (3d-3, `WorkflowInspectionService.computeActionMatrix`); (b) the endpoints enforce **state applicability** — a run not in `WaitingForManualExecution` (or with no parked `awaiting_manual` row) ⇒ `MANUAL_EXECUTION_NOT_APPLICABLE`. The frontend gates the surface on the advertised `allowedActions` strings (never a client role).

### R6 — Idempotency, one transaction, fingerprint includes the payload
Follow `accept-implementation`/`reject-implementation` exactly: required `Idempotency-Key`, optional `X-Actor-Identity` (property fallback via `LocalActorIdentityResolver`), `X-Correlation-Id` from the filter. The fingerprint must include the **artifact bytes** so two different artifacts under one key correctly conflict (`IDEMPOTENCY_KEY_CONFLICT`) while an honest retry replays. The finalize + ingest + event + transition execute in **one** `@Transactional` boundary so a mid-sequence failure leaves the run parked + unchanged (AC4/AC5).

### R7 — Downstream review must see the manual artifact identically (the whole point)
The manual artifact is ingested through the **same** `ArtifactOperationService.recordOperation` + availability-promotion the broker uses, so the `WaitingForReview` implementation-review (accept/reject, stories 3.20–3.24) and the spec-approval flow read it with no special-casing. The AC9 e2e IT proves park → submit → (WaitingForReview) → accept/reject works exactly as an automated run does. Do **not** introduce a "manual artifact" flavor anywhere downstream.

### R8 — Manual pr-output is the thorniest stage (Open Decision #2)
For INVESTIGATION (spec) and EXECUTION/implementationPlan, the artifact is text — straightforward. For EXECUTION/**pr-output**, the automated path runs `captureAndPush` to create the real branch/commit/PR. A manual operator presumably pushed the PR themselves. Default scope: validate the operator-reported `branch`/`commitSha`/`prReference` **format** (story 2.24 patterns) and ingest, **without** re-running `captureAndPush` (no workspace). Surface this clearly; if the pilot needs first-class manual pr-output with linkage validation against `integration_links`, that is a follow-up. Keep spec + implementationPlan unconditionally supported.

### R9 — No queue, no worker, no Docker — submission is synchronous in the caller tx
Unlike the automated path (enqueue → worker → async `onResult`), the manual submission runs **inline** in the REST/CLI request transaction (exactly like 3d-3's park ran inline in the submit/approve tx). There is no worker, no `dispatchTransactionTemplate` gymnastics, no lease. This is simpler — the row insert/finalize + event + transition just join the request tx.

### R10 — OpenAPI + frontend client regen in the same change
Task 6 adds real new paths/DTOs ⇒ `openapi.json` changes ⇒ you **must** `npm run generate-api` and commit `schema.d.ts`, or `check:api` cascades `format-static-checks` / `foundation-gate` / `runner-contract-real` red ([[openapi-regen-frontend-client-drift-cascade]], hit on 3c-8).

### Open Decisions surfaced for review (do not block implementation; defaults chosen)

1. **Ingest-reuse shape** — default: a **parallel slim** `RunnerBroker.ingestManualResult` reusing the same injected collaborators (NOT a refactor of `handleSuccess`), to keep the fragile container-path invariants untouched.
