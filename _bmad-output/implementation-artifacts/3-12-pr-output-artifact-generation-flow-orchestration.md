# Story 3.12: PR/Output Artifact Generation Flow (Orchestration)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Developer reviewing implementation output,
I want the workflow orchestration wired for the **pr-output sub-stage**: an approved implementation-plan → repository workspace prepared (idempotent reuse, story 3.9) → EXECUTION runner dispatched against the pr-output context bundle (story 3.10) → the runner-edited repo committed/pushed and a PR opened/updated (story 3.9 `captureAndPush`) → the `prOutput` artifact ingested and **enriched with the actual branch / commit / PR refs** → workflow auto-advanced to `WaitingForReview`,
so that FR15 (developer reviews implementation output — PR side), FR20 (relationship between implementation output, PR linkage, and review outcome), and FR40 (link governed implementation output to GitHub / PR refs) are wired end-to-end — **promoting the dormant `ExecutionSubStage.PR_OUTPUT` seam (the absorbing-state `else` branch story 3.11 left in `RunnerBroker.onResult`) into a live, directly-tested flow.**

## Context & Central Reconciliation (READ FIRST)

**This story is the PR-OUTPUT twin of story 3.11 (`dispatchPlanGeneration`).** 3.11 built the IMPLEMENTATION_PLAN sub-stage orchestration; 3.12 mirrors it for the PR_OUTPUT sub-stage and closes the four items 3.11 explicitly deferred to "story 3.12". **Read `3-11-implementation-plan-artifact-generation-flow-orchestration.md` first** — its `WorkflowOrchestrationService` plan methods, the broker `else`-branch (`RunnerBroker.java:1031-1038`), the lazy-`Supplier` cycle break, the stage→artifact-type guard, the `auto-dispatch` master switch, the in-flight guard, the benign-replay-vs-anomaly classification, the `PlanStage` config record, and the test shape are ALL reused. 3.12 adds the *pr-output twins* of those plan-stage methods plus the *artifact-enrichment + ref-validation* that the pr side uniquely needs.

**THE STRUCTURAL FACTS THAT SHAPE THIS STORY (each verified against current code):**

1. **The pr-output dispatch composer is already built — but it has NO production originator.** The downstream pieces exist and are unit/IT-tested:
   - `ContextBundleService.deriveExecutionSubStage(runId)` returns `PR_OUTPUT` **iff an approved implementation-plan artifact exists** for the run, else `IMPLEMENTATION_PLAN` (`ContextBundleService.java:421-429`). It queries `approvalReadPort.findLatestApprovedForArtifactLineage(runId, IMPLEMENTATION_PLAN.value())`.
   - `RunnerBroker.dispatch(runId, EXECUTION, key, actor)` resolves `repositoryRef`, clones+summarizes, derives the sub-stage, and composes the **pr-output** bundle (story 3.10 — the bundle additionally carries `approvedImplementationPlanReference`).
   - `RepositoryWorkspaceService.captureAndPush(runnerExecutionId)` already commits, pushes, and **creates/updates the GitHub PR** (story 3.9, calling `GitHubAdapter.createPullRequest`/`updatePullRequest`), returning `Optional<RepositoryPushOutcome>` = `(commitSha, branchRef, prRef, committed)` (`RepositoryWorkspaceService.java:246, 677-679`). **It is invoked inside `RunnerBroker.onResult` (`:944`) but its return value is currently DISCARDED.**
   - The `happy-pr-output.json` mock runner scenario already exists (`src/main/resources/runner-scenarios/happy-pr-output.json`) — so the entire approved-plan→dispatch→pr-output→`WaitingForReview` loop is testable WITHOUT Docker, a real repo, or real GitHub.
   - The stage→artifact-type guard already admits `EXECUTION → {implementationPlan, prOutput}` (`RunnerBroker.java:1048-1054`).
   - The transition table already admits `Executing → WaitingForReview` and `Executing → Failed` — **no transition-table change is needed** (`WorkflowTransitionTable.java:68-75`).
   - **What is missing:** (a) the live PR_OUTPUT auto-advance (the broker `else` branch at `:1031-1038` ingests + completes but drives NO transition — story 3.11's deferred "absorbing-state" item); (b) the orchestration entry point (`dispatchImplementation`/`retryImplementation`); (c) the artifact-enrichment + ref-validation that the pr side needs; (d) a per-sub-stage runner kind.

2. **THE TRIGGER (plan approval / `acceptImplementation`) DOES NOT EXIST — it is story 3.20 (backlog).** `ApprovalService` exposes only `approveSpec`/`rejectSpec` (`ApprovalService.java:140, 308`); there is NO `acceptImplementation`/`approveImplementation`/`approvePlan`. Because `deriveExecutionSubStage` returns `PR_OUTPUT` ONLY when an approved implementation-plan exists, and nothing in production approves a plan, **the PR_OUTPUT sub-stage has no production caller path today.** This is the *same wall* 3.11 hit with `markAvailable` and 3.10 hit with the dormant EXECUTION seam — and it is resolved the *same way*: **build the orchestration + broker delegation + config, prove it via a DIRECTLY-DRIVEN integration test** (seed an approved plan so `deriveExecutionSubStage→PR_OUTPUT`, then invoke `dispatchImplementation` directly), and **DEFER the live plan-approval trigger to story 3.20** (which will add `acceptImplementation` and call `dispatchImplementation`, exactly as `approveSpec` calls `dispatchPlanGeneration`). See Decision D1 / OQ-1.

3. **`markAvailable` STILL has no production caller (the 3a-1/3.10/3.11 carryover, OQ-2).** Epic AC3/AC5 say the prOutput artifact becomes `available` then state advances. But `ArtifactOperationService.markAvailable` has ZERO production callers ([[markavailable-has-no-production-caller]]). 3.12 mirrors the established precedent: fire `onPrOutputStageSucceeded` on successful artifact INGEST; the prOutput artifact stays `pending`; the `Executing → WaitingForReview` transition fires anyway. Do **NOT** take on `markAvailable` plumbing here — same boundary 3a-1 / 3.10 / 3.11 drew.

## Acceptance Criteria

> Criteria are the epic's verbatim ACs (`epic-03-agent-execution.md` §"Story 3.12", lines 236–255) with **binding clarifications** in **bold parentheticals** where the epic wording predates the live code or references not-yet-built upstream pieces (3.15 PR-linkage, 3.17 queue, 3.20 plan-approval trigger). Per Decision D1, 3.12 delivers the pr-output orchestration seam + artifact enrichment + ref-validation as a directly-tested flow; the live trigger and the `integration_links` linkage are deferred to their owning stories.

1. **Given** `WorkflowOrchestrationService.dispatchImplementation(workflowRunId)` in `application.workflow`, **When** invoked, **Then** it: (a) confirms the run is in `Executing` for logging then dispatches **without re-transitioning** (mirror `dispatchPlanInternal`'s no-transition discipline, Trap T1), (b) builds a deterministic idempotency key (Decision D2), (c) calls `RunnerBroker.dispatch(workflowRunId, RunnerStage.EXECUTION, key, systemActor(correlationId))` — which (already, story 3.10) resolves the repo, calls `prepareWorkspace(...)` (idempotent branch reuse), derives `ExecutionSubStage.PR_OUTPUT` (because an approved plan now exists), composes the pr-output bundle, and dispatches the runner kind resolved for the implementation stage (AC1d `deliveryline.runner.implementation-stage.kind`). **(AC1's separate `RepositoryWorkspaceService`/`ContextBundleService` calls are ALREADY composed inside `RunnerBroker.dispatch` for EXECUTION — orchestration calls the broker ONCE, never those services directly, preserving the ArchUnit boundary. The epic's "triggered by plan approval (story 3.17/3.20)" trigger is DEFERRED — story 3.20 will add `acceptImplementation` and call this method, exactly as `approveSpec` calls `dispatchPlanGeneration`. For 3.12 the method is reached only by the directly-driven IT + the recovery/retry baseline, OQ-1.)**

2. **Given** the runner exits successfully having edited files in `/workspace/repo`, **Then** `RepositoryWorkspaceService.captureAndPush(runnerExecutionId)` (story 3.9) stages, commits, pushes, and creates/updates the GitHub PR; the returned `RepositoryPushOutcome` (`commitSha` + `branchRef` + `prRef`) is **captured by the broker** (today its return at `RunnerBroker.java:944` is discarded) and threaded into the pr-output success path. **(captureAndPush is ALREADY invoked in `onResult`; 3.12's change is to STOP discarding its `Optional<RepositoryPushOutcome>` so AC3 enrichment + AC3/AC9 validation can use the actual refs.)**

3. **Given** the runner produces a `runner-result.v1.json` with `artifactType=prOutput`, **Then** the orchestration enriches the artifact's payload with the actual `branch`, `commitSha`, `prReference` from `captureAndPush`; the runner's reported values are validated against the actual git/GitHub state — a mismatch raises **`RUNNER_PR_REF_DRIFT`** (new `DomainErrorCode`, three-sites — [[new-domainerrorcode-three-sites]]) and routes the run to `Failed` via the existing contract-violation path. **(Decision D3: the prOutput artifact is ingested from the runner result FIRST [`onResult` parses + `recordOperation` ingests before `captureAndPush` runs]; enrichment therefore happens as a follow-on update keyed by the ingested artifact id, OR `captureAndPush` is hoisted ahead of EXECUTION ingest so the actual refs are available at `recordOperation` time. Recommend the follow-on update [least invasive — does not reorder the spec/plan ingest paths]; confirm with OQ-3. `diffReference` from the epic is OUT of scope — `RepositoryPushOutcome` carries no diffRef and `GitHubPullRequest` exposes `url`/`number`, not a diff handle.)**

4. **Given** the PR/output artifact's `prReference`, **Then** `IntegrationLinkService.linkGitHubPr(workflowRunId, prReference, ...)` is invoked transactionally — creating an `integration_links` row of type `github_pr`. **(DEFERRED to story 3.15: `IntegrationLinkService` exists [`application.integration.IntegrationLinkService`] but exposes only `linkTicket` [Linear]; there is NO `linkGitHubPr` and `captureAndPush` does NOT write an `integration_links` row for the PR [`RepositoryWorkspaceService.java:511-517` notes the linkage is "deferred to a caller that supplies the linkage (3.15/3.32)"]. 3.12 leaves a clearly-marked seam — a `// TODO(story 3.15): linkGitHubPr` call site after the prReference is validated — but does NOT build `linkGitHubPr`. The PR itself IS physically created/updated by `captureAndPush`; only the durable `integration_links` row is 3.15's deliverable.)**

5. **Given** the prOutput artifact is ingested (Decision D1 / [[markavailable-has-no-production-caller]]: ingest, not a true `available` artifact) AND any `captureAndPush` push/PR step succeeded, **Then** `WorkflowOrchestrationService.onPrOutputStageSucceeded(...)` fires the transition `Executing → WaitingForReview` with reason **`pr_output_ready`** — the pr-output twin of `onPlanStageSucceeded`. **This is the central new behavior** — the broker `else` branch (`:1031-1038`) currently drives NO transition for PR_OUTPUT (story 3.11's deferred absorbing-state). Delegate via the SAME lazy `Supplier<WorkflowOrchestrationService>` already in place. **Idempotent:** a duplicate/late result whose run already reached `WaitingForReview`/`Completed` surfaces `ILLEGAL_TRANSITION`, swallowed via `handlePrOutputReadyIllegalTransition` (mirror `handlePlanReadyIllegalTransition`; reuse `PLAN_READY_OR_BEYOND` or add a `PR_OUTPUT_READY_OR_BEYOND` set — see Trap T2).

6. **Given** wrong-ticket attach prevention per NFR20, **When** `linkGitHubPr` detects the linked PR's repo conflicts with the workflow's prior repository linkage, **Then** the orchestration raises `PR_REF_CONTEXT_MISMATCH` and refuses to advance. **(DEFERRED to story 3.15 with AC4 — the conflict check lives inside `linkGitHubPr`. Defense-in-depth only [story 3.9 AC9 already prevents the workspace from being prepared against a conflicting repo]. `PR_REF_CONTEXT_MISMATCH` is referenced as a test placeholder in `GitHubMockScenario` but NOT defined in `DomainErrorCode` — story 3.15 defines + wires it.)**

7. **Given** runner failures OR git-push rejections (story 3.9 AC7), **Then** the same handling as story 3.11 AC4 applies — failure event with the appropriate category, transition to `Failed`, preserve `runner_executions` + logs + workspace (incl. the branch on the local clone). **(ALREADY built: the broker drives EXECUTION failures via `driveWorkflowFailed`; the git-push-rejected path is handled at `RunnerBroker.java:945-970` [`GitCommandException` → `RUNNER_CONTRACT_VIOLATION` + `git.pushFailed` event + `driveWorkflowFailed`], and the table admits `Executing → Failed`. 3.12 CONFIRMS pr-output-stage failures land at `Failed` and reconciles the AC9/AC—success-only ArchUnit ownership exactly as 3.11 did — keep the broker's failure-drive, scope the new ArchUnit rule to the SUCCESS auto-advance only.)**

8. **Given** retry behavior, **Then** `WorkflowOrchestrationService.retryImplementation(workflowRunId)` re-dispatches with a fresh `runnerExecutionId` + fresh context-bundle version; `linkGitHubPr` uses idempotent linkage so a same-PR retry never duplicate-links. **(Built: `retryImplementation` re-dispatches ONLY [never re-transitions, Trap T1] with a key derived from durable run state [Decision D2]. The idempotent-linkage clause is DEFERRED with AC4 to story 3.15. `captureAndPush`/`createPullRequest` are ALREADY idempotent at the adapter layer [story 3.9/3.14: PR creation dedupes by `(repo, sourceBranch)`], so a same-branch retry reuses the existing PR even before 3.15 records the link.)**

9. **Given** runner output is untrusted (story 2.24), **Then** `prReference`, `branch`, `commitSha` strings are validated against documented patterns (branch `^[a-zA-Z0-9._/-]+$`; PR reference `^PR-\d+$` or a canonical GitHub PR URL; commit SHA `^[0-9a-f]{7,40}$`) — malformed strings raise **`RUNNER_OUTPUT_VALIDATION_FAILED`** (new `DomainErrorCode`, three-sites) and the artifact is rejected (routes to `Failed` via the contract-violation path). **(Validate the RUNNER-REPORTED values from the `runner-result.v1.json` prOutput payload, before/alongside the AC3 drift check. `diffReference` validation is out of scope — see AC3 clarification.)**

10. **Given** correlation propagation, **Then** the same `correlationId` chain extends through dispatch → runner events → push event → state transition. **(Thread the originating correlationId into `dispatchImplementation(runId, correlationId)` via `systemActor(correlationId)`, identical to the plan path. The `RunnerBroker.handleSuccess`/`onResult` already propagates the row's correlationId into the delegation — 3a-1 Trap T6.)**

11. **Given** the test suite, **Then** integration tests cover: happy path (approved plan present → `dispatchImplementation` → workspace prepared → runner edits → `captureAndPush` → prOutput artifact enriched → state at `WaitingForReview`), runner failure modes → `Failed`, push-rejection failure mode → `Failed` with git category, retry preserves audit, `RUNNER_PR_REF_DRIFT` when runner refs differ from actual git state, malformed PR ref / branch / commit SHA → `RUNNER_OUTPUT_VALIDATION_FAILED`, correlationId propagation. **(Mirror `ImplementationPlanOrchestrationIT`. The IT seeds an APPROVED implementation-plan artifact directly so `deriveExecutionSubStage→PR_OUTPUT`, then invokes `dispatchImplementation` directly [the live trigger is story 3.20]. Use the `happy-pr-output` mock scenario [override the EXECUTION default scenario via `@TestPropertySource`]. Name `*IT` so Failsafe runs it and the no-Docker Surefire fast tier excludes it — [[springboot-testcontainers-test-must-be-IT]]. Drive async via `pollActiveExecutions()`/`onResult(...)` directly, do NOT sleep on the poller — Trap T6. `PR_REF_CONTEXT_MISMATCH` / `ARTIFACT_PR_LINK_MISMATCH` / idempotent-linkage tests belong to story 3.15.)**

12. **Given** the `RecoveryService` scope-protected baseline (story 1.18 AC11), **Then** pr-output retry uses the baseline `retry` action only — deeper recovery (revert PR linkage, manual PR creation, reconcile diverged branch, force-push) lives in Epic 4 and any attempt to add such methods here fails the scope-protection ArchUnit rule. **(ALREADY enforced — confirm the new `retryImplementation` does NOT add any of those, mirroring `retryPlanGeneration`. No new code needed beyond honoring the boundary.)**

**Logging instrumentation** (cross-cutting; see task below) — `INFO` on `dispatchImplementation`/`retryImplementation` entry + dispatch decision + the `pr_output_ready` transition; `WARN` on in-flight no-op / retry / benign-replay-or-anomaly / ref-drift / ref-validation failure → `Failed`; carry `correlationId`, `workflowRunId`, `runnerExecutionId`, `stage`, `subStage`; never log payloads/secrets/host paths/PR bodies/diffs.

### Decisions (made by this story; rationale)

- **D1 — Build the pr-output orchestration seam as a DIRECTLY-TESTED flow; DEFER the live plan-approval trigger to story 3.20.** `ApprovalService` has no `acceptImplementation`; `deriveExecutionSubStage` returns PR_OUTPUT only when an approved plan exists, which nothing in production creates. This is the identical pattern to 3.10's dormant EXECUTION seam and 3.11's directly-tested plan seam. Story 3.20 will add `acceptImplementation` and call `dispatchImplementation` (exactly as `approveSpec` calls `dispatchPlanGeneration`). **Headline — confirm with OQ-1.** Fire `onPrOutputStageSucceeded` on successful artifact INGEST (the prOutput artifact stays `pending`; `markAvailable` unwired — [[markavailable-has-no-production-caller]], OQ-2).
- **D2 — Idempotency key from durable run state (mirror 3.11 D2).** `pr-output-dispatch:<runId>:<nextExecutionBundleVersion>` via `runnerExecutionRecordPort.nextContextBundleVersion(runId, EXECUTION)`. Deterministic + replay-safe; a retry advances the monotonic bundle version so the broker mints a fresh `runnerExecutionId`. (Note: plan and pr-output share the `(run, EXECUTION)` bundle-version counter, so their keys differ by prefix + version — verify the version monotonicity across the plan→pr-output progression doesn't collide; the plan dispatch consumes version N, the pr-output dispatch consumes N+1.)
- **D3 — Artifact enrichment via follow-on update, not ingest-time reorder.** The prOutput artifact is ingested (`recordOperation`) BEFORE `captureAndPush` runs in `onResult`. Recommend enriching the already-ingested artifact via a keyed update after `captureAndPush` returns (least invasive — does not reorder the shared spec/plan ingest path). Alternative: hoist `captureAndPush` ahead of EXECUTION ingest (riskier — touches the spec/plan path). Confirm with OQ-3. `diffReference` is OUT of scope (no source for it).
- **D4 — DEFER `IntegrationLinkService.linkGitHubPr` + `PR_REF_CONTEXT_MISMATCH` + `ARTIFACT_PR_LINK_MISMATCH` to story 3.15.** `linkGitHubPr` does not exist; building it is 3.15's entire deliverable. The PR is physically created by `captureAndPush` (story 3.9); 3.12 leaves a marked seam. AC4/AC6 are explicitly attributed to story 3.15 in the epic.
- **D5 — Keep the broker as failure-drive owner (mirror 3.11 D5).** Scope the new ArchUnit success-auto-advance rule to `onPrOutputStageSucceeded`; document the broker's `driveWorkflowFailed` as the pre-existing exception. The new ref-drift/ref-validation→Failed path also routes through the broker's contract-violation drive (consistent with `handleArtifactTypeMismatch`).
- **D6 — Two new DomainErrorCodes only.** `RUNNER_PR_REF_DRIFT` + `RUNNER_OUTPUT_VALIDATION_FAILED` (three-sites). No transition-table change, no Flyway, no schema patch (the prOutput artifact + events already model everything; enrichment updates an existing artifact payload). Confirm max Flyway stays at its current head before adding any migration.

### Logging Requirements (project-wide standard)

Every story is expected to leave the touched services observable enough to debug a production incident without re-deploying. Enforced via the "Logging instrumentation" task above.

- **Framework:** SLF4J + Logback. No `System.out`, no `printStackTrace()`. ADR `0019-structured-logging` governs format.
- **Surface:** `WorkflowOrchestrationService.dispatchImplementation`/`retryImplementation`/`onPrOutputStageSucceeded` + the broker PR_OUTPUT success-delegation + ref-drift/ref-validation branch. `INFO` lifecycle, `WARN` recoverable (in-flight replay, retry, benign-replay/anomaly, ref-drift/validation→Failed, runner/git failure→Failed), `ERROR` only unhandled. `DEBUG` hot-path + the deferred-linkage seam.
- **Required context keys:** `correlationId`, `workflowRunId`, `runnerExecutionId`, `stage`, `subStage`.
- **Forbidden:** payload bytes, secrets/tokens, raw PII, host absolute paths, PR/commit bodies, diffs. Route uncertain content through redaction before logging.
- **Test contract:** new logging surfaces pinned by at least one focused test (list-appender / `OutputCaptureExtension`).
