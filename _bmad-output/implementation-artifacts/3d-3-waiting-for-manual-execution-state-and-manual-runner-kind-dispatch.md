# Story 3d.3: `WaitingForManualExecution` State + `manual` Runner-Kind Dispatch

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **⚠️ READ FIRST — this story has real net-new schema + a state-machine + a registry fan-out; it is NOT a thin wiring story.** It introduces a first-class `manual` runner **kind** that, instead of launching a container or enqueuing container work, **emits the runner-contracts input bundle and parks the run in a new `WaitingForManualExecution` state**. The driver (ADR 0024): Claude dropped its unattended/headless prompt mode, so a subscription-only operator can't dispatch an automated Claude step — they must run the agent by hand and feed the artifact back through the governed pipeline. **3d-3 builds the dispatch-side park; 3d-4 builds the operator submission** (download bundle → run agent → `POST /manual-artifact` → transition out). Keep that line crisp: 3d-3 ends at "run is parked in `WaitingForManualExecution` with a retrievable bundle and an `awaiting_manual` runner_executions row + a `manual.executionRequested` event"; everything about *getting the bundle out* and *submitting a result* is 3d-4.
>
> **Three things the live codebase forces you to reconcile (read all three before coding):**
>
> 1. **There is NO per-project runner-kind selection today.** The `Project` aggregate (`domain.project.Project`) carries `ticketSourceKind`/`repoHostKind` (`ConnectorKind` = `linear`/`github`) — **not** a runner kind. The runner kind (`codex`/`claude`) is resolved **globally** from `RunnerProperties.kindForStage(stage)` / `kindForExecutionSubStage(subStage)`. AC1 ("selectable per project … via the Epic 3c configuration") therefore requires you to **add a per-project runner-kind override to the Project model** (new nullable field + `projects` column + entity/mapper/seeder/store fan-out) and a resolver method. This is the heaviest part of the story — see Task 1 + R1.
> 2. **The manual branch happens BEFORE enqueue — NOT inside `DockerRunnerAdapter`.** AC3/AC6 require manual to launch **no container** and occupy **no worker slot** ("parks rather than enqueues"). If you branch inside the adapter you've already gone queue → worker → `executeQueuedDispatch`, burning a worker slot to then "park" — that **violates AC6**. The correct seam is the **pre-enqueue chokepoint** (`WorkflowOrchestrationService.enqueueDispatch`, L1036, + the `RecoveryService` enqueue site, L427): resolve the kind there and, if `manual`, route to a park path that **never calls `runnerExecutionQueue.enqueue`**. See R2 — and mind the orchestration↔broker dependency cycle that story 3.17b deliberately broke.
> 3. **`runner_executions` has no `kind` column, and `awaiting_manual` is a brand-new non-terminal status.** Record manual provenance via the new `awaiting_manual` status (a 3-site registry+CHECK+placeholder widening, drop-then-re-add idiom like V12/V16) **plus** the `runnerKind=manual` detail on the `manual.executionRequested` event (`RUNNER_KIND` is already an allow-listed detail key). **Do NOT add a `kind` column to `runner_executions`** (R3) and **do NOT** add `awaiting_manual` to the terminal `ck_runner_executions_completed_correlation` set (it carries no `completed_at`).

## Story

As a backend developer,
I want a `manual` runner kind that emits the step's context bundle and parks the run in a new `WaitingForManualExecution` state instead of launching a container,
so that an operator can run an agent step by hand when an agent's unattended/headless auth is unavailable, through a governed path that re-enters the same validation/review pipeline as an automated runner.

## Acceptance Criteria

> These ACs are **reconciled** against the live codebase. The epic wording assumes "manual is selectable per project via Epic 3c config" and "a runner_executions row records kind manual" — but projects carry no runner kind today and runner_executions has no kind column. Where the epic wording assumes infrastructure that does not exist yet, the reconciled wording below is authoritative; the rationale is in Dev Notes (R1–R7).

1. **Given** the runner-kind registry, **Then** `MANUAL("manual")` is registered in `RunnerKind` alongside `CODEX`/`CLAUDE`, and a **per-project runner-kind override** makes `manual` selectable per project: a nullable `runnerKind` is added to the `Project` aggregate + the `projects` table (CHECK in the `RunnerKind` value set, null allowed); `ProjectRuntimeConfigResolver.resolveRunnerKind(workflowRunId, stage)` returns the project's override when present, else the existing **global** `RunnerProperties` per-stage kind. Selecting `manual` changes the **producer**, not the runner-contracts input/output schema (ADR 0024 D1). (Per-**stage**-per-project granularity is deferred — R1/Open Decision #1 — a single per-project override applied across stages ships the driver; the global per-stage kinds still apply to non-overridden projects.)

2. **Given** the workflow state machine (story 1.5), **Then** a new state `WAITING_FOR_MANUAL_EXECUTION("WaitingForManualExecution")` is added to `WorkflowState` + the three `workflow_runs.current_state` / `workflow_events.prior_state` / `workflow_events.resulting_state` CHECK constraints (additive migration, next free Flyway version, replay-safe drop-then-re-add). The `WorkflowTransitionTable` gains: **in** — `INVESTIGATING → WaitingForManualExecution` and `EXECUTING → WaitingForManualExecution` (the two dispatching states); **out** — `WaitingForManualExecution → {WaitingForSpecApproval, WaitingForReview, Failed, TakenOver, Reconciled}` (the post-step targets are exercised by 3d-4 on submission; `Failed`/`TakenOver`/`Reconciled` are recovery/safety edges). `assertCoversAllStates()` must still pass.

3. **Given** a step dispatched under the resolved `manual` kind, **When** the dispatch chokepoint runs, **Then** instead of `runnerExecutionQueue.enqueue(...)` it **composes + writes the runner-contracts input bundle** (persisted via `RunnerScratchStore.writeContextBundle`, retrievable by 3d-4) and transitions the run to `WaitingForManualExecution` — **no container is launched and no queue row is enqueued**. The park executes inside the caller's existing submit/approve transaction (eager compose, mirroring the deprecated synchronous `RunnerBroker.dispatch` body — NOT the worker's lazy compose).

4. **Given** the manual lifecycle, **Then** a new `WorkflowEventType MANUAL_EXECUTION_REQUESTED("manual.executionRequested")` is added and mirrored into **both** fixture sites (`workflow-event-types.fixture.json` + `workflow-events-response.schema.json`) per the "new WorkflowEventType → two fixture sites" rule; the OpenAPI snapshot regenerates **byte-identically** (the `eventType` schema is a free string, not a bound enum — no `openapi.json` change). The event is appended on park with `runnerExecutionId` + `workflowRunId` + `runnerKind=manual` reusing **existing allow-listed** `WorkflowEventDetailKeys` (no new detail keys). (`manual.artifactSubmitted` is **3d-4's** event — do **not** add it here.)

5. **Given** FR53 (common runner abstraction), **Then** a `runner_executions` row is recorded for the manual step with the **new non-terminal status `awaiting_manual`** (`RunnerExecutionStatus.AWAITING_MANUAL("awaiting_manual")`; 3-site widening: enum + `ck_runner_executions_status` CHECK + `runnerExecutionStatuses` placeholder), **no container/lease/worker columns set**, so the manual step is first-class in inspection/observability/lineage. The kind (`manual`) is carried by the `manual.executionRequested` event detail, **not** a new column (R3). `awaiting_manual` is **non-terminal** — it must **not** be added to `ck_runner_executions_completed_correlation` (no `completed_at`).

6. **Given** the queue (story 3.17), **Then** a manual step **does not occupy a worker slot** — the park path bypasses `RunnerExecutionQueue.enqueue` entirely; no `queued` row is created, the worker pool never sees it, and `RUNNER_QUEUE_FULL` backpressure is irrelevant to a manual dispatch.

7. **Given** allowed-actions (story 2.14), **Then** a `WaitingForManualExecution` run exposes the actions that let an operator obtain the bundle + submit a result: two new `AllowedAction` values (`OBTAIN_MANUAL_BUNDLE("obtain_manual_bundle")`, `SUBMIT_MANUAL_ARTIFACT("submit_manual_artifact")`) are added (drift: enum + `allowed-actions.placeholder.json` + `AllowedActionRegistryPinTest` wire-value pins) and a `WAITING_FOR_MANUAL_EXECUTION` case is added to `WorkflowInspectionService.computeActionMatrix` returning them (gated to the operator role — `workflow_owner` by default; other roles `VIEW_ONLY`). These values are **consumed by 3d-4** — 3d-3 only registers them + surfaces them in the matrix.

8. **Given** tests, **Then** coverage asserts: the resolved `manual` kind **parks** the run (state → `WaitingForManualExecution`) + **emits** the retrievable bundle + records the `awaiting_manual` `runner_executions` row + appends `manual.executionRequested`, and **no container is launched and no queue row is enqueued**; state-machine transitions in (`INVESTIGATING`/`EXECUTING` → `WaitingForManualExecution`) and out (→ `WaitingForReview`/`WaitingForSpecApproval`) are valid and illegal ones rejected; registry/CHECK/fixture/placeholder/OpenAPI drift all pass (states, runner status, event type, allowed actions); and **a default (non-manual) project is byte-identical to pre-3d** (no override ⇒ global per-stage kind ⇒ normal enqueue path, no new event, no park). New/changed code on `application.*` meets the standing **≥80% line-coverage** floor.

### R1 — Per-project runner-kind selection is the net-new keystone (and per-stage is deferred)
AC1's "selectable per project (and per stage)" has **no** backing in the current model — `RunnerKind` exists only as a global per-stage config + an image-lookup key. You are adding the **first** per-project runner-kind binding. Scope guard: ship a **single nullable per-project `runnerKind` override** (null ⇒ the existing global per-stage kind). That makes `manual` selectable per project — enough for the driver (an operator forcing a project's steps to manual). True **per-stage-per-project** selection (codex spec + manual execution on the *same* project) is a refinement — it needs either per-stage columns or a `project_runner_kinds(project_id, stage, kind)` table; defer it (Open Decision #1) and note the forward obligation. This mirrors how 3c-7 deferred ticket-source-**identity** routing while shipping the explicit-reference path. **Precedent:** 3d-1 adds a per-project (optionally per-stage) reviewer binding the same way — keep the two consistent if 3d-1 already merged a project-model migration (coordinate the column placement / migration version).

### R2 — Branch BEFORE enqueue; do not re-introduce the orchestration↔broker cycle
This is the architectural crux. The dispatch is async (3.17b): `WorkflowOrchestrationService`/`RecoveryService` call `runnerExecutionQueue.enqueue`; a worker later composes the bundle and calls `DockerRunnerAdapter`. For `manual` you must **not** go down that road at all (AC3/AC6: no container, no worker slot). So:
- **Resolve the kind at the chokepoint** (`enqueueDispatch` L1036, `RecoveryService` L427) — both already have (or can get) `ProjectRuntimeConfigResolver` (orchestration has it from 3c-7).
- **If `manual`, park; else enqueue.** The park composes the bundle **eagerly in the caller's tx** — which is actually *simpler* than the worker path: the worker has **no ambient tx** and must wrap every write in `dispatchTransactionTemplate` ([[story-3-17b-queue-activation-seams]]); the chokepoint runs inside the submit/approve `@Transactional`, so the row insert + event + transition just join it and roll back together on failure.
- **Cycle caveat:** 3.17b deliberately dropped orchestration's `RunnerBroker` field to break the broker↔orchestration cycle (ArchUnit pins the legacy `RunnerBroker.dispatch` to zero production callers). Do **not** re-add a `RunnerBroker` dependency to `WorkflowOrchestrationService`. Use a new `ManualExecutionDispatcher` (`application.runner`) that the chokepoints inject (like they inject `RunnerExecutionQueue`); the dispatcher → broker (compose only) edge is one-way and fine. Confirm with `ArchitectureBoundaryTest` after wiring.
- **Do NOT call the deprecated `RunnerBroker.dispatch`** (it's `@Deprecated` + ArchUnit-pinned to zero prod callers). Add a new `composeAndWriteManualBundle` method instead, factoring out the compose+write the legacy body already does.

### R3 — `awaiting_manual` status, no `kind` column
A manual row needs to be (a) distinguishable while parked and (b) not mistaken for a container execution. The new **non-terminal** status `awaiting_manual` does (a); the `manual.executionRequested` event's `runnerKind=manual` detail gives durable provenance for inspection/lineage (b) without a schema column. Adding a `kind` column would fan out across the entity, `insertPending`/`insertQueued`, every snapshot mapper, and the queue carriage for marginal benefit — skip it. **Critical:** `awaiting_manual` is non-terminal — keep it out of `ck_runner_executions_completed_correlation` (the `(status terminal) = (completed_at not null)` CHECK), exactly as `queued` is excluded (V16 comment). On 3d-4 submission the row finalizes to `completed` (terminal, stamps `completed_at`) — that's 3d-4's transition.

### R4 — Two dispatching states park; the OUT target depends on the parked stage
The runner is dispatched while the run is in a **working** state: spec runner ⇒ `INVESTIGATING`; execution runner (plan + pr-output sub-stages) ⇒ `EXECUTING`. So the park edges are `INVESTIGATING → WaitingForManualExecution` and `EXECUTING → WaitingForManualExecution`. On submission (3d-4) the run returns to the **stage-appropriate** post-step state: spec ⇒ `WaitingForSpecApproval`, execution ⇒ `WaitingForReview`. The parked run "remembers" its stage via the `runner_executions.stage` column — 3d-4 reads it to pick the target. 3d-3 declares **both** OUT edges in the transition table (additive); 3d-4 triggers them. Include `Failed`/`TakenOver`/`Reconciled` OUT edges so a parked run is recoverable / take-over-able and never wedged (ADR 0024 Consequences: a parked run has no timeout/auto-progress).

### R5 — No new DomainErrorCode in 3d-3
The submission-side typed errors (`MANUAL_EXECUTION_NOT_APPLICABLE`, `IDEMPOTENCY_KEY_CONFLICT`, validation failure, `RUN_NOT_FOUND`, `ACTION_NOT_ALLOWED`) belong to **3d-4's** `POST /manual-artifact` endpoint (epic AC 3d-4 #6). 3d-3's park path is internal and raises no new typed error. **Register zero new `DomainErrorCode`** here (avoid the three-sites fan-out for codes you don't use yet — [[new-domainerrorcode-three-sites]]).

### R6 — Allowed actions are registered here, consumed by 3d-4
`OBTAIN_MANUAL_BUNDLE` + `SUBMIT_MANUAL_ARTIFACT` are added + surfaced in the matrix in 3d-3 (AC7), but the endpoints that honor them (`GET …/manual-bundle`, `POST …/manual-artifact`) are 3d-4. The matrix case + drift pins must land now so the `WaitingForManualExecution` run already advertises the right actions when 3d-4 wires the endpoints. Role: gate to the single local operator (`workflow_owner` — the run owner); others `VIEW_ONLY`.

### R7 — Byte-identical parity for default/non-manual projects (the safety net)
The `default` project seeds `runnerKind = null` ⇒ `resolveRunnerKind` returns the global per-stage kind ⇒ the chokepoint takes the **existing enqueue path** unchanged. So no default/non-manual run ever parks, emits `manual.executionRequested`, or creates an `awaiting_manual` row. The AC8 parity test is the proof: a default-project dispatch is byte-identical to pre-3d (a `queued` row, worker dispatch, no new event). New behavior manifests **only** when a project's `runnerKind` override == `manual` (which only the park IT sets today — there's a project CRUD/UI in 3c-8/3c-9 but no UI affordance to set `runnerKind` yet; that surfacing is a forward concern / 3d-4-adjacent).

### Open Decisions surfaced for review (do not block implementation; defaults chosen)

1. **Per-project runner-kind granularity** — default: a **single** nullable per-project `runnerKind` override applied across stages (null ⇒ global per-stage kind). Per-stage-per-project selection (e.g. codex spec + manual execution on one project) is **deferred** to a follow-up (needs per-stage columns or a `project_runner_kinds` table). Proceeding single-override; flag at review if per-stage is needed for the pilot. **Coordinate with 3d-1** if it already added a project-model migration/columns.
2. **Park-path home** — default: a new `application.runner.ManualExecutionDispatcher` injected by both enqueue chokepoints (mirrors `RunnerExecutionQueue` injection), depending one-way on `RunnerBroker` for `composeAndWriteManualBundle`. Alternative: inline the branch in each chokepoint. Proceeding with the dedicated service (no duplication, no orchestration→broker cycle).
3. **Dispatch-result variant** — default: add `RunnerDispatchResult.Parked(handle, manualEventPublicId)` for honest logging; alternative: reuse `Queued`. Proceeding with `Parked`.
4. **Operator role for the new actions** — default: `workflow_owner` (the single local operator / run owner) gets `OBTAIN_MANUAL_BUNDLE`+`SUBMIT_MANUAL_ARTIFACT`; others `VIEW_ONLY`. Confirm against 2.14 role conventions; adjust in 3d-4 if the submitting role differs.
5. **`awaiting_manual` timeout/activity sentinel** — default: set `timeout_at = last_activity_at` (or a far-future sentinel) to satisfy `ck_runner_executions_timeout_after_activity` without implying a real timeout (a parked run has none — ADR 0024). Record the chosen sentinel + ensure the stale-scan/orphan reclamation never picks up an `awaiting_manual` row (it has no worker lease, so it should already be invisible to lease reclamation — verify against the 3.17b `findLeasedStaleByStageAndDispatchedAtBefore` scan).
