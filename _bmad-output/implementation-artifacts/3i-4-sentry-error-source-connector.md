# Story 3i.4: Sentry Error-Source Connector — issue ingest → operator-gated promotion to bug tickets

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an operator triaging production errors,
I want to browse Sentry issues for a project and promote selected ones into governed bug tickets,
so that the bugs I choose enter the governed workflow (on the Epic 3j bug profile) with their Sentry context — without Sentry auto-flooding the queue.

## Acceptance Criteria

1. **Given** a **new error-source adapter category** — an `ErrorSourceAdapter` port (a sibling to `TicketSourceAdapter`, *surfacing-not-sourcing*) with a `SentryErrorSourceAdapter` real/mock pair — **Then** it lists Sentry issues for a project filtered by environment / level / unresolved status, with credentials (Sentry auth token + org/project slug) via the 3c-5 encrypted store under the new `ConnectorRole.ERROR_SOURCE`. The Sentry adapter is resolved **by its own error-source category** (see Reconciliation **R-CK**: it does **not** get a `ConnectorKind` enum value and does **not** ride the `projects.ticket_source_kind` / `repo_host_kind` columns — a single registered impl resolved by ERROR_SOURCE-credential presence). It never `@Primary`-competes with the project's ticket source.
2. **Given** the 3c-5 credential store + redaction, **Then** Sentry credentials are write-only encrypted and never exposed on read; and Sentry issue payloads (title, culprit, stack context, permalink) pass the redaction / secret-fixture gate — the **two-gates** trap (fixtures-manifest **and** the hardcoded corpus `Set`), mirrored into `runner-contracts/redaction-policy.json` — before surfacing or promotion. Nothing secret is logged (ids/lengths only).
3. **Given** operator-gated promotion, **Then** a REST + CLI + FE surface lists Sentry issues and a **promote** action on a selected issue (a) creates a governed **bug ticket** in the project's ticket source via the 3f-1 `TicketSourceSubticketService` → `createSubticket` capability, carrying the Sentry issue context (title, culprit, permalink), then (b) submits a governed run through the **existing** `WorkflowCommandService.submit` path using the created bug-ticket ref as the origin reference. The run lands on the default spec pipeline today (see Reconciliation **R2** — Epic 3j's "bug profile" does not exist yet; the run reaches `bug`-profile parity only when 3j ships).
4. **Given** dedup, **Then** promotion is **idempotent on the Sentry issue id** — promoting the same issue twice neither creates a duplicate bug ticket nor a duplicate run. The durable dedup key is a persisted `sentry_issue` `integration_links` row keyed on the Sentry issue id (its active partial-unique index); a replay returns the existing `{bugTicketRef, workflowRunId}` linkage with `replay=true`.
5. **Given** the no-auto-create rule, **Then** **nothing** enters the queue without an explicit operator promote action — listing Sentry issues has **zero write effect** (read-only); there is **no poller / auto-promotion / `@Scheduled`** path in this story (a per-project auto-create flag is a documented forward option only).
6. **Given** the FE, **Then** a Sentry issue-list/promote view (reusing the 3c-9 `ProjectSelector` pattern) renders the filtered issue list with a per-issue promote action and an **"already promoted"** indicator (dedup made visible, non-color signifier); `schema.d.ts` is regenerated **first**; the view is **axe-clean** (WCAG 2.1 AA); **Vitest** covers list render, promote action, and already-promoted state; and the react-refresh-no-fn-export, `useLiveAnnouncement` one-commit-lag (`waitFor`), `validateSearch`-strips-param, and wire-sends-`null`-not-`undefined` traps are honored.
7. **Given** the doctor probe pattern (3c-10), **Then** a `sentry` doctor probe (auth + project reachability, profile-gated) is added and **every hardcoded `checksRun` assertion is incremented** (the fan-out trap: `18`→`19`); OpenAPI (`openapi.json`) + `schema.d.ts` regenerate (NOT byte-identical).
8. **Given** tests, **Then** coverage asserts: issue list (filtered, read-only — no write side-effect); promote → bug ticket + run with Sentry context; dedup replay (no duplicate bug/run, existing linkage returned); no-auto-create (list is read-only); redaction over Sentry credentials **and** a representative Sentry issue payload; doctor `checksRun` fan-out; `ConnectorRole`/Flyway drift; OpenAPI/`schema.d.ts` drift; FE Vitest + axe; and the `org.dradgo.application.integration.errorsource` package holds its **≥0.80 line** jacoco floor.
