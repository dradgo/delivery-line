# Story 1.18: CLI Minimum-Viable-Recovery Baseline

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a pilot installer or workflow-owner developer,
I want `deliveryline retry {runId}` plus detailed failure diagnostics on `status` / `history` that surface failed stage, last successful stage, failure timestamp, failure category, last activity timestamp, and next safe action,
so that when the first pilot run fails — which will happen before Epic 4 ships — there is a visible CLI recovery path rather than a stranded run.

## Acceptance Criteria

1. **`RecoveryService` baseline surface** — `org.dradgo.application.recovery.RecoveryService` exists as an `@Service` exposing **exactly two** public methods:
   - `RetryRecoveryResult retry(String workflowRunId, String idempotencyKey, ActorContext actor, String reasonText)`
   - `FailureDescription describeFailure(String workflowRunId)`
   No other public methods. Epic 4 will add `resume`, `rerun`, `reconcile`, `pause`, `classifyFailure`, and `takeover` — those are explicitly scope-protected by ArchUnit (AC12).

2. **`deliveryline retry {runId} [--idempotency-key K]`** — when invoked on a run in state `Failed`, the command:
   - (a) constructs a `RetryWorkflowCommand` (story 1.7) and flips the run `Failed → Executing` via `WorkflowCommandService.retryWorkflow(...)`,
   - (b) re-dispatches the last failed stage via `RunnerBroker.dispatch(...)` with a fresh `runner_execution_id` and fresh `context_bundle_version` (re-derived inside the broker as `recordPort.nextContextBundleVersion(runId, stage)`),
   - (c) appends a `recovery_actions` row (public id `rcv_…`) linking `triggering_event_id` to the `workflow.stateChanged → Failed` event and `resulting_event_id` to the `recovery.retried` event,
   - (d) appends a `recovery.retried` `workflow_events` row (`WorkflowEventType.RECOVERY_RETRIED`, intervention_marker=true, actor copied from the command).

3. **Retry on non-`Failed`** — when `retry` is invoked on a run whose `current_state` is not `Failed`, the service throws `DomainException(RETRY_NOT_APPLICABLE)` with `details.currentState` set to the actual state and `details.runId` set to the input. No state mutation, no recovery_actions insert, no event append.

4. **Interactive idempotency-key generation** — when the CLI `retry` is invoked without `--idempotency-key` and `CliInteractivityDetector.isInteractive()` returns true, a UUIDv7 is generated via the existing `UuidV7Generator` (same pattern as `submit` in `WorkflowCommands`). When stdin is non-interactive and no key is supplied, the existing `IdempotencyKeyValidator.missingKeyException()` is thrown (exit 101). Repeated retries with the same key REPLAY via `IdempotencyService` — no double-dispatch, no second `recovery_actions` row.

5. **`status` output adds failure diagnostics** — `WorkflowStatusView` gains the following nullable fields, populated only when `currentState == Failed`:
   - `failedStage` (the runner stage from `runner_executions.stage` of the most recent FAILED row, or `null` if no runner execution failed),
   - `lastSuccessfulStage` (the `prior_state` of the `workflow.stateChanged → Failed` event, which is the state the run last successfully entered),
   - `failureTimestamp` (the `created_at` of the `workflow.stateChanged → Failed` event),
   - `failureCategory` (the `failure_category` column from the same event row, normalized via `FailureCategory.value()`),
   - `lastActivityTimestamp` (the `last_activity_at` of the most recent runner_executions row for this run, or the failure timestamp if none),
   - `nextSafeAction` (computed: see AC8).
   When `currentState != Failed`, all five `failed*` / `last*Activity*` fields are `null` and `nextSafeAction` defaults to `await_outcome` (running) / `view_only` (terminal) per the table in Dev Notes. The `nextSafeAction` placeholder string `"pending (story 1.18)"` in `WorkflowInspectionService.NEXT_SAFE_ACTION_PLACEHOLDER` MUST be deleted by this story.

6. **`history` output on a Failed run** — `deliveryline history {runId}` already renders `event_type`, `prior_state → resulting_state`, `reason`, `failureCategory`, and `interventionMarker` (story 1.15). This story adds **no new fields to the history schema**. The story DOES add a regression test asserting that on a Failed run the rendered text/JSON shows the `workflow.stateChanged → Failed` and `runner.failed` events with the correct `failureCategory` and that the new `recovery.retried` event appears at the tail of a retried run's history. **No raw stack traces** in the output — diagnostic detail lives in structured logs (story 1.19; this story ensures logs carry `correlationId` so operators can grep).

7. **`describeFailure(runId)` returns typed `FailureDescription`** — a new public record with the same fields as AC5 plus `diagnosticReferenceCorrelationId` (the most recent `correlationId` recorded in `workflow_events.details` for this run, or `null` if none). `WorkflowInspectionService.getStatus(...)` consumes the same logic so the CLI and the application-facing `FailureDescription` cannot drift.

8. **`nextSafeAction = await_manual_reconciliation`** — when `describeFailure` (or `getStatus` on a Failed run) detects an `artifact_operations` row for this `workflow_run_id` with `status` in `('failed', 'failed_orphan')`, the returned `nextSafeAction` is the literal string `await_manual_reconciliation`. Otherwise, on a Failed run, `nextSafeAction = retry`. Tests pin both branches with fixtures.

9. **`recovery_actions` row contract** — the V1 schema already enforces the `rcv_` prefix, `action_type` CHECK in `('retry','rerun','resume','takeover','pause','reconcile')`, FK on `triggering_event_id` / `resulting_event_id` to `workflow_events`, FK on `workflow_run_id`, unique `idempotency_key`, and `result_status` CHECK in `('pending','succeeded','failed')`. This story populates the row with `action_type='retry'`, `triggering_event_id` = the failure event's `workflow_events.id`, `resulting_event_id` = the `recovery.retried` event's `workflow_events.id`, `actor_identity` and `actor_type` from the command, `reviewer_role=null`, `idempotency_key` from the command, and `result_status='succeeded'` after the broker dispatch completes (or `'failed'` if the dispatch throws — the row is still persisted with the typed error stamped in the `recovery.retried` event's `details`).

10. **Append-only guarantee (NFR4)** — `retry` never UPDATEs or DELETEs prior `workflow_events`, `artifacts`, `runner_executions`, or `approvals` rows. The retry adds: one `workflow.stateChanged` event (Failed→Executing, via the existing `WorkflowTransitionService` path), one `recovery.retried` event, one `recovery_actions` row, one new `runner_executions` row (fresh `rex_…`). A focused test (`RecoveryServiceAppendOnlyTest` or equivalent) seeds a Failed run, asserts the pre-retry event count `N`, invokes `retry`, and asserts the post-retry event count is `N + 2` (the state-changed event from `WorkflowTransitionService` + the `recovery.retried` event from `RecoveryService`).

11. **Scope-boundary comment + CLI help text** — `RecoveryService` Javadoc explicitly lists the Epic-4 methods (`resume`, `rerun`, `reconcile`, `pause`, `classifyFailure`, `takeover`) NOT included in this story. The `@Command(description = …)` on the new `retry` CLI command notes: *"Deeper recovery (reconcile, take over, rerun-from-arbitrary-step, failure-taxonomy classification, operator console) arrives in a later epic."*

12. **ArchUnit scope-protection** — `ArchitectureRuleCatalog` gains `RECOVERY_SERVICE_IS_SCOPE_PROTECTED`: a rule that the `org.dradgo.application.recovery.RecoveryService` class declares **exactly** the two public method names `retry` and `describeFailure` (private helpers allowed, public Epic-4 methods rejected). The rule fails loudly with a remediation hint pointing at Epic 4's planned methods so a future contributor cannot stealthily extend `RecoveryService` without an Epic-4 story.

  - [ ] `retry(runId, idempotencyKey, actor)` algorithm:
    1. `PublicIdPrefixes.require(runId, PublicIdPrefixes.WORKFLOW_RUN)` and `idempotencyKeyValidator.requireValid(idempotencyKey)` (or call through `WorkflowCommandService.retryWorkflow` which validates).
    2. Read the run snapshot. If `currentState != FAILED`, throw `DomainException(RETRY_NOT_APPLICABLE)` with `details = {runId, currentState}`. Do this BEFORE consuming the idempotency reservation so a misaddressed retry doesn't burn a key.

The next retry call (or operator intervention) can correct this; document the trade-off in Dev Notes.

### Architecture invariants (DO NOT violate)

- **Adapter package boundary** (`ADAPTER_PACKAGE_LAYOUT`): no new adapter slice. `RecoveryActionPersistenceAdapter` goes under `adapters.persistence`; the CLI `retry` command stays in the existing `adapters.cli.WorkflowCommands`.
- **`ONLY_WORKFLOW_TRANSITION_SERVICE_MAY_MUTATE_WORKFLOW_STATE`** (`ArchitectureRuleCatalog.java:227-232`): `RecoveryService` MUST go through `WorkflowCommandService.retryWorkflow(...)` (which calls `WorkflowTransitionService.transition`); it MUST NOT call `WorkflowRunStatePort.updateCurrentState(...)` directly. The ArchUnit rule will fail loudly if you try.
- **`APPLICATION_SERVICES_MUST_BE_NAMED_AS_SERVICES`** (line 212-217): the new class is `RecoveryService`, NOT `RecoveryOrchestrator` / `RecoveryManager` / etc. The suffix `*Service` is mandatory.
- **`APPLICATION_AND_DOMAIN_MUST_NOT_DEPEND_ON_PERSISTENCE_TYPES`**: `RecoveryService` depends on `RecoveryActionRecordPort` SPI only — never directly on `RecoveryActionEntity` / `RecoveryActionRepository`. The adapter implements the port.
- **`APPLICATION_COMMAND_DTOS_MUST_BE_SINGULAR`**: `RetryWorkflowCommand` already complies. Do not introduce a `*Commands` plural class outside `adapters.cli`.
- **`SPRING_SHELL_COMMANDS_MUST_BE_PLURALIZED`**: the new `@Command(name="retry", ...)` method goes on the EXISTING `WorkflowCommands` class — do not create a new `RetryCommand.java` or `RecoveryCommand.java` (the latter would violate `SHELL_COMMANDS_SUFFIX_REQUIRES_COMMAND_GROUP_ANNOTATION`).
- **`ADAPTER_SLICES_MUST_NOT_DEPEND_ON_EACH_OTHER`**: `adapters.cli` does NOT depend on `adapters.persistence`. `WorkflowCommands` reaches `RecoveryService` (application layer), not the persistence adapter.
- **No `System.out` outside `DoctorCommands`**: log via SLF4J only.
- **Stable correlation field name** `correlationId` (camelCase, no underscore, no capital ID): pinned by `IntegrationLoggingContractTest` + `RecoveryLoggingContractTest` (new).
- **Append-only**: NFR4. Retry never UPDATEs `workflow_events` rows. The `recovery_actions.result_status` column IS updateable (pending → succeeded / failed) and that update is intentional and pinned by tests — recovery_actions are NOT workflow_events.

### Failure-event discovery contract

The "failure event" is the `workflow_events` row matching ALL of:
- `workflow_run_id = runId`
- `resulting_state = 'Failed'`
- `prior_state IS NOT NULL`
- ordered by `created_at DESC, id DESC` — take the first.

This is the row that records the `Executing → Failed` transition. Story 1.5 guarantees that `WorkflowTransitionService` emits exactly one such row per failure (idempotency_key on the originating command prevents duplicates). The CHECK at line 81-95 of V1 schema constrains `resulting_state` and `prior_state` to canonical WorkflowState values; the parser in `WorkflowEventReadPort` returns typed enums.

**Edge case**: a run that was directly inserted with `current_state='Failed'` (no transition event — should never happen in production but is producible by malformed test fixtures) returns `null` for `failureTimestamp` / `lastSuccessfulStage` / `failureCategory`. `failedStage` is then derived solely from `runner_executions`. If no runner_execution exists either, all five new fields are `null` and `describeFailure` still returns a valid view with `nextSafeAction = retry`.

### Last-failed-runner-execution discovery contract

Among `runner_executions` rows for the run with status in `(failed, timed_out, orphaned)`, pick the one with the largest `created_at` (ties broken by `id`). Its `stage` column (one of `RunnerStage.values()` — `runner.spec`, `runner.implementation`, `runner.pr`, etc., depending on what 1.13 registered) is the stage to re-dispatch. Its `last_activity_at` is the `lastActivityTimestamp` field.

### Recovery-action vs runner-execution idempotency-key namespacing

The user-supplied `idempotencyKey` flows through TWO separate idempotency surfaces:
1. **`WorkflowCommandService.retryWorkflow`** — keys the `idempotency_records` table for the workflow-state transition.
2. **`RunnerBroker.dispatch`** — keys a `idempotency_records` row for the runner dispatch.

These collide if you pass the same key to both — the broker's `checkAndReserve` sees a row with `command_type = "RetryWorkflowCommand"` and a different `command_fingerprint` (the broker fingerprints by `workflowRunId|stage|contextBundleVersion`, not the retry envelope) and throws `IDEMPOTENCY_KEY_CONFLICT`.

**Solution**: namespace the broker's key with a stable suffix: `dispatchKey = idempotencyKey + ":runner"`. This is the same idiom story 1.14 used for Linear comment locking (per-`ticketRef` lock keys). Document the convention in Javadoc on `RecoveryService.retry`.

A third surface is **`RecoveryActionRecordPort`** itself — it also dedupes by idempotency_key. Use the bare key here (NOT the `:runner` suffix). The replay-detection in step 6 of the retry algorithm uses `RecoveryActionRecordPort.findByIdempotencyKey(rawKey)`.

### Recovery-action result_status state machine

```
        insert
          │
          ▼
       pending  ─── markSucceeded ──► succeeded   (terminal)
          │
          └────── markFailed    ──► failed       (terminal)
```

`succeeded` ⇆ `failed` transitions are NOT permitted. Adding this as a focused unit test in `RecoveryActionPersistenceAdapterUnitTest` is cheaper than baking it into a SQL trigger (architecture says triggers are deferred).

### Cross-cutting transactional concerns

- `retry(...)` runs inside `@Transactional`. The sequence:
  1. `WorkflowCommandService.retryWorkflow(...)` — its own `@Transactional` boundary (PROPAGATION_REQUIRED, so participates in the outer tx).
  2. `WorkflowEventWritePort.append(...)` for `recovery.retried` — participates.
  3. `RecoveryActionRecordPort.insert(...)` — participates.
  4. `RunnerBroker.dispatch(...)` — uses its own `dispatchTransactionTemplate` (PROPAGATION_REQUIRED) for the database half AND a non-transactional path for the actual adapter dispatch. **The broker's adapter dispatch happens AFTER the outer transaction commits** because `RunnerBroker.dispatch` performs `idempotencyService.complete(...)` followed by `scratchStore.writeContextBundle(...)` followed by `runnerAdapter.dispatch(...)` — all OUTSIDE the dispatch transaction template (see `RunnerBroker.java:209-232`). This means: if `RunnerBroker.dispatch` writes the runner_executions row successfully and the workflow_events row appends, then the outer tx commits, and then the adapter dispatch fails AFTER commit — the runner_executions row is `pending` in the DB but no runner is actually running. Re-running the timeout scan will eventually flip it. **This is the existing 1.13 contract; story 1.18 inherits it.** Document in Javadoc.
- `markSucceeded` / `markFailed` on the recovery action MUST happen INSIDE the outer transaction (PROPAGATION_REQUIRED) — if the outer tx rolls back, the recovery action row rolls back too, and the next retry attempt sees a clean slate.

### Open clarifications for the dev agent

(Numbered for cross-reference; default decisions in parentheses — proceed unless you find a blocker.)

1. **Should `RecoveryService.retry` call `WorkflowCommandService.retryWorkflow` (route through the existing command path) OR build its own transition?** *Default: route through `retryWorkflow`* — preserves the command pattern's idempotency, validation, and Reservation logic. If you find a concrete blocker (e.g., `retryWorkflow` rejects the command because the `idempotency_records.command_type` is `"RetryWorkflowCommand"` and the recovery_actions row keys off the same key — yes, this is exactly the case the namespacing in Dev Notes addresses), surface it and we'll revisit. **Do not** call `WorkflowTransitionService.transition` directly from `RecoveryService` — the ArchUnit `ONLY_WORKFLOW_TRANSITION_SERVICE_MAY_MUTATE_WORKFLOW_STATE` rule scopes that mutation to one path.

2. **`workflow-status.v1.schema.json` — bump to v2 or additive within v1?** *Default: additive within v1*, with the five new fields declared in `properties` AND listed in `required` (with `type: ["string","null"]` or `["string","null","date-time"]` so null is valid). The `schemaVersion: 1` constant stays. This honors the story-1.15 contract that the schema is forward-compatible within a major version.

3. **`describeFailure` on a non-Failed run — throw or return view?** *Default: return view with null fields*. `describeFailure` is called by `WorkflowInspectionService.getStatus` for EVERY status call, including non-Failed runs. Throwing would break the `status` command on every healthy run. The `retry` CLI path is the one that throws `RETRY_NOT_APPLICABLE` (AC3) — `describeFailure` is informational only.

4. **`runner_executions.stage` may be `null` if no runner was ever dispatched** — does AC5's `failedStage` then read null? *Default: yes, null is valid*. 6. **`recovery_actions.reviewer_role` column** — should retry populate it? *Default: leave NULL*. The column is nullable per V1 schema and the actor model in this baseline doesn't distinguish reviewer-role separately from `actor_type` for retry — Epic 4 will populate it for `takeover` / `reconcile` rows where the reviewer-role matters.

7. **Failure → Investigating transition path** — AC2 says retry transitions back to "the appropriate executing state per the transition table (story 1.5)". The transition table (line 40 of `WorkflowTransitionTable.java`) allows `Failed → Executing | Investigating | TakenOver | Reconciled`. *Default: always Executing* — the simplest baseline. Investigating-as-retry-target is an Epic-4 enhancement (e.g., "retry but route through Investigating so a human can re-scope first"). The retry command does not expose a target-state option.

The view fields are pinned to the **current** failure, not historical failures. A run can legitimately have a prior failed runner_execution if a previous retry-and-recover already happened; surfacing it would mislead.

### Logging Requirements (project-wide standard)

Every story is expected to leave the touched services observable enough to debug a production incident without re-deploying. Enforced via the "Logging instrumentation" task above.

- **Framework:** SLF4J + Logback (Spring Boot default). No `System.out`, no `printStackTrace()`.
- **Levels for this story:** INFO for `recovery retry start`, `recovery retry success`, `recovery retry replay`, `describe failure`, `describe failure resolved`. WARN for `recovery retry rejected` (RETRY_NOT_APPLICABLE), `recovery retry dispatch failed`. ERROR only on unexpected exceptions that escape `RecoveryService.retry` — these should be near-zero in practice because the typed-exception surface covers the documented sad paths.
- **MDC keys carried:** `correlationId` (pushed by `WorkflowCommands.pushCorrelation`), plus implicit `workflowRunId` parameter on every log line.
- **Forbidden in log output:** raw event details, full artifact payload byte content, raw context-bundle JSON. The CLI command's per-run idempotency key may appear at INFO since it's operator-supplied. NEVER log `correlationId` from external Linear webhooks or runner stdin — only the locally-generated UUIDv7 makes it into MDC.
- **Test contract:** `RecoveryLoggingContractTest` uses Logback `ListAppender<ILoggingEvent>` to pin log lines for the four happy / sad paths in Task 9.
