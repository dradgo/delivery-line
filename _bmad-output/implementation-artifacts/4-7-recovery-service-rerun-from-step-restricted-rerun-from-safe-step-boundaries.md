# Story 4.7: `RecoveryService.rerunFromStep` — Restricted Rerun from Safe Step Boundaries

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Workflow Owner who needs to rerun from an earlier safe step (e.g. re-spec because the original spec missed scope, or re-execute the implementation after fixing a runner config),
I want `RecoveryService.rerunFromStep(workflowRunId, targetStep, actor, idempotencyKey)` **restricted to safe step boundaries** — `Investigating` (re-spec) and `Executing` (re-implement) only,
so that operators have a deeper-than-retry rerun path without the unbounded "rerun from arbitrary step" risk that could re-execute already-approved decisions or re-create artifacts the team relied on.

## Context & Central Reconciliation (READ FIRST)

**This is the SEVENTH story of Epic 4 and the THIRD of the "Recovery Service Extensions" slice (4.5–4.9). It is a BACKEND-ONLY application-service story: add a `rerunFromStep(...)` method to the existing `RecoveryService`, backed by a new `WorkflowCommandService.rerunFromStepWorkflow` transition (to the caller-supplied `Investigating`/`Executing` target), a new `recovery.rerunFromStep` audit event, a `recovery_actions` row (`action_type='rerun'`), prior-approval INVALIDATION (the only real DB change — Flyway V38 adds two columns to `approvals`), runner re-enqueue with a fresh context-bundle version, a `rerun_from_step` allowed-action, a `SafeRerunStep` registry enum, and a best-effort Linear reopen notification. It has NO REST endpoint (story 4.12), NO CLI command (story 4.12 AC6), and NO frontend (stories 4.22/4.24). Ship ADR 0034.**

**Mirror `RecoveryService.resume` (`RecoveryService.java:676-972`) and `RecoveryService.reconcile` (`:974-1114`) — they are the structural twins** (single governed recovery action, `WorkflowCommandService`-routed transition to a caller-supplied target, REQUIRES_NEW prep tx, post-commit best-effort side-effect, full idempotency contract). Story 4.7 differs from 4.5/4.6 in FOUR substantive ways: (a) the transition target is chosen by the operator (`Investigating` vs `Executing`) not derived from a prior event; (b) it INVALIDATES the prior stage approval (the only Flyway migration in this slice); (c) its post-commit side-effects are TWO — the runner re-enqueue (like retry) AND a best-effort Linear reopen notification (like reconcile's integration re-push); (d) it records the pre-rerun active-leaf artifact ids as an audit annotation (there is NO artifact-supersession write — see Reconciliation 1).

**Read the seven Headline Reconciliations before coding — the epic AC text drifts hard from live code and these bindings win.** The dependency stories are DONE/verified: **4.5** (`resume` twin) merged `done`; **4.6** (`reconcile` twin) is in `review`; **4.28** (scope-lift) merged `done` — so `RECOVERY_SERVICE_IS_SCOPE_PROTECTED` is GONE and `rerunFromStep` is already NAMED on ADR 0033's sanctioned allow-list (`RecoveryService.java:69-70`). There is **no scope-lock to widen** (a hard drift from 4.5, which had to widen it).

### HEADLINE RECONCILIATIONS

1. **THERE IS NO ARTIFACT-SUPERSESSION MECHANISM — DO NOT BUILD ONE. Artifact obsolescence is expressed by lineage graft (`version`+1 moves the active leaf); the epic's "prior artifacts marked superseded" is satisfied by the EXISTING graft path as each re-run stage produces its next artifact version. `rerunFromStep` at rerun time only READS the current active-leaf artifact ids at/beyond the target step and records them in the `recovery.rerunFromStep` event's `details.supersededArtifactIds` for audit.** The `artifacts` table has NO `superseded_at`/`superseded_by` column and NO `superseded` status (`ArtifactStatus` = `PENDING/AVAILABLE/FAILED/LATE_OR_STALE`, `ArtifactStatus.java:6-9`; `V1__create_workflow_core_tables.sql:103-135`). The codebase's ONLY obsolescence mechanism for artifacts is the lineage chain (`parent_artifact_id` + monotonic `version`; the active leaf is resolved by the recursive CTE `ArtifactRepository.findActiveLineageLeaf`, `ArtifactRecordPersistenceAdapter.findLatestActiveLineageMemberEntity:402`). When the re-run runner produces its new artifact, `ArtifactOperationService.hasActiveLineage(...)` (`:524`) returns true and it GRAFTS `createNextVersion` (version N→N+1, `parent_artifact_id`=old leaf) — the prior version is preserved (audit / Compare Mode 4.19) and the leaf advances. ## Dev Notes

### Relevant architecture patterns and constraints

- **`RecoveryService.resume` (`:676-972`) + `reconcile` (`:974-1114`) are the exact structural templates.** Copy the shape: MDC scope → idempotency validate → input parse/validate → replay pre-check (actionType-guarded) → current-state/target resolution → locate linking event → REQUIRES_NEW prep tx (transition-via-command-service + append recovery event + insert `recovery_actions` row [+ approval invalidation for rerun]) → post-commit side-effect(s) OUTSIDE the tx with compensation → `markSucceeded` → return. `rerunFromStep` differs only in: the target is operator-chosen (`SafeRerunStep`→`WorkflowState`), a prior approval is invalidated in the prep tx, there are TWO post-commit side-effects (runner re-enqueue + best-effort Linear reopen), and it reads leaf artifact ids for the audit detail.
- **⚠️ Double-dispatch caution (inherited from resume).** Keep re-dispatch in EXACTLY ONE place: `rerunFromStepWorkflow` (the command method) does the transition ONLY; `RecoveryService.rerunFromStep` performs the single re-enqueue after the prep tx commits. Do NOT also enqueue inside `rerunFromStepWorkflowInternal`.
- **⚠️ No artifact-supersession write (Reconciliation 1).** The active leaf advances via lineage graft when the runner re-runs; rerun's only artifact interaction is a READ of the current active-leaf ids at/beyond the target step for `details.supersededArtifactIds`. Do NOT add an artifact status/column or a supersede port method — that overlaps the artifact-reconciliation stories (4.15/4.16/4.16a) and is explicitly out of scope.
- **State machine.** `FAILED→{INVESTIGATING,EXECUTING}` and `WAITING_FOR_REVIEW→EXECUTING` are legal today (`WorkflowTransitionTable.java:142-143,98`). `WorkflowTransitionService.transition` reads current state and validates target ∈ allowed-targets, raising `ILLEGAL_TRANSITION`/`CONCURRENT_TRANSITION_CONFLICT`. INVESTIGATING/EXECUTING targets need NO mandatory reason at the table level — rerun's required `reasonText` is a STORY-level guard (`MISSING_REASON_TEXT`). Pass `failureCategory=null` (the generic `transition` helper does).
- **Approval invalidation is the enforced gate.** `findLatestApprovedForArtifactLineage` + `getCurrentApprovedSpec` are the read surfaces; the single JPQL `invalidatedAt is null` filter makes both spec and future plan reads honor invalidation. There is NO `getCurrentApprovedPlan` today — the plan invalidation is a write + the generic read filter (no dedicated plan reader to change). Route the write through the approval package (`ApprovalService`) to honor the write-boundary spirit (mirror 4.6's `IntegrationConflictService.resolveConflict`).
- **Fresh context-bundle version is free.** `RunnerExecutionQueue.enqueue` mints `nextContextBundleVersion` (MAX+1) → `insertQueued` → a fresh dispatch fingerprint, so the re-run is not deduped against the prior run. `RecoveryService.retry:537-541` is the working template (incl. the manual-kind park branch).
- **`RecoveryActionSnapshot` shape** (11 components + `reviewerRole`): tests seed these directly (see `RecoveryLoggingContractTest`). Reuse the resume/reconcile replay + concurrent-replay helpers as templates (`resolveConcurrentResumeReplay:1257`, `resolveConcurrentReconcileReplay`).
- **Deferred review note carried from 4.5:** the `recovery.dispatchFailed` event reuses the retry-flavored `RECOVERY_RETRIED_EVENT_ID` detail key to carry the recovery-event id (the only allow-listed recovery-event-id key). Rerun's dispatch-failure event will do the same until a dedicated key is introduced — acceptable, matches resume.
