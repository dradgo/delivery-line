## Story

As an operator,
I want REST endpoints to list, create, edit, disable, credential, and connectivity-test projects through a governed, localhost-only, idempotent, Problem-Details contract that never returns a stored secret,
so that the Projects UI (3c-9) and operator scripts can manage projects without editing config files — and I can verify a project's repository + ticket-source + repository-host are reachable and authenticated before scoping governed work to it.

## Acceptance Criteria

> These ACs are **reconciled** against the live REST/idempotency/Problem-Details conventions, the actually-merged backend (`ProjectStore` minimal; credential store write-only; resolver live; **no connectivity probe exists**), and the absence of multi-user RBAC. Where the epic wording assumes infrastructure that does not exist yet, the reconciled wording below is authoritative; the rationale is in Dev Notes → "Why these ACs are reconciled."

1. **List / create / read / update / disable.** A `ProjectController` (`adapters.rest`, `@RestController @Validated @RequestMapping("/api/v1/projects")`) exposes:
   - `GET /api/v1/projects` → `List<ProjectResponse>` (bare list, no envelope — matches `WorkflowController`).
   - `POST /api/v1/projects` (create) → `201` + `ProjectResponse` (generates a `prj_` public id; slug uniqueness enforced).
   - `GET /api/v1/projects/{projectId}` → `ProjectResponse` (`PROJECT_NOT_FOUND` 404 on a miss).
   - `PUT /api/v1/projects/{projectId}` (update name / repository url / kinds / OpenSpec flag) → `200` + `ProjectResponse`.
   - `POST /api/v1/projects/{projectId}/disable` (soft-disable: `status := DISABLED`) → `200` + `ProjectResponse`.
   
   **`ProjectResponse` carries project configuration but NEVER any credential value (plaintext or ciphertext)** — it conveys per-role credential *presence* (`configured` / `not_configured`) only. The reserved `default` project (`slug = "default"`) **cannot be disabled** (it is the run-time fallback) — attempting it is rejected (R7b).

2. **Write-only credential set / rotate.** `PUT /api/v1/projects/{projectId}/credentials/{role}` accepts a single connector credential for `role ∈ {ticket_source, repo_host}` (underscored `ConnectorRole` wire values) in the request body, delegates to `ProjectCredentialService.setCredential(...)`, and returns ONLY a non-secret confirmation (`{ "role": "...", "status": "configured", "credentialId": "cred_…" }`). **No endpoint, DTO, serialization path, or log line ever returns the stored secret** — set/rotate only, never read back (3c-5's write-only contract is preserved end-to-end).

3. **Capability-aware connection test.** `POST /api/v1/projects/{projectId}/test-connection` runs **per-check** probes and returns `200` + a `TestConnectionResponse` with one result per check — **repository reachable**, **ticket-source auth**, **repository-host auth** — each `{ check, status: pass|fail|skipped, detail }`. It resolves the project's adapters via `ProjectConnectorResolver`, honors `getCapabilities()` (a check the adapter cannot perform is `skipped`, not `fail`), and probes connectivity via a **new vendor-neutral `verifyConnectivity()` port method** (R1). Per-check failures are **in-band data** (HTTP 200), not Problem-Details errors. Credentials used for the probe come from `resolveConnectorSecret` (3c-5 store) with the existing host-env path as fallback, and are **never written to logs, the response, or any history/audit row** (R5).

4. **Error handling via registered codes + secret-hostile cipher mapping.** Problem-Details responses use the already-registered codes: `PROJECT_NOT_FOUND(404)`, `PROJECT_SLUG_CONFLICT(409)` (create/update slug collision, mapped at the persistence adapter), `UNSUPPORTED_CONNECTOR_KIND(400)` (a project carrying a kind with no registered adapter), idempotency codes (`IDEMPOTENCY_KEY_CONFLICT`, `MISSING_IDEMPOTENCY_KEY`, `STALE_IDEMPOTENCY_RESERVATION`), and `CREDENTIAL_MASTER_KEY_UNCONFIGURED(503)` when a credential set is attempted with no master key. A `CredentialCipherException` (tamper / wrong-key / bad-algo on the credential path) is mapped to a **generic secret-hostile 500** (`INTERNAL_ERROR`, no plaintext/ciphertext/keyId in the body or log) — it must not fall through to the opaque generic handler. **No new `DomainErrorCode` is introduced** (default; see Open Decision #3).

5. **Idempotency (story 1.9).** `POST /api/v1/projects` (create) and `PUT …/credentials/{role}` (set/rotate) accept an `Idempotency-Key` header, validated with the same guards `WorkflowController` uses (`requireNonBlankIdempotencyKey` + `rejectMultiValuedIdempotencyKeyHeader`), and routed through the existing **generic** `IdempotencyService.checkAndReserve(key, commandType, actorIdentity, fingerprint)` → `complete(...)`. The fingerprint is a SHA-256 over the canonical command payload (excluding the secret value for credential-set — only its presence/role/project participate, so a replay with the same key+role is idempotent without the plaintext entering the fingerprint). A conflicting key with a different payload → `IDEMPOTENCY_KEY_CONFLICT(409)`; a missing/blank key on a required endpoint → `MISSING_IDEMPOTENCY_KEY(400)`.

6. **Backend-reported allowed actions.** `ProjectResponse` carries a backend-computed `allowedActions: String[]` (wire values) reflecting what is permissible for that project's current state — e.g. an `ACTIVE` non-default project allows `edit`, `disable`, `set_credential`, `test_connection`; a `DISABLED` project allows `edit`, `enable`, `set_credential`, `test_connection` (not `disable`); the `default` project never offers `disable`. Actions are **backend-derived, not frontend-inferred**, consistent with the workflow `allowed-actions` model (single-operator, no RBAC — actions gate on project status, not a role).

7. **Localhost-only binding.** The project endpoints bind loopback-only via the **existing** `RestBindingGuard` (no per-endpoint work); a test asserts a project endpoint is reachable on `127.0.0.1` exactly as the existing OpenAPI snapshot test proves the connector bound loopback.

8. **OpenAPI snapshot + drift.** The new endpoints + request/response schemas are reflected in `src/main/resources/openapi/openapi.json` (regenerated byte-identically via `-Dopenapi.snapshot.write=true`) and pass `OpenApiSnapshotContractTest`; the test's pre-existing-operation assertions (the workflow POST/GET set) stay green, and the new `listProjects`/`createProject`/`getProject`/`updateProject`/`disableProject`/`setProjectCredential`/`testProjectConnection` operations are present.

9. **Tests.** Coverage asserts: CRUD behavior (create→read→list→update→disable); **write-only** credential handling (set returns only the `cred_` id; no read-back method/path exists; no serialization of ciphertext); connection-test per-check result shape (pass/fail/skipped incl. a capability-skipped check); error mapping (slug conflict 409, not-found 404, unsupported kind 400, master-key 503, cipher-failure secret-hostile 500); idempotency (replay returns the same result; payload conflict 409); allowed-action derivation per status; and the default-project-cannot-be-disabled guard. New `application.project` + `adapters.rest` code meets the standing **≥80% line-coverage** floor; credential-adjacent paths **≥90%**.

### R1 — The connectivity probe is the one genuinely net-new capability (read this twice)
Everything else in 3c-8 is wiring over merged backend. The probe is not: the ports have **no** health/ping/verify method, and 3c-10 (doctor) explicitly **defers live connectivity to 3c-8** (its `connectionTest=not-run`). So 3c-8 **owns** the first live probe. The reconciled design adds `ConnectivityResult verifyConnectivity()` to both ports because: (a) reusing business reads (`getRepositoryByRef`/`pollNewTickets`) conflates "404 not-found" with "401 unauthenticated" and has side effects (polling advances state) — it cannot cleanly answer *reachable* vs *authenticated*; (b) a dedicated probe returns a clean per-check tri-state and is trivially deterministic for mock/stub adapters. The cost is the same fan-out 3c-3 paid for `connectorKind()` (6 adapters + test fakes). The return type is a **neutral record** (no vendor leak). **This is Open Decision #1** — if the team rejects a port widening, the fallback is reuse-existing-reads with documented 404/401 ambiguity; flag at review before implementing, but the default is the dedicated probe.

### R2 — `findAll` is a co-edit with 3c-10; the slug-conflict mapping is a real gap
`ProjectStore.findAll()` is claimed by **both** 3c-8 (the list endpoint) and 3c-10 (doctor's project listing). Whichever story merges first introduces it; the second reuses the identical signature (clean rebase-merge). Separately, 3c-6 shipped the `ProjectPersistenceAdapter` with **no** `DataIntegrityViolationException → DomainException` translation — the seeder just catches a raw DIVE as "already seeded". The REST create/update path needs the typed `PROJECT_SLUG_CONFLICT(409)`; add the `mapViolation`-style switch (precedent: `ProjectCredentialPersistenceAdapter`). Without it, a duplicate slug surfaces as an opaque 500.

### R5 — Credential paths stay secret-hostile end-to-end
3c-5 built the store secret-hostile (no read-back, no secret in logs). 3c-8 must not regress that at the REST boundary:
- **`SetCredentialRequest.secret` is the only plaintext ingress** — `@Schema(accessMode = WRITE_ONLY)`, never echoed, never logged, **excluded from the idempotency fingerprint**.
- **`ProjectResponse` carries presence, not the value** — `configured`/`not_configured` per role (derive from `ProjectCredentialRecordPort.findActive` presence or a thin `ProjectCredentialService.isConfigured(project, role)` helper — add one if absent; it returns a boolean, never the secret).
- **`CredentialCipherException` → generic 500** with a fixed title and an `ERROR` log of only `project`/`role` — no message/cause/keyId. The connection-test's `getDecrypted` can throw it (tampered row) — catch it in `ProjectConnectivityService` and render the affected check as `fail` with a safe detail, **not** a 500 (a tampered stored credential is a per-check failure, not a request error).
- **The connection-test probe never persists** the secret to logs, the response, or any history/audit row (AC3). The probe credential is resolved at use-time and discarded.

### R6 — Allowed actions: status-derived, no RBAC, embedded in the response
The workflow `allowed-actions` model gates on **run state + actor role**. Projects have **no role dimension** (single operator) — so project actions gate purely on **status**: `ACTIVE` → `edit`/`disable`/`set_credential`/`test_connection`; `DISABLED` → `edit`/`enable`/`set_credential`/`test_connection`; `default` project → never `disable`. Keep the derivation a small pure function (shared by the service + tests). Do **not** add a `ProjectRole`/`ProjectAllowedAction` enum unless the wire surface needs distinct typed values — a `List<String>` of wire action names embedded in `ProjectResponse` is sufficient and matches `AllowedActionsResponse`'s `actions: String[]` shape. (Open Decision #2: separate `GET …/allowed-actions` endpoint vs embedded field — default embedded.)

### R7b — The `default` project is immutable-ish
The seeded `default` project (`slug = "default"`, `publicId = "prj_default"`) is the run-time fallback (`ProjectRuntimeConfigResolver`). Disabling or deleting it would break every default-project run's resolution (3c-6 review flagged "failed/deleted default → per-request `PROJECT_NOT_FOUND`"). So `disableProject` **rejects** the `default` slug. Editing its config (repo url, kinds, OpenSpec, credentials) is allowed — that is how an operator configures the single-project deployment via the UI. Deletion is **out of scope** (the epic says disable, not delete; soft-disable only).
