# Story 3.10: Full Context Bundle Generation for Implementation Stage

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a backend developer,
I want `ContextBundleService.create(...)` (the **execution-stage** bundle path, sibling of story 2.8/3a-2's spec-stage path) extended to produce full implementation-stage context bundles — carrying the **approved spec** (plan sub-stage) or **approved implementation-plan** (pr-output sub-stage), prior reviewer decisions + incorporated clarifications, repository workspace context (tree/README/manifests from story 3.9/3a-2), the expected deterministic branch name (story 3.9 AC2), and a pointer to the `/workspace/repo` mount — gated so that **no-repo and non-execution dispatches stay byte-for-byte identical to today**,
so that runners dispatched at the implementation stage have everything they need to act without reconstructing context — fulfilling FR54 (full bundle generation) and FR55 (inspectable bundles for an agent step).

## Context & Central Reconciliation (READ FIRST)

This story extends the **existing, working** generic execution-stage composer — it does NOT create a parallel service. The execution bundle is composed by `ContextBundleService.create(...)` (`deliveryline-backend/src/main/java/org/dradgo/application/runner/ContextBundleService.java:140`), assembled by the private `assemble(...)` (`:451`), redacted once via `RedactionPolicyService.redact(root, classification)` (`:175`), validated against `context-bundle.v1.schema.json` by `RunnerContractValidator`, and returned as redacted bytes. You are making this path **stage-aware** and **repo-aware** for the two implementation sub-stages, sourcing the new content from the approvals/clarifications read ports and from a prepared repository workspace. **This is the direct execution-stage analog of what story 3a-2 did for `createForSpecInvestigation` — read `3a-2-spec-stage-repo-context-bundle-extension.md` first; this story mirrors its decisions, traps, and gating discipline almost verbatim.**

**THE THREE STRUCTURAL FACTS THAT SHAPE THIS STORY:**

1. **The wire enum has only two stages.** `RunnerStage` is `{INVESTIGATION, EXECUTION}` (`domain/registry/RunnerStage.java:6-7`) — there is **no** `implementation-plan` or `pr-output` constant. Both implementation sub-stages map to `RunnerStage.EXECUTION`. **The implementation-plan-vs-pr-output distinction is therefore SEMANTIC and MUST live in the composition method, not the registry** — exactly as `createForSpecInvestigation` carries the spec semantics while reusing `RunnerStage.INVESTIGATION` (`ContextBundleService.java:218-240`). Do **NOT** add registry enum values (it would fan out to `RunnerStage` parsers, `RunnerProperties` timeout/scenario maps, mock scenarios, and the SQL/contract surface — out of scope and unnecessary).

2. **No production caller dispatches `EXECUTION` today — this is a DORMANT seam.** `WorkflowOrchestrationService` (story 3a-1) only dispatches `RunnerStage.INVESTIGATION` (`WorkflowOrchestrationService.java:153,204`). The epic ACs reference `dispatchPlanGeneration` (story 3.11) and `dispatchImplementation` (story 3.12) as the live callers, but **both are epic-3b deferred and do not exist**. Therefore — exactly like stories 3.9 and 3a-2 — **this story delivers the full, directly-tested capability + a gated seam**, proven by **unit tests** (composition) + a **`github-mock`-profile integration test** (repo-context end-to-end), NOT a full spec-approved→plan-dispatch e2e (that is story 3.11's job). The `RecoveryService` retry path (`RecoveryService.java:418`) can re-dispatch a `failedStage` of `EXECUTION`, so the execution `create(...)` path is *reachable* but not *originated* in production.

3. **The repo-context seam is wired for INVESTIGATION only — this story extends it to EXECUTION.** The broker resolves `repositoryRef` and clones-then-summarizes **only when `stage == RunnerStage.INVESTIGATION`** (`RunnerBroker.java:388-391`, `:413-418`); the `else` branch (EXECUTION) calls `contextBundleService.create(...)` with **no repo context** (`:434-444`). Story 3a-2 built `prepareWorkspace` / `summarize` / `resolveConfiguredRepositoryRef` / the 5 additive schema repo-fields / the `RunnerDispatchRequest` repo seam — **all of that is reusable verbatim**; this story extends the broker's gating to also cover the EXECUTION stage and threads the summary + branch into the extended `create(...)`.

**THE GATING DISCIPLINE (mirrors 3.9 / 3a-1 / 3a-2):**

- The fast Surefire tier runs with **no `github-mock`/`github-real` profile**, so the profile-gated `RepositoryWorkspaceService` bean is **absent** → the broker's nullable `repositoryWorkspaceService` field (`RunnerBroker.java:99`, resolved from `ObjectProvider.getIfAvailable()` at `:156`) is `null` → **no repo summary is produced → the execution bundle's repo fields are absent**. Combined with the sub-stage default below, the no-repo execution bundle must stay valid and minimal. ~780 fast tests stay green.
- The full repo-context path is proven by a **`github-mock`-profile integration test** with a configured repo + the story-3.9 local-bare-repo harness (mirror `SpecStageRepoContextIT`).
- `repositoryRef` has **no Linear↔GitHub mapping** (deferred to stories 3.32/3.33). For the pilot it is **config-resolved** from `deliveryline.workflow.repos` via the existing `RepositoryWorkspaceService.resolveConfiguredRepositoryRef()` (1:1 single-repo). `ticketRepositoryMappingVersion` is the same config-derived marker 3a-2 uses.

**Scope boundary:** Do **NOT** build `dispatchPlanGeneration` / `dispatchImplementation` / the `WaitingForReview` auto-transitions (stories 3.11/3.12). Do **NOT** change `createForSpecInvestigation` (story 3a-2's path — spec-investigation only). This story is the **execution-stage `create(...)` composer + the broker's EXECUTION repo-context gating + the schema/fixtures to support them.**

## Acceptance Criteria

> Criteria are the epic's verbatim ACs (`epic-03-agent-execution.md` §"Story 3.10", lines 203–214) with **binding clarifications** added inline in **bold parentheticals** where the epic wording predates the live code or references not-yet-built upstream pieces.

1. **Plan sub-stage composition.** `ContextBundleService.create(...)` is extended so that for the **implementation-plan** sub-stage it assembles: `ticketSummary` (existing), the **approved spec artifact reference** (`approvedSpecificationReference` — already sourced via `latestAvailable(run, SPEC)` at `:160`), **prior PM decision history** (approvals + rejection feedback rows, sourced from `ApprovalReadPort` — `listByWorkflowRunAndArtifactType` / `listRejectionsByWorkflowRunAndArtifactType` for `ArtifactType.SPEC`, mirroring `createForSpecInvestigation`'s rejection sourcing at `:275`), **incorporated clarification answers** (status `incorporated` per story 2.12, sourced from `ClarificationReadPort.listByWorkflowRunId` filtered by `Clarification.isIncorporated()`), `executionConstraints`, `classification`. **(PM decisions + clarifications ride the existing `priorFeedbackReferences` array via distinct `kind` values — `spec.approval` / `spec.rejection` / `clarification.incorporated` — NOT new top-level schema fields; see Decision D3.)**

2. **PR-output sub-stage composition.** For the **pr-output** sub-stage, the bundle additionally includes: the **approved implementation-plan artifact reference** (`approvedImplementationPlanReference` — NEW additive optional schema field, sourced via `latestAvailable(run, IMPLEMENTATION_PLAN)`), **technical-feedback history** if a prior plan version was rejected (`priorFeedbackReferences` `kind=implementationPlan.rejection` from `ApprovalReadPort.listRejectionsByWorkflowRunAndArtifactType(run, IMPLEMENTATION_PLAN)`), **repository context** (the 5 repo fields from story 3a-2: `repositoryWorkspaceRef`, `repositoryTreeSummary`, `repositoryReadmeRef`, `packageManifestRefs`, `ticketRepositoryMappingVersion` — derived by `RepositoryWorkspaceService.summarize`), the **expected branch name** from the deterministic convention (`repositoryBranchRef` — NEW additive optional field, = `RepositoryMount.branch()` from story 3.9 AC2), and the pointer to `/workspace/repo` (already `repositoryWorkspaceRef`). **(Repo context + branch are emitted ONLY when a workspace was prepared; absent on no-repo dispatches — byte-identical to today. The implementation-plan sub-stage MAY also carry repo context when a workspace is prepared — repo context is workspace-gated, not sub-stage-gated; only `approvedImplementationPlanReference` + the technical-feedback `kind` are pr-output-specific.)**

3. **Schema validation.** The produced bundle conforms to `context-bundle.v1.schema.json` (story 1.6) and is validated by `RunnerContractValidator` **before persistence** — invalid bundles fail at the boundary (existing behavior at `:182-201`). The two NEW fields (`approvedImplementationPlanReference`, `repositoryBranchRef`) are added as **optional** `properties` (NOT in `required`) so no-repo / spec-investigation / legacy bundles still validate; `additionalProperties:false` and `schemaVersion const:1` are preserved. **Additive backward-compatible in-place v1 patch — no version bump** (mirrors the 3a-2 repo-field precedent + the `minItems` 1→0 precedent at `context-bundle.v1.schema.json:86-87`). `ContextBundleService.CONTEXT_BUNDLE_SCHEMA_VERSION` stays `1`. **No Flyway migration** (max stays V11).

4. **Redaction (NFR14 + story 1.10 + secrets exclusion story 3.5).** The bundle excludes credentials, raw `.env` content, runner secrets, and absolute machine paths — via the **existing single** `redactionPolicyService.redact(root, classification)` pass (`:175`), which walks every text leaf including the embedded `repositoryTreeSummary` entries. **Adversarial fixture tests prove** no Linear API key (`lin_api_…`), GitHub token (`ghp_…` / `github_pat_…`), absolute machine path (`C:\Users\{name}\…`, `/Users/{name}/…`, `/home/{name}/…`), `.env` `KEY=VALUE` secret, or PEM private-key block appears in the persisted bundle even when the source data (a tree entry, README filename, manifest content, or feedback row) contains them. The persisted bundle carries **only** the container mount path (`/workspace/repo`), mount-relative paths, and the branch name — **never** a host absolute path (Trap T7).

5. **Versioning.** Each bundle is persisted with the monotonic `contextBundleVersion` per (workflowRun, stage) already assigned by `recordPort.nextContextBundleVersion(...)` (`RunnerBroker.java:357`); a re-dispatch (e.g. a `RecoveryService` retry, or 3.11/3.12 retry later) creates a new version with a freshly-summarized workspace — never overwrites; older versions remain inspectable for FR55. No new persistence column (bundle bytes live in scratch; only `contextBundleVersion` is on `runner_executions`). **No Flyway migration.**

6. **Inspection (FR55).** `WorkflowInspectionService.getContextBundleForArtifact(artifactId)` (`WorkflowInspectionService.java:811`) already returns the persisted scratch bytes **verbatim**, keyed by the artifact→runner-execution link — so it returns the full implementation-stage bundle when the artifact is `implementationPlan` or `prOutput` **with NO service code change** (mirrors 3a-2 Decision D7). The new fields surface automatically. Resolution is by the runner-execution link, independent of artifact `status` (relevant: implementation artifacts may stay `pending` — [[markavailable-has-no-production-caller]]). **Verify** the fields render via CLI `deliveryline status {runId} --include-context-bundle` (text + JSON) and the REST detail expansion path (no code change expected; assertion-only).

7. **Artifact references are stable identifiers, not payloads.** The bundle carries `approvedSpecificationReference` / `approvedImplementationPlanReference` / `artifactReferences[]` as `{artifactId, artifactType, artifactStatus, referenceAvailable, referencePath, unavailableReason}` (existing `writeArtifactReference` shape at `:496`) — runners read payloads via the file system from the mounted input dir, never embedding payload content inline. README/manifests are likewise reference-by-mount-path (story 3a-2 Decision D4), not embedded bodies; only the small `repositoryTreeSummary` is embedded (and redacted).

8. **ArchUnit boundary.** `ContextBundleService` stays in `application.runner` and depends only on application services + domain types + project-owned records (`RepositoryContextSummary`, the approvals/clarifications snapshots) — **no adapter types leak into bundle composition**; redaction goes through `RedactionPolicyService` (no bespoke regex — `CREDENTIAL_DETECTION_MUST_STAY_IN_APPLICATION_SECURITY` would fail the build). Do NOT inject the profile-gated `RepositoryWorkspaceService` into `ContextBundleService` (Trap T1) — pass the `RepositoryContextSummary` + branch as **method parameters**. `RepositoryWorkspaceService`'s `REPOSITORY_WORKSPACE_SERVICE_SCOPE` rule still passes.

9. **Test coverage.** Tests cover: (a) implementation-plan bundle composition (approved spec + PM decisions + incorporated clarifications, no approved-plan ref); (b) pr-output bundle composition (approved plan + technical feedback + repo context + branch reference); (c) bundle versioning across re-dispatch; (d) redaction adversarial fixtures (PEM / `.env` / GitHub+Linear tokens / `C:\Users\{name}` paths embedded in repo content + feedback rows); (e) schema validation rejection of a malformed implementation-stage bundle; (f) FR55 inspection returns the bundle used by a specific artifact's runner execution; (g) the no-repo execution bundle stays byte-minimal and valid (repo fields + branch absent). Plus a `github-mock`-profile **integration test** (configured repo → `prepareWorkspace` clone via local bare repo → EXECUTION dispatch → bundle carries repo context + branch → `getContextBundleForArtifact` returns it → no token / host-path leak).

10. **Fixture extension.** At least one fixture event stream entry in story 1.23's set (`deliveryline-backend/src/test/resources/fixture-event-streams/`) includes a **full implementation-stage bundle** so E2 UI tests + future E3 dev-review UI (story 3.23+) have realistic fixture data for the `--include-context-bundle` inspection path. A **new valid** runner-contracts fixture carrying the implementation-stage fields is added under `deliveryline-runner-contracts/src/test/resources/fixtures/valid/` (e.g. `context-bundle.v1.implementation-stage.valid.json`); existing valid fixtures (spec-investigation bootstrap + repo-context) stay valid; the `RunnerContractValidatorTest` corpus passes; the three FixtureEventStream contract tests stay green (extend `workflow-events-response.schema.json` `details` if needed).

11. **Logging instrumentation** (cross-cutting; see task below) — thin, field-only sub-stage + repo-context summary logging; NEVER tree contents, file bodies, feedback bodies, tokens, or host paths.

### Decisions (made by this story; rationale)

- **D1 — Sub-stage is a project-owned `ExecutionSubStage` enum passed as a method param, NOT a `RunnerStage` value.** The wire enum stays `{INVESTIGATION, EXECUTION}`; the implementation-plan-vs-pr-output semantics live in `create(...)` exactly as the spec semantics live in `createForSpecInvestigation`. Avoids fanning a new registry value into parsers/timeout maps/SQL/contracts. `subStage == null` preserves today's generic composition for the `RecoveryService` retry and all existing tests.
- **D2 — `repositoryRef` is config-resolved; do NOT widen `dispatch(...)`.** Reuse `RepositoryWorkspaceService.resolveConfiguredRepositoryRef()` (3a-2 D2, 1:1 pilot). `ticketRepositoryMappingVersion` stays the `config:<repoKey>@1` marker. Resolve internally in the broker for EXECUTION (mirrors the INVESTIGATION branch) — no new dispatch caller churn.
- **D3 — PM decisions + clarifications ride `priorFeedbackReferences` (distinct `kind`s), not new top-level fields.** The array already exists, `kind` is free-form `minLength:1`, and `createForSpecInvestigation` already uses `kind="spec.rejection"`. Use `spec.approval` / `spec.rejection` / `implementationPlan.rejection` / `clarification.incorporated`. This keeps the schema patch to just the two genuinely-new dedicated slots (`approvedImplementationPlanReference`, `repositoryBranchRef`), minimizing the v1 surface.
- **D4 — The broker derives the sub-stage from run state.** No live caller passes a sub-stage (3.11/3.12 deferred). Derive `PR_OUTPUT` when an approved `IMPLEMENTATION_PLAN` artifact exists for the run, else `IMPLEMENTATION_PLAN`. When 3.11/3.12 land they can pass it explicitly (additive). This is the dormant-seam-compatible default — document the coupling note à la 3.9 OQ-2.
- **D5 — Additive optional schema patch, no version bump, no Flyway.** Two new optional `properties`; `schemaVersion const:1`; `required` unchanged. ### Traps (wiring hazards — each maps to a memory or a verified code fact)

- **T1 — Do NOT inject the profile-gated `RepositoryWorkspaceService` into the unconditional `ContextBundleService`** ([[unconditional-service-needs-profile-gate]]). Pass a plain `RepositoryContextSummary` + branch string as method params; the broker (which holds the nullable service via `ObjectProvider`) owns the gating. (Same as 3a-2 T1.)
- **T2 — Adding `ClarificationReadPort` IS a constructor change to a two-ctor bean** ([[two-public-constructors-need-autowired]], [[docker-adapter-ctor-dep-fans-out]]). ### Logging Requirements (project-wide standard)

Every story is expected to leave the touched services observable enough to debug a production incident without re-deploying. This is enforced via the "Logging instrumentation" task above.

- **Framework:** SLF4J + Logback (Spring Boot default). No `System.out`, no `printStackTrace()`. ADR `0019-structured-logging` governs format.
- **Surface = `ContextBundleService.create` + the broker's EXECUTION repo-context branch.** `INFO` lifecycle (sub-stage chosen, repo resolved/embedded, bundle ok with `priorFeedbackCount`/`repoContextPresent`/`approvedPlanPresent`), `WARN` recoverable (no repo resolved when expected, approved-plan missing at pr-output, empty approval/clarification read), `ERROR` only for unhandled failure. `DEBUG` per-entry detail.
- **Required context keys:** `correlationId`, `workflowRunId`, `runnerExecutionId`, `subStage`, `repositoryRef`, `contextBundleVersion` — via MDC where the broker scopes it.
- **Forbidden:** tree contents, README/manifest/feedback/clarification bodies, host absolute paths, GitHub/Linear tokens, secrets, raw PII. Route any uncertain content through the redaction path before logging.
- **Test contract:** new logging surfaces pinned by at least one focused test (list-appender or `OutputCaptureExtension`) including a negative assertion that no token / host path is serialized.
