# Story 4.9: `RecoveryService.classifyFailure` + Failure Taxonomy Registry Management

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Workflow Owner classifying a failed run for cross-run pattern analysis (Growth-stage analytics per PRD § Growth Features),
I want `RecoveryService.classifyFailure(workflowRunId, taxonomyValue, actor, idempotencyKey)` that applies a governed failure-taxonomy classification, plus governance over the taxonomy registry itself (additions, deprecations, semantic-stability rules),
so that FR37 + FR38 (workflow owners can apply + review a governed failure taxonomy) are wired and NFR33 (failure-taxonomy values used on historical runs remain interpretable if the taxonomy changes later) is upheld.

## Context & Central Reconciliation (READ FIRST)

**This is the NINTH story of Epic 4 and the LAST of the "Recovery Service Extensions" slice (4.5–4.9). It is a BACKEND-ONLY application-service story: add `classifyFailure(...)` to the existing `RecoveryService`, a NET-NEW `FailureTaxonomyValue` registry enum with deprecation semantics, a Flyway migration (3 columns on `workflow_runs` + widen the `recovery_actions.action_type` CHECK), a `recovery.failureClassified` audit event, a `recovery_actions` row (`action_type='classify_failure'`), a `classify_failure` allowed-action, a `classify_failure` always-safe recommendation, a new inspection read surface, and an ADR governing taxonomy stability. ## Dev Notes

### Relevant architecture patterns and constraints

- **`RecoveryService.reconcile` (`:974-1114`) + `performReconcilePrep` (`:1315-1411`) are the structural templates — then subtract.** Copy: MDC scope → key validation → replay pre-check (actionType-guarded, **before** input validation) → input parse → run read + state guard → locate triggering event → `REQUIRES_NEW` prep tx (append event + insert `recovery_actions`) → return. **Subtract:** the `workflowCommandService.<transition>` call, the post-commit side-effect block, the `resultStatusTransactionTemplate` / `markSucceeded` flip, the `INTERNAL_ERROR` escalation, and the entire sealed-command fan-out. **Add:** the `applyClassification` column write as the FIRST statement in the prep tx (its returned prior value feeds `details.priorTaxonomyValue`).
- **⚠️ The `actionType` replay guard is not optional.** `resume` shipped without it and a code review caught that a prior `retry`/`takeover` row under the same idempotency key echoed back as a false resume replay (`RecoveryService.java:701-717` is the fix). `retry`'s Step 1 still has the gap. Classify's guard must be present from day one, and its unit test must seed a `resume`-typed prior snapshot to prove it.
- **⚠️ No `@DynamicUpdate` on `WorkflowRunEntity`.** This is why the three new columns must stay off the entity (R7) — a full-row UPDATE from a stale entity in a concurrent transition would null them. `build_fix_loop_count` / `lint_fix_loop_count` / `split_proposal_loop_count` are the live precedent for `workflow_runs` columns owned by a JDBC port rather than the entity.
- **`recommend(...)` runs only for `FAILED`** (`RecommendationService.java:90-95`), so AC10's "always safe" and AC3's `FAILED`-only gate agree without extra guarding — but the drift-downgrade loop (`:158-171`) actively rewrites SAFE→CAUTION for every action except `reconcile`. The exemption is a real, easily-missed line of work.
- **The `recovery_actions.action_type` CHECK is the sharp edge.** `RecoveryActionPersistenceAdapter.insert` does not validate `action_type` in Java — it relies on the DB CHECK and translates only the idempotency-key unique violation (`:208-224`). An un-widened CHECK therefore surfaces as a raw `DataIntegrityViolationException` from inside the prep tx, not a typed domain error. Widen it in the migration; the real-PG IT is what proves it.
- **`WorkflowInspectionService` may depend on `application.recovery`** — it already injects `RecoveryService.describeFailure` and `RecommendationService` (`:2948-3051`, `:251-256`). Placing `WorkflowRunFailureClassificationPort` in `application/workflow/spi` (next to `WorkflowRunRejectionLoopPort`) keeps both the recovery writer and the inspection reader on a sanctioned import path.
- **Event-detail redaction.** `reasonText` is operator free-text. Route it through the same path `reconcile` uses (`details.reason` + the event's `reason` column); do not add it to a log line. The `details` JSONB has a 64 KB CHECK (`V1:65`).
