## Deferred from: code review of 1-21-github-actions-ci-tiered-pipeline (2026-05-17)

- **doctor-smoke Windows runner coverage** _(added 2026-05-18 during CI stabilization)_ — the original 1.17 AC8 matrix included `windows-latest` to exercise the `DOCTOR_DOCKER_MISSING` WARN-tolerance path (Windows runners have no Docker Desktop). With story 1.21's full-Spring-context doctor boot, the transitive bean graph (`WorkflowCommands` → services → JPA repositories) requires a real persistence layer — and Windows runners can't start the compose-managed Postgres. Doctor-smoke was collapsed to Ubuntu-only as a pragmatic unblock. Re-enabling Windows requires either: (1) decoupling doctor from the persistence bean graph (e.g., a separate Spring profile/sub-context that excludes service beans) or (2) wiring a non-Docker DataSource for Windows (HSQLDB embedded, with Flyway disabled). [`.github/workflows/ci.yml:doctor-smoke`]
- **`RedactionLayoutHolder` masks Spring startup-failure diagnostics** _(added 2026-05-18 during CI stabilization)_ — when context refresh fails before `RedactionLayoutInitializer.@PostConstruct` can wire the holder, every log message (including Spring's `LoggingFailureAnalysisReporter` output) becomes the `[redaction-pending]` sentinel. The fail-closed design is intentional (story 1.19 D1 resolution), but it makes CI failures un-diagnosable without a local repro. Fix candidate: wire the holder via `ApplicationContextInitializer` or `SpringApplicationRunListener` so it's set before any bean creation. [`deliveryline-backend/src/main/java/org/dradgo/infrastructure/observability/RedactionLayoutHolder.java`]
- **Maven dependency-cache strategy is per-job** — every tier re-resolves the same Maven dependencies (no shared warmup step). Optimization for a 9-tier pipeline; revisit when measurable cold-cache cost surfaces. Out of story scope.
- **Checkstyle uses JAR-bundled `google_checks.xml`** — `<configLocation>google_checks.xml</configLocation>` resolves from the Checkstyle JAR. Future Checkstyle version bumps will silently change the enforced rule set. Future hardening: vendor a pinned copy under `config/checkstyle/google_checks.xml`.
- **Default `actions/checkout@v4` shallow `fetch-depth: 1`** — fine for current tiers, but tiers that need git history (e.g., diff-vs-main for OpenAPI drift in story 6.9, or release-readiness tag scans in `bundled-jar-smoke`) will require `fetch-depth: 0` or a targeted unshallow step. Forward-looking concern.
- **Frontend cache uses `setup-node@v4` built-in `cache: npm` rather than `actions/cache@v4` with explicit `restore-keys`** — Task 5 sub-bullet 3 asked for `actions/cache` with `restore-keys` fallback. Functionally near-equivalent (`setup-node@v4` does cache `~/.npm` keyed by lockfile hash), low value to refactor before story 2.1 lands real frontend tooling.
