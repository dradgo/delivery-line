## Story

As a frontend developer (Decision Bar `recovery_operator` mode in story 4.22) and CLI user,
I want a REST endpoint `POST /api/v1/workflows/{workflowRunId}/pause` wired to `RecoveryService.pause` (story 4.8), plus the sibling `deliveryline operator pause` CLI command,
so that operators have a one-step manual pause — halting orchestrator dispatch and cancelling in-flight + queued runner work without taking over (which is non-reversible per story 3.25 AC9) — flowing through the standard mutation conventions (idempotency + Problem Details + OpenAPI).

## Dev Notes

### Relevant architecture patterns and constraints

- **The 4.10 `resume` method (`WorkflowController.java:2084-2161`) is the exact structural template**, committed (db72600). Copy: annotations → guard prologue → `requireWorkflowOwnerRole` → `ActorContext` build → service call → rich response `from(runId, result)` → two log lines. Pause is the CLOSEST sibling to resume (same 4-arg service-call shape, no domain field before `idempotencyKey`); it differs only in the four ways enumerated in Reconciliation 3 (`reasonText` un-`@NotBlank`, `priorState` + two counts in the response, `currentState` REQUIRED, `PAUSE_NOT_APPLICABLE` error).
- **Two-endpoint trap (service layer).** `WorkflowCommandService.pauseWorkflow` (thin, transition-only, called INTERNALLY by the rich service) vs `RecoveryService.pause` (rich). 4.13 ships one endpoint wired to the rich path — Reconciliation 2. Wiring the thin path silently skips runner cancellation + audit + the `PAUSABLE_SOURCE_STATES` gate, leaving a `Paused` run whose runners keep getting dequeued and reaped into `Failed`.
- **`ActorContext` lives in `org.dradgo.application.artifact`**, not `application.recovery`. Its canonical ctor rejects a blank `actorIdentity`/null `actorType` — safe because `localActorIdentityResolver.resolve(...)` falls back to `local-operator` and `ActorType.HUMAN` is hard-coded.
- **RBAC is audit-only.** `requireWorkflowOwnerRole` is a request-shape check; the controller never returns 401/403. The resolved actor identity is stamped on the audit trail. Note `requireWorkflowOwnerRole` throws `INVALID_REVIEWER_ROLE_FOR_ENDPOINT` for a non-blank wrong role; a BLANK `role` is caught by `@NotBlank` bean-validation FIRST as `INVALID_COMMAND_PAYLOAD` (the 4.10 debug-log lesson — split the test accordingly).
- **The `pause_workflow` allowed-action is state-gated** to the 8 `PAUSABLE_SOURCE_STATES` for `ROLE_WORKFLOW_OWNER` (4.8 AC10) — the controller adds NO state check of its own; the `PAUSABLE_SOURCE_STATES` gate inside the service is the enforcement (`PAUSE_NOT_APPLICABLE`). The allowed-actions list is a read-model concern, NOT a service guard.
- **Idempotency: two surfaces, you touch neither.** `recovery_actions.idempotency_key` unique key (outer) + `executeIdempotent` inside `WorkflowCommandService.pauseWorkflow` (inner). `RecoveryService.pause`'s replay pre-check guards `actionType == pause` (`:1154`) — cross-action key reuse is `IDEMPOTENCY_KEY_CONFLICT`, not a false replay. The fingerprint treats `reasonText` as identity ([[story-4-8-recovery-service-pause]] Reconciliation 9), so a same-key/different-reason call is a conflict — and `MISSING_REASON_TEXT` fires BEFORE the replay check (Reconciliation 8) because a blank reason has no fingerprint identity. The controller passes the raw header + reason through and lets the service decide.
- **No `WorkflowCommand` permit, no fingerprint arm, no `EXPECTED_PERMITS` edit.** `PauseWorkflowCommand` was already added to the sealed hierarchy by 4.8. This story adds only REST DTOs, which are not `WorkflowCommand`s.

### Logging Requirements (project-wide standard)

- **Framework:** SLF4J + Logback. No `System.out` / `printStackTrace()`.
- **Where to log:** REST entry (`INFO`), REST success (`INFO`), role rejection (`WARN`, inside the shared helper), CLI completion (`INFO`, success + failure with the typed `DomainErrorCode`). The recovery-service log surface is already pinned by 4.8's `RecoveryLoggingContractTest` — do not duplicate it in the adapter.
- **Required context keys:** `correlationId`, `workflowRunId`, `actorIdentity`, plus `recoveryActionId` + `priorState` + the two cancellation counts on success. MDC `correlationId` is stamped by `CorrelationIdFilter` (REST) and `pushCorrelation` (CLI).
- **Forbidden:** `reasonText` prose (log its length only), idempotency-key values, secrets, tokens, PII. The `priorState`/`currentState` values ARE loggable (bounded governed enums).
- **Test contract:** `ListAppender` pins on the `WorkflowController` logger for entry/success/rejection.
