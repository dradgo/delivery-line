# Story 2.7: Tri-Pane Application Shell with Artifact-Primacy Layout Rules

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a **PM, developer, or workflow owner**,
I want **a consistent tri-pane application shell — left navigation rail + central main review pane + right supporting context panel — with artifact-primacy layout rules that keep the main pane as the visual anchor**,
so that **every run view presents workflow truth in a stable, predictable layout where the artifact dominates and side panels support without competing**.

## ⚠️ Read first — scope, sequencing, and what this story is NOT

**Scope in one line:** build the *structural shell* — the three-region tri-pane layout, the landmarks, the artifact-primacy collapse invariant, the responsive skeleton, the left-rail run-identity region, and the right-panel composition slot. It is the host that every later Epic-2 composite plugs into. **Frontend-only. No backend changes.**

This story builds the **skeleton**, not the contents. The composites that fill it ship later:

| Surface | Built by | 2.7's job |
|---|---|---|
| Run / Review Queue Item, Queue shell states | 2.15, 2.20 | the queue route renders in the main pane; 2.7 ships the pane, not the queue UI |
| Run Context Strip | 2.16 | 2.7 ships the **right-panel slot** it plugs into — not the strip |
| Artifact Review Panel (ARP) | 2.17 | 2.7 ships the **main pane** the ARP later occupies — not the ARP |
| Clarification Region (sidebar variant) | 2.18 | plugs into the right-panel slot — not built here |
| Approval / Decision Bar | 2.19 | not built here |
| Empty / Loading / Error state components, nav helpers, breadcrumb stack | 2.22 | 2.7 ships the shell that *hosts* them; 2.22 AC8 explicitly says the global catastrophic-error overlay "lives in the AppShell from story 2.7" — reserve a place for it, do not build it |
| Full WCAG 2.1 AA audit (axe-core, contrast, screen-reader checklist) | 2.25 | 2.7 ships correct landmarks + focus baseline; the audit is 2.25 |
| Full responsive breakpoint matrix, Tailwind breakpoint aliases, `RESPONSIVE.md` ADR, mobile sticky decision-bar | 2.26 | 2.7 ships the responsive *structure* + `useResponsiveLayout` — see TRAP 3 |

If you find yourself building a composite, a queue, an artifact renderer, a decision bar, or Compare Mode — **stop**. This story ends at the empty shell with documented slots.

## Acceptance Criteria

1. **Given** `src/features/workflows/AppShell.tsx` (or equivalent), **Then** the shell renders a three-region layout: left navigation rail (fixed width, queue/state navigation), central main review pane (flex-grow, houses Artifact Review Panel in stories 2.17+), right supporting context panel (fixed width, houses blockers/open questions/artifact metadata/history).
2. **Given** artifact-primacy rules (UX-DR5), **Then** the central main pane's minimum width is configured so that if viewport shrinks, the **right context panel collapses before the main pane narrows** — a layout test asserts this by shrinking viewport and checking main-pane width remains at or above the minimum.
3. **Given** the left navigation rail, **Then** it includes stable placement for: primary nav (queue home), current run identity (when inside a run), global app status indicator — and is keyboard-focusable with semantic `<nav>` landmark.
4. **Given** the right context panel, **Then** it can host (via slot/composition): Run Context Strip (story 2.16), Clarification Region (story 2.18) in sidebar variant, blocker list, artifact metadata, run history timeline — composites plug into the slot; the shell does not hard-code content.
5. **Given** responsive behavior (story 2.26 details), **Then** at tablet breakpoints the right panel becomes togglable (slide-out or drawer), and at mobile the tri-pane collapses to single-column with progressive disclosure — preserving artifact-primacy priority.
6. **Given** the visual language per UX-DR5, **Then** panel borders are restrained (1px with subtle token colors), background surfaces use neutral palette from story 2.3, and the main pane has slightly more vertical whitespace headroom than side panels to signal visual primacy.
7. **Given** landmarks and semantics for accessibility (story 2.25), **Then** the shell uses `<nav>`, `<main>`, and `<aside>` landmarks with labeled regions (`aria-label="Workflow navigation"`, `aria-label="Supporting context"`) — keyboard users can skip between regions with standard landmark navigation.
8. **Given** the "hybrid coherence rules" (UX spec § Hybrid Coherence Rules), **Then** the tri-pane shell remains structurally stable across normal review and Compare Mode (Epic 4) and clarification states — it is not a "mode switch"; the same shell hosts different panels per state.
9. **Given** scroll isolation, **Then** each region scrolls independently — the main pane's long artifact reading doesn't scroll the nav rail or context panel — supporting long-form spec inspection without losing context.
10. **Given** the "artifact primacy is a hard rule" directive (UX-DR5), **Then** a documented layout ADR under `src/features/workflows/LAYOUT.md` states: "When layout pressure increases, context panels collapse before the main pane; compare mode (Epic 4) is the only state where main pane may share primacy with a second artifact view." This ADR is referenced by future story ACs to prevent drift.
11. **Given** correlation with CLI `deliveryline status` output (story 1.15), **Then** the shell's "current run identity" region displays the same identifiers (runId, current state, current actor, last transition timestamp) that CLI `status --format=json` returns — proving UI is a faithful view of backend state, not an independent source of truth.

## 🚨 Traps & disasters this story must prevent

### TRAP 1 — Mount the shell in `__root.tsx`; de-duplicate the route `<Container>` wrappers

The shell wraps the router `<Outlet />` exactly once — replace `RootLayout`'s bare `<Outlet />` (`src/routes/__root.tsx`) with the shell, where the central `<main>` pane contains the `<Outlet />`. **But every leaf route currently renders its own `<Container className="py-8">`.** After the shell provides the main pane, those wrappers double-pad and risk **two `<main>` landmarks per page** (an a11y failure). Audit and adjust the 4 route components (`routes/workflows/index.tsx`, `routes/workflows/$workflowRunId/index.tsx`, `routes/workflows/$workflowRunId/artifacts/$artifactId.tsx`, and the `routes/-states/DeadEndState.tsx` usages) so the shell owns the single `<main>` + base padding and routes render plain content into it. There must be exactly **one** `<main>` on the page.

### TRAP 2 — The right panel is a SLOT. Do not build the composites that fill it.

AC4 lists Run Context Strip (2.16), Clarification Region (2.18), blocker list, artifact metadata, run history — **none of those are built here.** They do not exist yet. 2.7 ships the **right `<aside>` with a documented composition slot mechanism** and an empty/placeholder state. If you build a Run Context Strip, you have done story 2.16's job and will collide with it. Same for the queue UI (2.15/2.20) and the ARP (2.17) — the shell provides empty regions.

### TRAP 3 — Responsive overlap with story 2.26: build the structure, not the full matrix

2.26 ("Responsive Design") owns: the explicit Tailwind breakpoint aliases (2.26 AC1), the full collapse matrix + tests (2.26 AC2/AC12), the mobile sticky decision-bar (2.26 AC3/AC7), and the `src/features/workflows/RESPONSIVE.md` ADR (2.26 AC10). **2.7 AC5 says "responsive behavior (story 2.26 details)"** — so 2.7 builds the responsive *structure* the shell needs to function across breakpoints, and **creates the `useResponsiveLayout()` hook** (the shell cannot collapse without it; 2.26 then hardens it + adds the full test matrix — same way story 2.6 stood up the minimal Vitest runner that 2.27 extends). Do **NOT**: write `RESPONSIVE.md`; redefine Tailwind `screens` (Tailwind's default `md`=768 / `lg`=1024 already match the tablet/desktop boundaries — 2.26 formalizes the aliases); build the mobile sticky decision-bar. Document the 2.7↔2.26 split in `LAYOUT.md`.

### TRAP 4 — Artifact primacy is a HARD layout rule, and jsdom cannot test computed width

AC2's invariant (right panel collapses before the main pane narrows) is **load-bearing** — it must be encoded structurally in CSS (the main `<main>` carries a real `min-width`; the right `<aside>` is the element that shrinks/collapses under pressure, driven by `useResponsiveLayout`). **jsdom has no layout engine** — `getBoundingClientRect()` returns zeros, so a true computed-pixel-width assertion is impossible in Vitest. The "layout test" (AC2) therefore asserts the **structural contract**: the `<main>` element carries the min-width class/token; driving `useResponsiveLayout` via a mocked `matchMedia` to the tablet/mobile breakpoint makes the right panel render as a drawer/collapsed (not inline) while `<main>` keeps its min-width class. The true pixel-level computed-layout assertion defers to Playwright in story 2.26 AC12 / 2.27 — say so in `LAYOUT.md` and the test comments.

### TRAP 5 — Run identity comes from TanStack Query, never `useState`

The left-rail run-identity region (AC3/AC11) reads `currentState`/`currentActor`/`lastTransition` from `useWorkflowDetail` — the backend is the single source of truth (architecture.md:761-766, 800-805; story 2.6 invariant). Do **not** copy workflow state into `useState`. Because hooks cannot be conditional, render the identity region as a child component `<RunIdentityRegion workflowRunId={id} />` mounted only when a `workflowRunId` route param exists — the child unconditionally calls `useWorkflowDetail`.

### Architecture-prescribed rules (architecture.md)

- **Server state = TanStack Query; backend is the single source of truth** (761-766, 800-805). The run-identity region reads `useWorkflowDetail` — no workflow state in `useState` (TRAP 5). The `Consistency Drift Prevention` anti-patterns (825-836) name "store server workflow state as independent frontend state" explicitly.
- **Frontend scope guardrails** (483-489): backend-reported state drives the UI; no frontend-only workflow transitions; no frontend interpretation of approval eligibility. The shell *displays* state; it never computes it.
