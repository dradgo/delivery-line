## Story

As a Developer joining the pilot,
I want a `docs/execution-walkthrough.md` that explains the Epic 3 surface end-to-end — what happens when the workflow dispatches agent work, how to read the implementation plan and PR/output artifacts, how developer review + takeover preserve context, how the queue + worker pool work — with annotated diagrams,
so that I can complete a developer-side review on my first pilot run unaided (NFR42 satisfied for the developer persona) — and the takeover non-reversibility expectation (per story 3.25 AC9) is set explicitly rather than discovered as a surprise.

## Scope Decisions (read first — these resolve epic-vs-reality tensions)

**This is a PURE DOCUMENTATION story. It produces exactly one new markdown file (`docs/execution-walkthrough.md`), one README "Quick links" entry, and a small set of `docs/glossary.md` additions. It touches ZERO application / frontend / backend code, no tests, no CI workflow logic.** The walkthrough must describe the surface **exactly as it is implemented today** — every label, route, state name, config key, CLI command, and message below was verified against the live `deliveryline-backend` / `deliveryline-frontend` source and `application.yml`. **The epic's AC text drifts from reality in several places; the reconciliations (R1–R15) below pin the doc to the shipped code. Where epic AC wording and the live code disagree, the live string wins.** Quote real strings verbatim — a walkthrough that names a button, command, or config key the developer can't find is worse than no walkthrough.

This story is the **direct twin of story 2.29** (the PM-loop walkthrough doc-increment). Model the new doc's house style, validator-placeholder line, diagram approach, glossary discipline, and README-as-index decision on `2-29-pm-loop-walkthrough-documentation-increment.md` and the two existing walkthroughs it produced/extended.
