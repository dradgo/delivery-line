# Story 3.33: RepositoryHostAdapter Abstraction (Extract from GitHubAdapter)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **Story type:** Backend architectural refactor (epic-3b). **No wire/REST/CLI surface change is in scope** — this extracts a vendor-neutral `RepositoryHostAdapter` port from the existing GitHub-shaped `GitHubAdapter` (story 3.13) so a future repository host (Bitbucket, GitLab, Gitea, Azure DevOps Repos) is a one-interface, one-contract add. The existing GitHub behavior must be **byte-for-byte preserved** (parity tests prove it).
>
> **This is the symmetric GitHub sibling of story 3.32 (TicketSourceAdapter from LinearAdapter).** 3.32 is already `ready-for-dev`. Keep the two abstractions **structurally symmetric** — capabilities record, leak rule, parity foundation contract, extension-contract doc, ADR — so a future reader sees one pattern, not two. Where 3.32 made a decision (opaque vendor token, keep-profiles-add-`kind`, governed-shape-preserved, log-don't-event), this story makes the GitHub-side equivalent unless the live code forces otherwise.
>
> **⚠ READ THE RECONCILIATIONS FIRST.** The ACs below are copied verbatim from `epic-03-agent-execution.md §Story 3.33`. They describe an *idealized* port shape that **does not match the live code** in several load-bearing ways. The live contract is authoritative. Each ⚠ RECONCILE marker points at the live truth; the full reconciliation table is in Dev Notes §"The reconciliations that prevent disasters". **Do not implement the AC text literally where a ⚠ marker contradicts it.**

## Story

As an architect preparing for future repository-host extension (Bitbucket, GitLab, Gitea, Azure DevOps Repos),
I want the existing `GitHubAdapter` port (story 3.13) renamed/refactored to a vendor-neutral `RepositoryHostAdapter` interface — with `GitHubMockAdapter` + `GitHubRealAdapter` becoming concrete implementations alongside future `BitbucketAdapter`/etc. — plus a documented extension contract,
so that adding a new repository host in a future version requires implementing one interface against one documented contract, not refactoring a GitHub-shaped port.

## Acceptance Criteria

> ACs verbatim from the epic. **⚠ RECONCILE** markers point at the live contract the AC text predates; the live contract wins — see Dev Notes.

1. **Given** the `application.integration.repohost` package, **Then** the generic `RepositoryHostAdapter` interface exists with vendor-neutral domain-shaped methods: `getRepositoryByRef(RepositoryRef ref) → Optional<Repository>`, `getPullRequestByRef(PullRequestRef ref) → Optional<PullRequest>`, `getBranchByRef(RepositoryRef repo, String branchName) → Optional<Branch>`, `createPullRequest(RepositoryRef repo, String sourceBranch, String targetBranch, String title, String body) → PullRequest`, `updatePullRequest(PullRequestRef ref, String body) → PullRequest`, `commentOnPullRequest(PullRequestRef ref, String body) → CommentResult`, `getCapabilities() → RepositoryHostCapabilities` — all parameters and return types use vendor-neutral domain models defined in `domain.integration.repohost`. **⚠ RECONCILE:** the live port (`GitHubAdapter`, `application/integration/github/GitHubAdapter.java`) uses bare `String` refs everywhere and has **`createPullRequest(String repoRef, String branch, String title, String body)` — four params, NO explicit `targetBranch`** (the base/target branch is resolved internally to the repo default branch), and **`void commentOnPullRequest(String prRef, String body)`** (no `CommentResult`). See Dev Notes §R1 (the `targetBranch` param — OQ-2), §R2 (`RepositoryRef`/`PullRequestRef` are net-new), §R3 (`CommentResult` — OQ-3).
2. **Given** the existing `GitHubAdapter` port from story 3.13, **Then** it is renamed/refactored such that `GitHubAdapter` is no longer a separate port; `GitHubMockAdapter` + `GitHubRealAdapter` (stories 3.13, 3.14) now implement `RepositoryHostAdapter` directly. Migration note in `docs/adr/0008-repository-host-abstraction.md` records the change. **(ADR number 0008 is free — existing ADRs are 0001–0004, 0006, then 0019–0023; 3.32 claims 0007, this story claims 0008.)**
3. **Given** capability detection, **Then** `RepositoryHostCapabilities` exposes typed booleans: `supportsDraftPullRequests`, `supportsPullRequestComments`, `supportsBranchProtection`, `supportsForkPushes`, `supportsRequiredStatusChecks` — consumers check capabilities before invoking optional features. **⚠ RECONCILE:** `RepositoryHostCapabilities` is **net-new** (no capabilities type exists today). The only optional-feature surface a consumer could gate today is `commentOnPullRequest` (gate behind `supportsPullRequestComments`); the AC10 example "`supportsDraftPullRequests=false` → no draft flag" is **vacuously satisfiable** because the live `createPullRequest` has **no draft parameter at all** and no production caller asks for a draft PR. See Dev Notes §R5 (OQ-5).
4. **Given** vendor-neutral domain types in `domain.integration.repohost`, **Then** `RepositoryRef`, `Repository`, `PullRequestRef`, `PullRequest`, `Branch`, `CommentResult`, `RepositoryHostCapabilities` are defined with no GitHub-specific fields (no `node_id`, no GitHub-specific URL formats); vendor-specific data lives only inside the implementing adapter. **⚠ RECONCILE — this is OQ-1, the #1 decision.** The live ref strings are GitHub-shaped: a repo ref is `"owner/repo"` and a PR ref is `"owner/repo#number"` (parsed by regex inside `GitHubRealAdapter`; emitted as `prRef` on `GitHubPullRequest`). A strictly-neutral `PullRequestRef` cannot encode `owner/repo#number` as a typed field — but it **can** carry it as an **opaque, vendor-uninterpreted string token** (only the GitHub impl parses it). Mirror 3.32's `sourceStatusId` opaque-token resolution. **Also note:** the live domain records (`GitHubRepository`/`GitHubPullRequest`/`GitHubBranch`) currently live in the **application** layer (`application.integration.github`), not the domain layer — this story moves+renames them into `domain.integration.repohost` (framework-free records). See Dev Notes §R2 + §R6.
5. **Given** Spring profile-based wiring, **Then** `application.yml` `deliveryline.integration.repo-host.kind=github` (default) selects the implementation; future kinds (`bitbucket`, `gitlab`, `gitea`, `azure-devops`) plug in by adding a new implementation + a profile entry. **⚠ RECONCILE:** selection today is via mutually-exclusive Spring **profiles** (`github-mock` / `github-real`), asserted in `GitHubConfiguration.assertExclusiveGitHubProfile`. GitHub config lives under `deliveryline.github.*` (`GitHubProperties`). **Add** the `kind` selector key (default `github`); **keep** the profile mechanism + `deliveryline.github.*` keys (renaming them is an ops-breaking change out of scope). Mirror 3.32 R4 (OQ-4). See Dev Notes §R4.
6. **Given** a documented extension contract `docs/integrations/repository-host-extension-contract.md`, **Then** it specifies: every method's expected behavior, error classification per `IntegrationFailureCategory`, idempotency guarantees (especially for `createPullRequest` which must be idempotent by `(repo, sourceBranch, targetBranch)` per story 3.14 AC4), redaction-on-egress requirements, capability declaration, auth-model documentation (token vs OAuth vs basic auth — per-vendor), branch-naming compatibility (e.g., Bitbucket forbids `:` in branch names; the deterministic naming convention from story 3.9 AC2 must work across all supported hosts), configuration-key conventions, and testing requirements (parity test against the same fixture scenarios used for GitHub). **⚠ RECONCILE — idempotency key:** the live idempotency key is `(repoRef, sourceBranch)` (the mock's `CreatePullRequestKey(repoRef, branch)`; the real adapter's open-PR search `head=owner:branch&base=defaultBranch&state=open`). It already includes the target via the internally-resolved base branch. If OQ-2 keeps the 4-param shape, document the key as `(repo, sourceBranch)` with `targetBranch = repo default branch`; if OQ-2 adds the param, the key becomes the literal `(repo, sourceBranch, targetBranch)`. **Branch-naming is already Bitbucket-safe:** story 3.9's `RepositoryWorkspaceService.branchName()` builds `deliveryline/{slug}/stage-{runIdShort}` using `/` separators and sanitizes the slug to `[A-Za-z0-9._-]` — **no `:` is ever produced** (document this as the cross-host-compatible convention). Mirror the structure of `docs/integrations/linear-completion-sync.md`; reference the GitHub ADRs 0020/0021/0022.
7. **Given** ArchUnit boundary, **Then** `RepositoryHostAdapter` lives in `application.integration.repohost`; concrete implementations in `adapters.integration.repohost.{kind}`; domain types in `domain.integration.repohost`; ArchUnit asserts no vendor-specific types (GitHub REST DTOs, Bitbucket types) leak through the port. **⚠ RECONCILE:** generalize the existing `GITHUB_TYPES_MUST_NOT_LEAK_THROUGH_PORT` rule (in `architecture/ArchitectureRuleCatalog.java#672-686`) to target `org.dradgo.application.integration.repohost..` and keep banning `org.kohsuke.github..` / `com.github..` / `org.springframework.web.client..` / `org.springframework.http.client..`. **Leave 3.32's `LINEAR_TYPES_MUST_NOT_LEAK_THROUGH_PORT` (→ ticketsource) untouched** — that story owns the Linear equivalent. Add residence rules for the three new repohost packages. **There is NO existing GitHub PR-comment posting restriction rule** (unlike Linear's `ONLY_ORCHESTRATION_AND_CLI_MAY_POST_LINEAR_COMMENT`) — do **not** invent one (GitHub comments aren't governed-fingerprinted the way Linear's are). ArchUnit runs in **Failsafe**, not Surefire (memory [[archunit-runs-in-failsafe-not-surefire]]).
8. **Given** existing consumers (story 3.9 `RepositoryWorkspaceService`, story 3.15 `IntegrationLinkService.linkGitHubPr`, runner orchestration in stories 3.11/3.12), **Then** they are refactored to depend on `RepositoryHostAdapter`. Method names like `linkGitHubPr` should be renamed to `linkPullRequest` in this story to keep the naming vendor-neutral; service method renames trigger updates to story 3.15's call sites. **⚠ RECONCILE:** the live direct adapter consumers are `RepositoryWorkspaceService` (field inject — `getRepositoryByRef`/`getPullRequestByRef`/`createPullRequest`/`updatePullRequest`) and `IntegrationLinkService` (`ObjectProvider<GitHubAdapter>` — `getPullRequestByRef`/`getBranchByRef`). `RunnerBroker`, `WorkflowOrchestrationService`, and `TechnicalApprovalService` touch the adapter **only via `IntegrationLinkService`** (no direct dep). The CLI does **not** touch the adapter. `linkGitHubPr` → `linkPullRequest` is the mandated rename; its sole production call site is `RunnerBroker.linkGitHubPrBestEffort` (+ tests + `IntegrationLinkGitHubPrFoundationContract`). See Dev Notes §"Source-tree map".
9. **Given** git-protocol independence, **Then** `RepositoryWorkspaceService` (story 3.9) clones via standard git HTTPS — independent of which `RepositoryHostAdapter` is active; the host adapter handles only the API-layer concerns (PR creation, branch metadata via API, comment posting), while git operations (clone, push) use vendor-agnostic git CLI/library. **✅ ALREADY TRUE:** `RepositoryWorkspaceService` clones via the `GitCommandPort` SPI (`git.cloneRepository(...)`) using `repository.url()` — the GitHubAdapter is used only to *resolve* the repo/PR metadata, never to clone. No change needed to satisfy AC9; just preserve the decoupling through the rename.
10. **Given** the foundation gate (story 1.23) widening, **Then** the gate now asserts: `RepositoryHostAdapter` interface exists, current GitHub implementations satisfy it, capability declaration is honored by consumers (e.g., if `supportsDraftPullRequests=false`, `createPullRequest` is invoked without the draft flag). **⚠ RECONCILE:** add a new `*FoundationContract` + a `@Nested` delegate in `FoundationGateVerificationTest` mirroring the `GitHubMockVsRealParityFoundationContract` pattern (current GitHub parity is **Contract #11**, link is **#12**; 3.32 adds **#13**; this story adds **#14** — see Dev Notes §"Foundation-gate numbering"). The "capability honored by consumers" clause is **vacuously satisfied** for draft PRs (no draft path exists); assert instead (a) both impls `implements RepositoryHostAdapter`, (b) happy read returns a neutral type in mock + (MockRestServiceServer-stubbed) real, (c) a classified failure surfaces the same `IntegrationFailureCategory` in both, (d) `getCapabilities()` returns the declared GitHub set in both.
11. **Given** the test suite, **Then** tests cover: existing GitHub scenarios pass against `RepositoryHostAdapter` interface (refactor preserves behavior), capability-driven graceful degradation, config-driven implementation selection, no vendor-specific type leakage at port boundary, extension-contract documentation completeness, deterministic-branch-naming compatibility (a synthetic test asserts the naming convention from story 3.9 AC2 produces strings valid in GitHub + a documented Bitbucket-compatibility variant). **⚠ RECONCILE:** "capability-driven graceful degradation" has no live unconditional consumer to degrade (see AC3/AC10 reconcile) — implement it as a focused unit test that injects a mock with `supportsPullRequestComments=false` and asserts the (single defensible) comment-guard skips + logs, OR keep it as a capability-declaration assertion if no guard is added. The branch-naming compatibility test asserts `RepositoryWorkspaceService.branchName(...)` output matches both a GitHub-valid and a Bitbucket-valid (`:`-free) regex.

## Dev Notes

This is a **backend-only** structural refactor. The entire surface is `deliveryline-backend/` + `docs/`. **No `openapi.json` / REST DTO / frontend / wire-enum change is in scope** — the abstraction is purely internal to the application/adapters boundary, and the durable `github_pr` integration-link `integrationType` string + DB shape are unchanged. ### The reconciliations that prevent disasters

1. **R1 — `createPullRequest` is 4-param today; AC1/AC6 want an explicit `targetBranch` (OQ-2).** Live: `GitHubPullRequest createPullRequest(String repoRef, String branch, String title, String body)`. The base/target branch is resolved internally (real: the open-PR search uses `base=<default branch>`; mock: idempotency key is `(repoRef, branch)`). AC1's idealized signature adds `String targetBranch`, and AC6 wants idempotency by `(repo, sourceBranch, targetBranch)`. **Recommended:** add the explicit `targetBranch` param — the sole caller `RepositoryWorkspaceService` already resolves `repository.defaultBranch()`, so passing it **preserves today's behavior** (target stays the default branch) while making the port honest for hosts where base ≠ default. Extend the mock's `CreatePullRequestKey` to 3-tuple and pass `targetBranch` as the real adapter's `base=`. **Alternative (minimal churn):** keep 4-param, document `targetBranch = default branch`. [Source: `adapters/integration/github/GitHubRealAdapter.java#182-240,342-363`, `GitHubMockAdapter.java#111-146,321`]
2. **R2 — `RepositoryRef`/`PullRequestRef` are net-new; everything is `String` today.** The port, `GitHubRepository.repoRef`, `GitHubPullRequest.prRef`, `IntegrationLink.externalRef`, and the workspace branch logic all use bare `String` (e.g. `"owner/repo"`, `"owner/repo#42"`). Introduce thin value records and thread them through the port + the two direct callers (`RepositoryWorkspaceService`, `IntegrationLinkService`). **Persistence (`integration_links.external_ref`) stays a `String`** — map `.value()` at the persistence boundary; do not migrate the DB column. [Source: `application/integration/github/GitHubAdapter.java`, `GitHubPullRequest.java`, `IntegrationLinkService.java`]
3. **R3 — The comment method is a raw string + `void` today (OQ-3).** Live: `void commentOnPullRequest(String prRef, String body)`. Unlike Linear's *governed* comment (which carries a fingerprint + classification and must keep its shape), GitHub's comment is already a plain body — so AC1's `commentOnPullRequest(PullRequestRef, String) → CommentResult` is a clean fit. Change `String prRef` → `PullRequestRef` and `void` → `CommentResult` (`POSTED`/`SKIPPED_DUPLICATE`). The mock dedups on `(prRef, fingerprint(body))` → `SKIPPED_DUPLICATE`; the **real adapter does not dedup server-side** → always `POSTED` (document this asymmetry in the extension contract). The real adapter must keep routing `body` through `RedactionPolicyService` (`SHAREABLE_REDACTED`) on egress (AC6). **No production code calls `commentOnPullRequest` today** — it is a dormant port method, so the return-type change is low blast-radius. [Source: `GitHubMockAdapter.java#170-198`, `GitHubRealAdapter.java#264-285`]
4. **R4 — The neutral ref format is GitHub-shaped — OQ-1, the #1 decision (AC4).** A repo ref is `"owner/repo"`; a PR ref is `"owner/repo#number"` (regex-parsed in `GitHubRealAdapter`, emitted as `prRef`). AC4 forbids "GitHub-specific URL formats" on the neutral types. A naive neutral type can't encode `owner/repo#number` as a typed field — but `RepositoryRef(String value)` / `PullRequestRef(String value)` can carry it as an **opaque, vendor-uninterpreted token**: only the GitHub impl parses it; neutral consumers treat it as a key. This is the exact analog of 3.32's `sourceStatusId` opaque-token resolution and is a defensible reading of "no GitHub-specific URL formats" (an opaque string ≠ a typed GitHub DTO). **Watch-item:** `IntegrationLinkService.assertArtifactPrLinkMatches` is GitHub-format-aware (it format-checks `owner/repo#number`) and `prRef` validation has historically drifted between `PR-<n>`/URL and `owner/repo#number` forms (memory [[proutput-prref-validator-rejects-real-adapter]]). **Do not change validator behavior** during the rename — keep the live acceptance set exactly; tightening/loosening it is a separate concern. **Confirm OQ-1 with Alex before mass moves.** [Source: `GitHubRealAdapter.java#87-93,591`, `IntegrationLinkService.java#571-600`]
5. **R5 — Selection is profile-based today, not `kind`-based (AC5) — OQ-4.** `github-mock` / `github-real` profiles are mutually exclusive (`GitHubConfiguration.assertExclusiveGitHubProfile`), beans are `@Profile`-gated, and `gitHubRestClient` only exists under `github-real`. `github-mock` is in the default `local`/`test`/`demo` profile groups. AC5 wants a `deliveryline.integration.repo-host.kind` selector. **Recommended:** add the `kind` key as the *documented* selector and *validate it against the active profile* (fail-fast on mismatch) — **keep** the profile mechanism + the existing `deliveryline.github.*` keys. Renaming `deliveryline.github.*` is an ops-breaking `.env`/deploy change and is **out of scope** (note as a future cosmetic migration in the ADR). [Source: `infrastructure/config/GitHubConfiguration.java#49-86`, `application/integration/github/GitHubProperties.java`, `application.yml#12-17,148-161`]
6. **R6 — The live domain records are in the APPLICATION layer; AC4/AC7 want them in DOMAIN.** `GitHubRepository`/`GitHubPullRequest`/`GitHubBranch`/`GitHubAdapterException`/`GitHubProperties` all currently sit in `org.dradgo.application.integration.github`. AC4/AC7 require the neutral types in `domain.integration.repohost`. Move+rename the three records and the exception (→ `Repository`/`PullRequest`/`Branch`/`RepositoryHostAdapterException`; exception co-located with port per 3.32). **Keep `GitHubProperties` in `application.integration.github`** (it is github-impl config, not a neutral type — mirrors 3.32 keeping `LinearProperties`). The package-rename is the highest-churn part (~151 references across ~26 files). [Source: `application/integration/github/*.java`]
7. **R7 — Capabilities have weaker consumer-grounding on the GitHub side (AC3/AC10/AC11) — OQ-5.** 3.32 could ground "capability honored by consumers" on the live `syncCompletionToLinear` comment path. GitHub's analog optional features (draft PRs, comments) have **no live unconditional consumer**: `createPullRequest` has no draft param, and `commentOnPullRequest` has no production caller. Declare `RepositoryHostCapabilities.githubDefaults()` (all five `true`) and treat the draft clause as vacuously satisfied (no draft path to gate — do not invent one). The single defensible guard is `supportsPullRequestComments` around `commentOnPullRequest`; add it forward-lookingly or assert capability-declaration only. The foundation contract leans on parity + declaration, not behavioral degradation. [Source: `GitHubRealAdapter.java` (no draft param), consumer map — no `commentOnPullRequest` caller]

5. **OQ-5 — capabilities grounding (AC3, AC10, AC11).** `RepositoryHostCapabilities` is net-new and GitHub's optional features (draft PRs, comments) have no live unconditional consumer. **Recommended:** declare `githubDefaults()` (all five `true`), add a forward-looking `supportsPullRequestComments` guard around `commentOnPullRequest`, and do **not** add a `draft` param to `createPullRequest` (no consumer; AC10's draft example is vacuously satisfied). A blank/`null` `targetBranch` is the back-compat path — the real adapter resolves the repository default branch internally exactly as before, so the existing HTTP sequence + parity stubs are byte-for-byte unchanged.
