## Story

As a Workflow Owner repairing ambiguous artifact history after partial failure or replay conflict,
I want explicit lineage-recovery actions that let me reattach an orphan payload, mark a dead lineage terminal, or approve creation of a new lineage branch with recorded rationale,
so that ambiguous artifact history is resolved through auditable recovery rather than hidden automatic behavior (NFR19 — no silent overwrite).

## Context & Central Reconciliation (READ FIRST)

**This is the THIRD and final half of the Epic-4 artifact-reconciliation split: detection = 4.15 (`done`), operator-driven drift repair = 4.16 (`done`), lineage/fork governance = 4.16a (THIS story).** You extend the SAME service (`ArtifactReconciliationService`) that 4.16 built the repair coordinator on ([[story-4-16-artifact-reconciliation-operator-driven-repair-actions]]) — read that class end-to-end first; its `repairArtifactDrift` coordinator is the exact structural template you mirror.

**⚠️ THE ONE ARCHITECTURAL FACT THAT RESHAPES THIS ENTIRE STORY — lineage conflicts are TRANSIENT, never persisted.** Unlike 4.16 (which resolves a persisted `artifact_drift_detected` row keyed by a `driftId`), there is **NO lineage-conflict table**. `ARTIFACT_OPERATION_INTENT_CONFLICT` and `ARTIFACT_LINEAGE_ALREADY_EXISTS` are thrown **inside `@Transactional` operation paths and rolled back** — they surface only as a transient 409 to the caller and are written nowhere. ## Dev Notes

### Relevant architecture patterns and constraints

- **The transient-conflict reality is the whole story (READ Reconciliation 1 twice).** There is no `driftId`/`conflictId` — the operator names the ambiguous artifact directly. Do not scaffold a detection/persistence surface for lineage conflicts; the ACs never ask for one (AC8's inspection surfaces are the EXISTING audit/history/queue, fed by the `recovery_actions` row + event). If you find yourself adding a `lineage_conflicts` table, STOP — that is the deferred "4.16b" (OQ-1).
- **Mirror `repairArtifactDrift`, not the older orphan-reconciliation path.** `ArtifactReconciliationService` has two idioms: the 4.15 orphan-sweep path (uses `ArtifactEventPort.append`, per-tick `UUID` correlationId) and the 4.16 repair path (uses `WorkflowEventWritePort.append` directly with a pre-generated `evt_` id + `interventionMarker=true`, correlationId from `actor.correlationId()`, single `REQUIRES_NEW` tx, `succeeded`-on-INSERT, replay-first). **Use the 4.16 repair idiom** — it is the single-operator-action shape. `performRepair`'s structure (`ArtifactReconciliationService.java:771-885`) is your template: MDC scope begin → mutate → best-effort triggering event (here: null) → event append → recovery_actions insert → (here: no `resolveDrift` — there is no drift row) → MDC scope end.
- **ZERO new ctor deps (Reconciliation 8).** The 3 lineage-write methods go on the already-injected `ArtifactRecordPort`; the coordinator reuses `RecoveryActionRecordPort`/`WorkflowEventWritePort`/`WorkflowEventReadPort`/`IdempotencyKeyValidator`/`ApprovalService`/`Clock`/the `REQUIRES_NEW` `TransactionTemplate`. Do not add a new port or ctor arg. If you add a `requireLineageSeams()` guard it is a no-op alias of `requireRepairSeams()` (same objects).
- **Uniqueness + version discipline (Reconciliation 4).** `uq_artifacts_workflow_run_id_artifact_type_version` forbids two version-1 rows in one `(run,type)`. A fork MUST use `version=max+1` (like `createNextVersion`) but with `parent_artifact_id=NULL` + `lineage_recovery=true`. Reattach keeps the orphan's existing version (already unique) and only re-parents. Both write under the lineage lock (`lockLineageForUpdate`) to serialize against concurrent drafts.
- **Fail-closed is already true — do not weaken it (Reconciliation 11).** Story 1.12c made the operation layer refuse to guess. 4.16a does not add "auto-resolve"; it adds an EXPLICIT operator path and leaves the artifact state such that the existing fail-closed decision resolves correctly on the next ingest. The scope-protected hot path (`RunnerBroker`, `ArtifactOperationService` decision) stays untouched.
- **Registries + gates.** `action_type='artifact_lineage_reconcile'` → SQL CHECK widen + a constant (NO registry enum, NO `RegistryContractTest` impact). `WorkflowEventType.ARTIFACT_LINEAGE_RECONCILED` → un-CHECKed text, fixture-pinned (no migration). New `DomainErrorCode`s → the exhaustive `ProblemDetailsCatalog` + `problemTypeUris` + foundation-gate. New `lineageAction` detail key → `WorkflowEventDetailKeys` holder + `ALLOW_LISTED_KEYS` + contract test + schema. `lineageAction` is application-enum-only (inline OpenAPI enum), not a persisted registry value.
- **ArchUnit + naming.** NEW class-scoped rule permitting only `ArtifactReconciliationService` to call the lineage-write methods (Reconciliation 12). `ArtifactLineageController` must end in `Controller` + live under `adapters.rest`; must call the service, never a `*Port`. New rules run under Failsafe.
- **Scope protection.** Do NOT touch `RecoveryService`, `RunnerBroker`, or `ArtifactOperationService`'s CREATE/UPDATE decision. Lineage recovery is artifact-scoped operator repair.
