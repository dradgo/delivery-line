# Story 2.13: Backend — REST Mutation Endpoints + OpenAPI

Status: done

## Story

As a frontend developer (UI work in stories 2.18 / 2.19 / 2.21 mutation hooks),
I want REST mutation endpoints `POST /api/v1/workflows/{workflowRunId}/approve-spec`, `POST /api/v1/workflows/{workflowRunId}/reject-spec`, and `POST /api/v1/workflows/{workflowRunId}/clarifications/{clarificationId}/answer` with required `Idempotency-Key` headers, `X-Actor-Identity` header (with local-user fallback), Problem Details error responses, and a regenerated OpenAPI snapshot,
So that the UI's mutation hooks (story 2.6 AC6) have a stable typed contract and CLI/REST equivalence (story 1.7 AC5) is maintained for the new spec-loop commands.

## Acceptance Criteria

1. **Given** `WorkflowController` in `adapters.rest` (extended from story 6.9), **Then** three mutation endpoints exist with the exact paths: `POST /api/v1/workflows/{workflowRunId}/approve-spec` (already present from story 2.9 — rebuilt by this story), `POST /api/v1/workflows/{workflowRunId}/reject-spec` (already present from story 2.10 — rebuilt by this story), `POST /api/v1/workflows/{workflowRunId}/clarifications/{clarificationId}/answer` (**new** in this story) — paths use kebab-case action names per architecture rule.

2. **Given** request bodies, **Then** they are typed `record` DTOs in `adapters.rest` with camelCase JSON serialization, **header-vs-body split per AC4 already applied**:
   - `ApproveSpecRequest { artifactId, expectedArtifactVersion, expectedContextBundleVersion, reviewerRole?, reason? }` — rebuilt from the existing record; rename `artifactVersion` → `expectedArtifactVersion`, `contextVersion` → `expectedContextBundleVersion`; drop `actorIdentity`, `actorType`, `correlationId` (moved to headers).
   - `RejectSpecRequest { artifactId, expectedArtifactVersion, expectedContextBundleVersion, reviewerRole?, reasonText, taggedFeedback }` — same body-shape rebuild; `reasonText` + `taggedFeedback` remain required; `taggedFeedback` typed as `RejectionTaxonomy` (story 2.10 enum).
   - `AnswerClarificationRequest { artifactId, expectedArtifactVersion, answerText }` — **new**; `expectedArtifactVersion` is the spec version the answer pins (story 2.11 `SubmitClarificationCommand.artifactVersion`); `answerText` constraints mirror the command (`@NotBlank @Size(max = 8192)` — story 2.11 SUBMIT-CLAR record).
   - All field-level validation uses `jakarta.validation.constraints.*` with `@Size`/`@NotBlank`/`@Positive` mirroring the underlying command-model annotations; field-level violations return 400 `INVALID_COMMAND_PAYLOAD` with `details: [{field, code, message?}, ...]` (mirror story 1.8 mapping).

3. **Given** every state-changing endpoint, **Then** the `Idempotency-Key` header is **required**; missing returns 400 `MISSING_IDEMPOTENCY_KEY`; format violations (per `IdempotencyKeyValidator`) return 400 `INVALID_IDEMPOTENCY_KEY`. Existing approve-spec / reject-spec endpoints currently declare `@RequestHeader(name = "Idempotency-Key", required = false)` — this story tightens to `required = true` and adds a controller-advice mapping for Spring's `MissingRequestHeaderException(Idempotency-Key)` → `DomainException(MISSING_IDEMPOTENCY_KEY)` so the Problem Details body is returned rather than Spring's default 400 text. The new clarification endpoint inherits the same wiring.

4. **Given** the `X-Actor-Identity` header (E2 deferred-auth model — local trusted user per architecture security posture lines 256–257, 343), **Then**:
   - The header identifies the actor for the application command (`ActorContext.actorIdentity`).
   - When the header is **missing OR blank**, the controller falls back to a configured local-user identity via a new typed property `deliveryline.security.local-actor-identity` (Spring `@ConfigurationProperties` or `@Value`); default value: `local-operator`. Document the default in `application.yaml` with a comment that production deployments must override.
   - **Actor type** is always `ActorType.HUMAN` for REST entries — there is no role-claim plumbing in the MVP and the reviewer role comes from the request body (`reviewerRole`). RBAC is NOT enforced (audit-only per architecture line 256). `@RequestHeader(name = "X-Actor-Identity", required = false)` + property fallback — never a 401/403.
   - The `X-Correlation-Id` header is already populated by `infrastructure.observability.CorrelationIdFilter` (auto-generated UUID v7 if missing) and propagated into MDC; the controller does NOT need to re-read it for the command — it reads `MdcKeys.get(MdcKeys.CORRELATION_ID)` and passes that into the command's `correlationId` field. The filter's existing UUID validation + 128-char length cap (per its line 52 log) handles malformed-header cases at the filter layer.

5. **Given** Problem Details mapping (story 1.8 + the existing `ProblemDetailsCatalog`), **Then** typed error responses for these three endpoints cover at minimum:
   - `MISSING_IDEMPOTENCY_KEY` (400, not retryable)
   - `INVALID_IDEMPOTENCY_KEY` (400, not retryable)
   - `INVALID_COMMAND_PAYLOAD` (400, not retryable) — schema validation failures, with `details: [{field, code}, ...]`
   - `INVALID_ID_PREFIX` (400, not retryable) — malformed `workflowRunId` / `artifactId` / `clarificationId` path or body params
   - `RUN_NOT_FOUND` (404, not retryable)
   - `CLARIFICATION_NOT_FOUND` (404, not retryable)
   - `ARTIFACT_RECORD_NOT_FOUND` (404, not retryable)
   - `APPROVAL_VERSION_MISMATCH` (409, retryable)
   - `IDEMPOTENCY_KEY_CONFLICT` (409, not retryable)
   - `ILLEGAL_TRANSITION` (409, not retryable)
   - `ARTIFACT_PAYLOAD_UNAVAILABLE` (503, retryable — already in catalog at line 145–148)
   - `CLARIFICATION_ARTIFACT_VERSION_MISMATCH` (409, retryable)
   - `CLARIFICATION_TERMINAL_STATE` (409, not retryable)
   - `ILLEGAL_CLARIFICATION_TRANSITION` (409, not retryable)
   - `WORKFLOW_RUN_TERMINAL` (409, not retryable)
   
   All listed codes are **already mapped** in `ProblemDetailsCatalog.createMetadata` — verify each is reachable via the three endpoints' service stacks and that contract tests assert `code` + `status` + relevant `details` (never human text). No new `DomainErrorCode` enum values required for this story.

6. **Given** OpenAPI generation via `springdoc-openapi` (already configured per memory `springdoc-boot4-version.md`: starter-webmvc-ui 3.0.3 / maven-plugin 1.5), **Then** the three endpoints appear with full request/response schemas (`@Operation`, `@ApiResponses`, `@Schema(implementation = ...)` for each Problem Details and success type per the existing pattern in `WorkflowController.getWorkflow` lines 99–131); the committed OpenAPI snapshot at `deliveryline-backend/src/main/resources/openapi/openapi.json` is regenerated via `scripts/regen-openapi.sh` and committed; CI's drift check (story 1.21 AC6 — the `openapi-snapshot-drift` job) passes; the frontend client regenerated under the same script runs cleanly. Memory `openapi-regen-platform-shim.md` documents the WSL2-vs-PowerShell shell split for the two regen steps.

7. **Given** CLI/REST equivalence (story 1.7 AC5 — both transports call the same application services), **Then** Spring Shell command implementations (NOT placeholders) are added under `adapters.cli.WorkflowCommands` (Spring Shell 3.x `@Command` style — see lines 124, 181, 234, 312 for the existing `submit` / `status` / `retry` / etc. pattern) calling `workflowCommandService.approveSpec(...)`, `workflowCommandService.rejectSpec(...)`, `workflowCommandService.answerClarification(...)`:
   - `deliveryline workflow approve-spec <runId> --artifact-id ... --expected-artifact-version N --expected-context-bundle-version N [--reviewer-role ...] [--reason ...] [--idempotency-key ...] [--actor-identity ...] [--actor-type ...] [--correlation-id ...] [--verbose]`
   - `deliveryline workflow reject-spec <runId> --artifact-id ... --expected-artifact-version N --expected-context-bundle-version N --tagged-feedback {missing_scope|unclear_specification|misunderstood_implementation} --reason-text ... [--reviewer-role ...] [--idempotency-key ...] [--actor-identity ...] [--actor-type ...] [--correlation-id ...] [--verbose]`
   - `deliveryline workflow answer-clarification <runId> <clarificationId> --artifact-id ... --expected-artifact-version N --answer-text ... [--idempotency-key ...] [--actor-identity ...] [--actor-type ...] [--correlation-id ...] [--verbose]`
   - CLI parameter defaults: `--idempotency-key` auto-generates a UUID v7 if absent (mirror `submit` line 150–164); `--actor-identity` falls back to the same `deliveryline.security.local-actor-identity` property as REST (so CLI and REST share the local-actor model); `--actor-type` defaults to `human`; `--correlation-id` uses `CorrelationScope` push/pop pattern (mirror `submit` lines 146 / 177). Each command uses the existing `WorkflowCliExitStatusExceptionMapper` for `DomainException` → CLI exit codes.
   - A new contract test `CliRestEquivalenceContractTest` (in `deliveryline-backend/src/test/java/org/dradgo/contract/`) asserts that for identical command payloads, CLI and REST produce identical `WorkflowStateChangeResult` outputs (workflowRunId, currentState, correlationId echoed) — mirror story 1.7's symmetry contract (`CommandModelSymmetryFoundationContract`).

8. **Given** the architecture forbids workflow orchestration in adapters (architecture lines 670, 681–683), **Then** an extended/new ArchUnit rule asserts `WorkflowController`'s mutation methods (the three new/rebuilt) only do (a) header/path/body parsing, (b) command-record construction, (c) `workflowCommandService.*` invocation, (d) response-DTO mapping. The rule can be expressed as: any class in `org.dradgo.adapters.rest` must not import from `org.dradgo.application.workflow.spi`, `org.dradgo.application.clarification.spi`, `org.dradgo.application.artifact.spi`, `org.dradgo.adapters.persistence`, `org.dradgo.application.runner`, or `org.dradgo.adapters.runner` (the existing `REST_AND_CLI_ADAPTERS_MUST_NOT_TOUCH_PERSISTENCE_OR_EXTERNAL_ADAPTERS` rule in `ArchitectureRuleCatalog` may already cover most of this — extend its package list if a gap exists). The rule lives in `ArchitectureRuleCatalog` and is wired via an `@ArchTest` in `ArchitectureBoundaryTest`.

9. **Given** the responses, **Then** success returns `200 OK` with a typed result DTO carrying the new state, optional new artifact version (when applicable to the variant), and stamped `correlationId`:
   - approve-spec / reject-spec → `WorkflowStateChangeResponse { workflowRunId, currentState, correlationId }` (existing record — reuse unchanged; `currentState` is the post-mutation state, e.g., `Executing` after approve, `Investigating` after reject).
   - answer-clarification → a **new** `ClarificationAnswerResponse { workflowRunId, clarificationId, clarificationStatus, currentState, correlationId }` where `clarificationStatus` is the post-mutation clarification status (e.g., `"answered"`) and `currentState` is the unchanged workflow state (answering does NOT transition workflow state — it only mutates the clarification row + appends `clarification.answered`).
   - The `X-Correlation-Id` response header echoes the request correlation ID (or the auto-generated one). The existing `CorrelationIdFilter` already adds this on the response side — verify by integration test; do NOT re-implement in the controller.

10. **Given** the contract test suite, **Then** for each of the three endpoints there is a `*ContractTest` (Spring `@WebMvcTest` against the controller with a `@MockitoBean WorkflowCommandService`, or `@SpringBootTest` + Testcontainers if end-to-end is more natural — match the pattern in existing `*ContractTest.java` siblings) that covers:
    - **Happy path** 200 with correct response body shape (per AC9) — schema match against the regenerated OpenAPI snapshot, not exact human strings.
    - **Every documented error code** in AC5 (one test per code per endpoint where reachable): `MISSING_IDEMPOTENCY_KEY` (omit header), `INVALID_IDEMPOTENCY_KEY` (malformed), `INVALID_COMMAND_PAYLOAD` (missing/oversize fields), `INVALID_ID_PREFIX` (malformed path id), `RUN_NOT_FOUND` (unknown runId), `CLARIFICATION_NOT_FOUND` (clarification endpoint only), `APPROVAL_VERSION_MISMATCH` (stale `expectedArtifactVersion` on approve), `CLARIFICATION_ARTIFACT_VERSION_MISMATCH` (stale on answer), `IDEMPOTENCY_KEY_CONFLICT` (same key, different fingerprint).
    - **Idempotent replay** (same key + same payload → identical response from the second call — no duplicate row insert, no duplicate event).
    - **Idempotency-conflict** (same key + different fingerprint → 409 `IDEMPOTENCY_KEY_CONFLICT`).
    - **Schema validation failures** with field-level `details` array shape.
    - **X-Actor-Identity** fallback: omit the header on each endpoint and assert the persisted `actor_identity` column equals the configured `deliveryline.security.local-actor-identity` default.
    - **X-Correlation-Id** response header echoes the request correlation ID; auto-generated ID is a structurally valid UUID v7 when the request omitted the header.
    
    Assertions on `code` + `status` + `details` (machine-readable fields only) — never on human-readable `title` / `detail` text per architecture line 712.

### Logging Requirements (project-wide standard)

Every story is expected to leave the touched services observable enough to debug a production incident without re-deploying. This is enforced via the "Logging instrumentation" task above.

- **Framework:** SLF4J + Logback (Spring Boot default). No `System.out`, no `printStackTrace()`.
- **Where to log (minimum surface):**
  - Public controller methods → `INFO` on entry (params + idempotency-key prefix) + `INFO` on success (status + response correlationId) / `WARN` on typed-domain rejection / `ERROR` on unexpected failure.
  - DTO mapping failures (Jackson / Bean Validation) → `WARN` "request validation failed endpoint={} errorCount={}".
  - Header resolution → `DEBUG` "actor identity resolved source={header|property} value={...}" (do NOT log property value at INFO; it may be PII).
  - State-machine transitions → `INFO` "transitioned X from {from} to {to}" (already logged by `ApprovalService` / `ClarificationService` — verify no duplicate emission from the controller layer).
- **Required context keys** (carried via MDC or as structured parameters): `correlationId`, `workflowRunId`, `idempotencyKey`, `actorIdentity`, `actorType`, plus the entity public ids touched (`clarificationId`, `artifactId`, `approvalId` where applicable).
- **Forbidden in log output:** payload bytes, secrets/tokens, raw PII, classification-restricted fields. `answerText` is **user-authored free text** — do NOT log it in full; log its length and the first 16 chars at DEBUG only (mirror how `ClarificationService.submitAnswer` logs `answerText.length=` per `ClarificationService.java` precedent).
- **Test contract:** new logging surfaces must be pinned by at least one focused test (list-appender or Spring Boot `OutputCaptureExtension`) so downstream refactors can't silently delete them.
