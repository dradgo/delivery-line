# Story 3.22: Developer Takeover Service — `takeoverWorkflow` with Preserved Context

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Developer who needs to continue implementation work outside the orchestrator (per UX spec § Developer Flow),
I want `DeveloperTakeoverService.takeoverWorkflow(...)` that transitions a run to `TakenOver`, **stops orchestrator runner dispatch** (cancels in-flight + queued executions), **preserves all prior artifacts + run history + GitHub PR linkage**, and records the takeover with developer attribution — fulfilling **FR18, FR19, FR33**,
so that I can continue work in the linked GitHub branch using normal IDE/git tooling without losing the governed run's context, history, or merge-ready handoff trail.

## Acceptance Criteria

1. **Given** an `application.recovery` package extension (story 1.18 stubbed `RecoveryService` baseline), **Then** a **new** `DeveloperTakeoverService` exposes `takeoverWorkflow(TakeoverWorkflowCommand command) → TakeoverResult`. `DeveloperTakeoverService` is the **canonical executor** for the `takeover_workflow` action. (It is a **sibling service**, NOT a third method on `RecoveryService` — Trap T1.)
2. **Given** the existing `TakeoverWorkflowCommand` (`WorkflowCommand`, already in the sealed model), **Then** it carries `workflowRunId`, `actorIdentity`, `actorType` (`= ActorType.HUMAN`), `idempotencyKey`, `correlationId`, `reasonText` (required). The developer `reviewerRole` is a **takeover invariant** (`= developer`) applied at the `recovery_actions` insert — it is NOT added as a command field (Trap T2).
3. **Given** the `recovery_actions` table (story 1.3 / V1), **Then** a takeover row is inserted via the **existing** `RecoveryActionRecordPort.insert(RecoveryActionWriteCommand)`: `public_id` (`rcv_` prefix), `workflow_run_id`, `action_type='takeover'` (already in the V1 CHECK), `triggering_event_id`, `resulting_event_id`, `actor_identity`, `actor_type='human'`, `reviewer_role='developer'`, `idempotency_key`, `result_status` (`pending → succeeded`). **No new Flyway migration for `recovery_actions`** — `'takeover'` is already an allowed `action_type`.
4. **Given** the workflow state machine (story 1.5), **Then** the `→ TakenOver` transition is performed by **reusing** `WorkflowCommandService.takeoverWorkflow(TakeoverWorkflowCommand)` (already wired: `executeIdempotent` + `replayStateChange` + `WorkflowTransitionService.transition(…, TAKEN_OVER, …)`). `* → TakenOver` is already legal from every non-terminal state and the transition table already enforces a non-blank `reason` (Trap T3). The service does **not** call `WorkflowTransitionService` directly.
5. **Given** **stop orchestrator runner dispatch** per FR18, **When** `TakenOver` is reached, **Then** every `runner_executions` row for the run in `{queued, pending, running}` is transitioned to a new terminal status `cancelled_for_takeover`: (a) the DB status flip is the **authoritative** no-more-dispatch signal (the worker pool's `dequeueNext` leases only `status='queued'`; the broker's `ACTIVE_STATUSES` is `{pending, running}` — a `cancelled_for_takeover` row is invisible to both); (b) for any row that was `running`, the live container is gracefully stopped **best-effort after commit** via `DockerRunnerAdapter.cancel(runnerExecutionId)` (`docker stop`, never throws — Trap T5); (c) the scan covers `queued` + `pending` + `running` to close the dequeue race window.
6. **Given** **preserved context** per FR19 + FR33, **Then** all prior artifacts (spec, plan, PR/output) remain persisted; the active `integration_links` `github_pr` row is **left untouched** (developer continues on the same PR); the full append-only audit trail is preserved. Takeover writes only: the `→ TakenOver` state-change event, the takeover `recovery_actions` row, the runner-row status flips, and (decision OQ-3) an optional `recovery.takenOver` event. **It deletes/supersedes nothing.**
7. **Given** **continuation outside the orchestrator**, **Then** the developer continues editing the linked GitHub branch (`deliveryline/{ticketRef}/stage-{runId}` per story 3.9 AC2) with normal git tooling; DeliveryLine dispatches no further runners but the PR linkage stays readable via the run read-model.
8. **Given** post-takeover visibility, **Then** `WorkflowInspectionService.getRunSummary` returns `state='TakenOver'`, `takenOverBy={actorIdentity, actorType, reviewerRole}`, `takenOverAt={timestamp}`, `takenOverReason={reasonText}` as fields on `WorkflowRunDetailedSummaryView`. **REST/CLI/UI surfacing of these fields is deferred** to stories 3.25 / 3.28 / 3.29 — the application-internal view is the AC8 home (exact precedent: 3.20's `productApprovalState`/`technicalApprovalState`, 2.12's `pendingClarifications` — Trap T8).
9. **Given** allowed-actions integration (story 2.14), **Then** a new `AllowedAction.TAKEOVER_WORKFLOW("takeover_workflow")` is registered; `computeActionMatrix` returns `takeover_workflow` for `state=WAITING_FOR_REVIEW` + `role=developer` (alongside `accept_implementation` + `reject_implementation`). After `TakenOver` is reached, the only allowed action is `view_only` (**already wired** for the `TAKEN_OVER` state — no change there).
10. **Given** Linear completion sync (story 3.16), **Then** takeover does **not** auto-detect completion in E3 — the run stays `TakenOver` until an explicit operator action (Epic 4) closes it. Takeover transitions to `TakenOver` (a terminal state), so **no completion hook fires** (the post-commit hook is `→ COMPLETED` only).
11. **Given** idempotency (story 1.9), **Then** retries with the same `idempotencyKey` + identical fingerprint replay the prior `TakeoverResult`; the same key + different fingerprint raises `IDEMPOTENCY_KEY_CONFLICT`. Two independent backstops apply: `WorkflowCommandService.takeoverWorkflow`'s `executeIdempotent` (idempotency_records) AND `uq_recovery_actions_idempotency_key` (recovery_actions). Replay re-reads the run's current state (it is already `TakenOver`).
12. **Given** the test suite, **Then** covers: happy-path takeover → `TakenOver` + cancels in-flight + queued executions (status = `cancelled_for_takeover`); prior artifacts + GitHub PR linkage preserved; audit trail preserved; takeover from each non-terminal state succeeds; takeover from `Completed`/`TakenOver`/`Reconciled` raises `ILLEGAL_TRANSITION`; post-takeover allowed actions reduced to `view_only`; idempotent replay + idempotency-conflict; FR19 reconstruction (who/when/why/what-state-preserved readable via `getRunSummary`).

**Scope guardrails:**

- **In scope:** the `DeveloperTakeoverService` orchestrator + `TakeoverResult`; the `cancelled_for_takeover` runner status (enum + V15 migration + state-machine + `RecordPort.markCancelledForTakeover` + adapter); the `AllowedAction.TAKEOVER_WORKFLOW` matrix wiring; the `getRunSummary` takeover fields; the test suite.
- **Out of scope (do NOT build):** the REST `/takeover` endpoint **enrichment** + CLI `deliveryline takeover` + OpenAPI regen (story 3.25 — see **OQ-1**); the UI Decision Bar takeover affordance (3.28) + Run Context Strip / timeline takeover surfacing (3.29). The existing transition-only `POST /takeover-workflow` endpoint **stays as-is** in 3.22.
- **No new `DomainErrorCode`.** `ILLEGAL_TRANSITION`, `IDEMPOTENCY_KEY_CONFLICT`, `RUN_NOT_FOUND` all exist. `cancelled_for_takeover` is a **status**, not an error code (it reuses `ILLEGAL_TRANSITION` for guard rejections — `RunnerExecutionStateMachine`'s existing pattern).
- **One new Flyway migration:** `V15__add_cancelled_for_takeover_status.sql` (widens the `runner_executions` status CHECK only). **No `recovery_actions` migration.**

- **OQ-2: `triggering_event_id` / `resulting_event_id` for the takeover `recovery_actions` row.** Retry links `triggering = failure event`, `resulting = recovery.retried event`. Takeover may fire from a non-failure state (`WaitingForReview`). **Recommendation:** `triggering_event_id` = the latest `workflow_events` row for the run at takeover time (or NULL — the FK is nullable); `resulting_event_id` = the `WORKFLOW_STATE_CHANGED → TAKEN_OVER` event (or the `recovery.takenOver` event if OQ-3 adds it).
- **OQ-3: dedicated `recovery.takenOver` event vs reuse the state-change event.** A dedicated event mirrors `RECOVERY_RETRIED` and feeds 3.29's "takeover event renders in the timeline" + FR19. **Recommendation:** add `RECOVERY_TAKEN_OVER("recovery.takenOver")` with the fixture-site lockstep (Trap T9) and store `reasonText` in its `details` (which also cleanly sources OQ-4). **Fallback** under scope pressure: skip it; use the state-change event as `resulting_event_id` and read `details.reason` for OQ-4; 3.29 can add the event later.

### Architecture compliance

- **Component boundaries:** `application.recovery` depends only on `application.*` ports + `domain.*` types — no JPA entities, no `adapters.*` ([[application-cannot-import-adapters]]). The container-stop capability is reached through an `application.runner.spi` port (Task 4).

- **State+event atomicity (architecture.md):** the `→ TakenOver` transition + state-change event (inside `workflowCommandService.takeoverWorkflow`) + the runner-row flips + the `recovery_actions` insert form the durable audit. The `docker stop` is intentionally **post-commit best-effort** (it can't roll back the takeover; the DB status flip already stopped dispatch).
