> **⚠️ READ FIRST — this story closes a SILENT GAP, not a reported regression.** The clarification feature's **back half shipped** in Epic 2 (2.11 submission + `/answer`, 2.12 incorporation lifecycle, 2.18 `ClarificationRegion` UI) but its **front half — turning an agent's open questions into `clarifications` rows — was deferred to "Epic 3 runner-contracts" and never built.** Evidence (verified 2026-06-23): `ClarificationWritePort.insertOpen(...)` — the ONLY method that creates a clarification row — has **zero production callers** (only the adapter impl + the interface ref); `runner-result.v1.schema.json`'s `specArtifact` carries only `contentReference` (no question channel); the only clarification REST endpoint is `/answer` (no create endpoint). Net effect: **no run will ever show a clarification question.** Real specs (e.g. `run_8172295672634c71b7c0ee28d6a5be0a`, `run_c53cacd1cae54f1eaaad3440e658b8c7`) DO raise open questions — but only as prose inside `spec.md` ("Confirm whether…", "Decide whether…"), which is silently dropped.
>
> **3e-1 builds the CREATE half only: spec runner emits structured questions → broker inserts `open` clarifications on spec ingest → they appear in the existing `ClarificationRegion` and are answerable via the existing `/answer` endpoint.** The accept→regenerate→incorporate loop (markAccepted trigger + structured acknowledgement + spec rebuild grafting) is **3e-2**. Keep the line crisp: 3e-1 ends at "an `open` clarification row exists per emitted question, is surfaced by the read model, and `/answer` works"; everything about *acceptance and incorporation* is 3e-2.
>
> **Epic placement (proposal — ratify via correct-course):** this is an **Epic 2 PM-loop completion**, not an Epic 3d per-step-execution-control story. It does not fit 3d's theme (FR64–FR69). Proposed home: **new Epic 3e "Clarification Loop Activation" = {3e-1 create, 3e-2 incorporate}**, FR10. Add to `sprint-status.yaml` + `epics.md` via a sprint-change-proposal before `dev-story`.
>
> **Three things the live codebase forces you to reconcile (read all three before coding):**
>
> 1. **The runner-result contract has NO question channel and no `schemaVersion` bump is needed.** `runner-result.v1.schema.json` `specArtifact` uses `unevaluatedProperties:false`. Add an **optional** `questions[]` to `specArtifact.properties` (NOT in `required`, NO `schemaVersion` bump) — the additive-optional-field pattern story 3d-7 used for `providerUsage`. Adding a field to an `additionalProperties/unevaluatedProperties:false` object **without declaring it in `properties` would fail validation**, so it MUST be declared. See [[runnerproperties-record-component-fanout]] for the analogous fan-out discipline and R1.
> 2. **The runner must EXTRACT questions from agent output — there is a precedent: the OpenSpec fence-split.** Both `runners/codex/lib/runner.mjs` and `runners/claude/lib/runner.mjs` already carry a **BYTE-IDENTICAL** "fence split" (story 3a-8, L454–520) that lifts a fenced block out of agent stdout. Mirror it: the agent emits a fenced ` ```clarifications ` JSON block; the runner parses it into `artifact.questions`. **Both runner files change in the SAME PR (RUNNER_CONTRACT mirror rule)** and **both offline mocks (`INSTALL_*_CLI=false`) must emit a deterministic question** or conformance ITs / `runner-image-compat` go red — see [[runner-tool-self-test-needs-offline-mock]] and R2.
> 3. **Creation must NOT unwind a successful completion.** The `insertOpen` calls ride inside `RunnerBroker.handleSuccess` AFTER `recordCompleted` semantics, exactly where `markArtifactAvailable` sits (L1639–1648). That block **swallows ALL `RuntimeException`s** because `onResult`'s outer try has only a `finally` (no catch) — an escaping exception strands the execution `RUNNING` and re-harvests forever. Clarification creation MUST adopt the same best-effort guard (swallow per-question failures, log WARN) and a **deterministic idempotency key** so replay/re-harvest doesn't double-insert. See R3.

## Story

As a product reviewer,
I want the spec runner's open questions to become first-class `open` clarifications attached to the spec,
so that when a spec needs my input I see explicit, answerable questions in the review pane instead of buried prose — and the `/answer` endpoint that already exists actually has something to answer.

2. **Given** the two runner entrypoints, **Then** both `runners/codex/lib/runner.mjs` and `runners/claude/lib/runner.mjs` (BYTE-IDENTICAL change) split a fenced ` ```clarifications ` block (JSON array of `{questionId, questionText}`) out of agent stdout — mirroring the existing OpenSpec fence-split — and, **only at `stage === 'spec'`**, set `artifact.questions` to the parsed array (omit the field entirely when the block is absent or empty; never emit `questions: []` to keep no-question results byte-identical to today). Malformed JSON in the block is **non-fatal** (logged, treated as "no questions") — a clarification problem never fails spec delivery (mirror the OpenSpec `T-ADDITIVE-NEVER-BLOCKS` rule).

3. **Given** the offline mock runner branch (`INSTALL_CODEX_CLI=false` / `INSTALL_CLAUDE_CLI=false`), **Then** each mock emits **one deterministic** question (e.g. `questionId="Q-MOCK-001"`, `questionText="Mock clarification: confirm scope?"`) at `stage === 'spec'` so the broker ingest IT is deterministic and `runner-image-compat`/conformance ITs stay green. Real-runner builds emit whatever the agent fenced.

4. **Given** a spec runner result whose `specArtifact.questions` is non-empty, **When** `RunnerBroker.handleSuccess` ingests the spec artifact (INVESTIGATION stage), **Then** for each question an `open` `clarifications` row is created via `ClarificationWritePort.insertOpen` — `workflowRunId` = the run, `artifactId`+`artifactVersion` = the just-ingested spec artifact (captured like the existing `prOutputArtifactId` at L1539/1607), `questionId`/`questionText` from the result, `idempotencyKey` = `"runner-result-clarification:" + runnerExecutionId + ":" + questionId` (deterministic → replay-safe). The work is done by a **new `application.clarification.ClarificationIngestService`** (NOT inline in the broker — keeps the broker free of a clarification-write dependency growth; mirrors how the broker delegates the spec-ready transition to `WorkflowOrchestrationService`).

5. **Given** the creation seam runs inside `handleSuccess`, **Then** it is **best-effort and never unwinds the completion**: it is positioned with / immediately after the SPEC `markArtifactAvailable` block (so the artifact exists + is available) and wraps the whole per-result clarification batch in a `try { … } catch (RuntimeException) { log.warn(…) }` (same rationale as the L1639 availability guard), and an `IDEMPOTENCY_KEY_CONFLICT` `DomainException` from `insertOpen` on replay is caught and logged at INFO as a benign duplicate (not rethrown). A failure to create clarifications leaves the run correctly advanced to `WaitingForSpecApproval` with the spec available — clarifications simply re-create on a re-harvest.

6. **Given** the clarification lifecycle audit, **Then** a new `WorkflowEventType CLARIFICATION_RAISED("clarification.raised")` is appended once per created clarification (or once per batch with a `count` detail — implementer's choice, note it) carrying `clarificationId` + `artifactId` + `questionId` via existing allow-listed `WorkflowEventDetailKeys` (add `questionId` to the allow-list only if not present — confirm at impl time). The type is mirrored into **both** fixture sites (`workflow-event-types.fixture.json` + `workflow-events-response.schema.json`) per [[new-workfloweventtype-fixture-sites]]; the `openapi.json` snapshot regenerates **byte-identically** (eventType is a free string).

7. **Given** the read model + UI (2.14/2.18), **Then** the created `open` clarifications are surfaced by `WorkflowInspectionService` clarification status and the existing `ClarificationRegion` renders them without code change beyond fixtures (the read path already exists — `useClarifications`/`clarificationView`). AC verifies end-to-end: ingest creates rows → `/workflows/{id}` (or the clarification read surface) lists them → `/answer` records an answer over one (existing endpoint, no change).

8. **Given** tests, **Then** coverage asserts: (a) contract — valid-with/without-questions pass, malformed fail; (b) runner unit — fence-split parses `questions`, absent block omits the field, malformed block is non-fatal (sibling of `runner-split-fenced.test.mjs`, both runners); (c) broker IT (Failsafe + Testcontainers) — a mock spec result with a question creates an `open` clarification visible via `ClarificationReadPort`, replay/re-harvest does NOT duplicate (idempotency), a result with NO questions creates none (parity — a default run is byte-identical to pre-3e); (d) `CLARIFICATION_RAISED` registry/fixture/OpenAPI drift green; (e) an existing `/answer` flow succeeds over a created clarification. New `application.*` code meets the standing **≥80% line-coverage** floor.

## Dev Notes

### Why these ACs are reconciled (epic/FR wording vs. the live codebase)

| Wording assumption | Reality (verified 2026-06-23) | Reconciliation |
|---|---|---|
| "the spec runner raises clarifying questions that become clarifications" (FR10) | `insertOpen` has **zero** production callers; the only clarification endpoint is `/answer`; `specArtifact` has no question field. | Add `questions[]` to the contract (AC1), runner emission (AC2/3), and a `ClarificationIngestService` called from `handleSuccess` (AC4) — the missing CREATE half. |
| "questions arrive structured from the agent" | The runner builds `spec.md` from agent stdout (codex L289); agents today bury questions as prose. | Add a fenced ` ```clarifications ` block (mirror the OpenSpec fence-split, byte-identical in both runners) the agent emits and the runner lifts into `questions[]` (R2). |

### R1 — Additive optional field, no schemaVersion bump (the 3d-7 pattern)
`runner-result.v1` `specArtifact` closes its shape (`unevaluatedProperties:false`). An undeclared field would be rejected, so `questions` MUST be declared — but as **optional** (absent from `required`). This is exactly how 3d-7 added `providerUsage` to `normalizedOutput`: declare-in-properties, not-required, no `schemaVersion` change, both runners + mocks in the same PR. A no-question result stays byte-identical to today (field omitted), which keeps every existing spec-ingest IT green.

### R2 — Runner emission rides the OpenSpec fence-split precedent; both runners + mocks in one PR
The runner cannot invent questions; the **agent** must. The established mechanism for "agent emits structured side-data alongside its main artifact" is the OpenSpec fence-split (3a-8): the agent prints a fenced block, the runner lifts it out of stdout before writing the artifact. Mirror it for ` ```clarifications `. Hard rules from prior runner stories: (a) **both `runner.mjs` files change byte-identically** in the same PR — the RUNNER_CONTRACT mirror rule, enforced by runner-image-compat; (b) **the offline mock branch must emit a deterministic question** or conformance ITs go red ([[runner-tool-self-test-needs-offline-mock]], [[local-codex-runner-latest-was-mock]]); (c) a clarification-parsing problem is **never fatal** to spec delivery (`T-ADDITIVE-NEVER-BLOCKS`). The agent prompt that instructs emitting the fence is a runner-image concern (the system/wrapper prompt) — note it but it is not a backend change.

### R3 — Creation is best-effort inside `handleSuccess`; deterministic idempotency or it double-inserts
The seam sits where `markArtifactAvailable` sits (RunnerBroker L1639). That block swallows ALL `RuntimeException`s on purpose: `onResult`'s outer try has only a `finally`, so an escape strands the execution `RUNNING` and the poller re-harvests forever (the same failure mode documented at L1629–1638 and L2028). Clarification creation MUST inherit this guard. AND the poller CAN legitimately re-harvest a result (recovery scratch-replay, concurrent harvest) — so `insertOpen`'s idempotency key must be **deterministic per (runnerExecutionId, questionId)**, not random, and an `IDEMPOTENCY_KEY_CONFLICT` on replay is benign (the DB `uq_clarifications_idempotency_key` backstop maps to it — see `ClarificationWritePort` javadoc). Without the deterministic key a re-harvest creates duplicate questions.

### R4 — The read/render half already works; do not rebuild it
`WorkflowInspectionService` already computes clarification status, `ClarificationReadPort` filters `archived_at IS NULL`, and the FE `useClarifications`/`clarificationView`/`ClarificationRegion` (2.18) render `open` rows. Once rows exist they surface. 3e-1 adds NO new read endpoint and NO new FE component — only fixtures + (optional) an e2e. Resist scope creep here.

### R5 — `artifactId`/`artifactVersion` come from the just-ingested spec, captured like `prOutputArtifactId`
The clarification is pinned (composite FK) to the EXACT spec artifact + version it was raised against (so a later spec version supersedes it — 2.12 semantics). In `handleSuccess` the spec artifact is created by `artifactOperationService.recordOperation(...
