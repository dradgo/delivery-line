# Story 4.8: `RecoveryService.pause` — Manual Pause for Operator Intervention

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Workflow Owner who needs to halt a run mid-flight to investigate something (e.g. a suspected runner config issue, integration sync drift, or an external dependency outage),
I want `RecoveryService.pause(workflowRunId, actor, idempotencyKey, reasonText)` that transitions the run to `Paused`, cancels in-flight and queued runner work without erasing it, and preserves the prior state for later resume (story 4.5),
so that NFR5 (pause when uncertain) is fully wired with a typed manual pause path — operators don't have to take over (irreversible) just to investigate.

## Context & Central Reconciliation (READ FIRST)

**This is the EIGHTH story of Epic 4 and the FOURTH of the "Recovery Service Extensions" slice (4.5–4.9). It is a BACKEND-ONLY application-service story: add a `pause(...)` method to the existing `RecoveryService`, backed by a new `WorkflowCommandService.pauseWorkflow` transition, a new `recovery.paused` audit event, a `recovery_actions` row (`action_type='pause'` — a pre-reserved V1 CHECK slot), a new terminal `cancelled_for_pause` runner-execution status (the ONE Flyway migration), a `pause_workflow` allowed-action, and a `PAUSE_NOT_APPLICABLE` error code. It has NO REST endpoint (story 4.13), NO CLI command (story 4.13 AC6), and NO frontend (story 4.22).**

**`pause` is the mirror image of `resume` (`RecoveryService.java:676-972`) and inherits its cancellation mechanics from `DeveloperTakeoverService` (`:356-451`). Those two files are the exact structural templates.** ADR 0033 already names `pause(...)` on its sanctioned allow-list (`RecoveryService.java:69-72`), so — unlike 4.5 — **there is no ArchUnit scope-lock to widen**; only the class javadoc moves `pause` from the "not yet present" list to the present list.

**Read the six Headline Reconciliations before coding. Pause is NOT a small story: it is the first code that ever writes `WorkflowState.PAUSED`, and three shipped subsystems (4.4's recommender, 4.5's resume, the runner pollers) have latent assumptions that only become true — or only become bugs — the moment pause exists.**

Dependencies: **4.5** (`resume`) `done`; **4.6** (`reconcile`) `done`; **4.28** (scope-lift + ADR 0033) `done`. **4.7** (`rerunFromStep`) is `ready-for-dev` and shares two artifacts with this story (`MISSING_REASON_TEXT`, the next free Flyway number) — see Reconciliation 6.

### HEADLINE RECONCILIATIONS

1. **Pause is legal from an EXPLICIT ALLOW-LIST of 8 source states — NOT the epic's literal "any non-terminal state". Four non-terminal states are deliberately EXCLUDED because an autonomous driver owns their out-edge, and pausing them would silently destroy a one-shot trigger.** Epic AC3 says pause is valid "from any non-terminal, non-`Paused`, non-`TakenOver` state". Applied literally that admits `INBOX`, `PLANNED`, `SPLIT`, and `WAITING_FOR_DEPENDENCIES` — each of which is advanced by a background driver, not by a human:
   - `WAITING_FOR_DEPENDENCIES` → `RunDependencyReleaseService` fires `WAITING_FOR_DEPENDENCIES → INVESTIGATING` exactly once, when the last prerequisite reaches `Completed` (`WorkflowTransitionTable.java:119-127`). If the run is `Paused` at that instant the release transition raises `ILLEGAL_TRANSITION`, the trigger is consumed and never re-fires, and the run is **permanently wedged** — resume restores it to `WaitingForDependencies` with all prerequisites already complete and nothing left to release it.
   - `SPLIT` → the 3f-7 completion rollup drives `SPLIT → COMPLETED` via an afterCommit hook when the last child completes (`WorkflowState.java:12-14`). Pausing a split parent strands its children. (The 3f-8 advisory-locked sweep would eventually self-heal a stranded parent, but only after resume — a confusing, avoidable state.)
   - `INBOX` → intake auto-dispatches `INBOX → INVESTIGATING`; the run has not started, so there is nothing to halt.
   - `PLANNED` → reserved/dead; nothing enters or leaves it in production.

   **Bind: `PAUSABLE_SOURCE_STATES = { INVESTIGATING, WAITING_FOR_SPEC_APPROVAL, EXECUTING, WAITING_FOR_REVIEW, WAITING_FOR_MANUAL_EXECUTION, WAITING_FOR_LINT_APPROVAL, WAITING_FOR_DELIVERY, FAILED }` — an EnumSet constant on `RecoveryService`. A current state outside the set raises `PAUSE_NOT_APPLICABLE` (409) with `details.currentState`, which satisfies AC3's stated rejections (`Completed`, `TakenOver`, `Paused`) as a strict superset.** This is the executor-as-gate current-state precondition, not a transition-table inference ([[gate-action-needs-explicit-current-state-precondition]]). Do NOT reuse `RecoveryService.TERMINAL_STATES` (`:183`) as the guard — an allow-list is the contract; terminal-subtraction would silently re-admit the four excluded states. Do NOT extract `WorkflowState.isTerminal()` — that is story 4.30's change and would collide. See OQ-1. [Source: WorkflowTransitionTable.java:119-127; WorkflowState.java:12-14,22-27; RecoveryService.java:183; epic-04-recovery.md#Story 4.8 AC3]

2. **⚠️ THE SYMMETRY INVARIANT — every `X → Paused` edge you add MUST have a matching `Paused → X` edge added in the SAME change, or you ship a runbook that strands runs. This is the single highest-risk item in the story, and 4.5 explicitly deferred it to you.** `resume` reads the prior state off the typed `WORKFLOW_STATE_CHANGED → Paused` event and transitions back to it (`RecoveryService.java:793-824`), but it does **not** validate that the recovered `priorState` is a legal `Paused →` target — story 4.5's own code review logged this as a deferred finding: *"`priorState` is not validated as a legal `Paused → X` target before the prep-tx transition — a non-`EXECUTING` priorState yields raw `ILLEGAL_TRANSITION` instead of `RESUME_NOT_APPLICABLE` … becomes relevant when pause (4.8) supports more source states."* Today the table has exactly ONE inbound edge `EXECUTING → PAUSED` (`WorkflowTransitionTable.java:94`) and `PAUSED → {EXECUTING, TAKEN_OVER, RECONCILED}` (`:163-168`). **Bind: (a) add `WorkflowState.PAUSED` to the target set of each of the 7 not-yet-wired `PAUSABLE_SOURCE_STATES` rows (`EXECUTING` already has it); (b) widen the `PAUSED` row to `{EXECUTING, INVESTIGATING, WAITING_FOR_SPEC_APPROVAL, WAITING_FOR_REVIEW, WAITING_FOR_MANUAL_EXECUTION, WAITING_FOR_LINT_APPROVAL, WAITING_FOR_DELIVERY, FAILED, TAKEN_OVER, RECONCILED}`; (c) pin the invariant with a NEW table contract test `PauseTransitionSymmetryTest`: `∀ S ∈ PAUSABLE_SOURCE_STATES → PAUSED ∈ allowedTargets(S) ∧ S ∈ allowedTargets(PAUSED)`.** Because the two sets are constructed together, every recorded `priorState` is a legal target BY CONSTRUCTION and 4.5's deferred finding is CLOSED — say so in the completion notes. Guard mechanics: `assertTransitionAllowed` (`:192-237`) requires a non-blank `reason` only for `→TAKEN_OVER`/`→RECONCILED`, and rejects a non-null `failureCategory` on any edge except `{EXECUTING,INVESTIGATING} → FAILED` — so pause and resume both pass `failureCategory=null`. `PAUSED → FAILED` (resume of a paused-from-`Failed` run) is legal under that guard with a null category. 5. **Pause cancels `{queued, pending, running}` runner rows ONLY — it does NOT touch `awaiting_manual` parked rows, and it does NOT delete the context bundle. ## Dev Notes

### Relevant architecture patterns and constraints

- **`RecoveryService.resume` (`:676-972`) + `performResumePrep` (`:1116-1176`) are the exact structural template.** Copy the shape: MDC scope → idempotency validate → input validate → actionType-guarded replay pre-check → current-state guard → locate linking event → REQUIRES_NEW prep tx (transition-via-command-service + append recovery event + insert `recovery_actions` row) → post-commit side-effect OUTSIDE the tx → `markSucceeded` → return. `pause` differs in exactly four ways: (a) the target state is the constant `PAUSED` (no `targetState` on the command); (b) the prep tx additionally flips runner rows to `cancelled_for_pause`; (c) the post-commit side-effect is `runnerAdapter.cancel(...)`, not a re-dispatch — so there is **no dispatch-failure compensation branch**; (d) the linking event is the run's latest `WORKFLOW_STATE_CHANGED`, resolved **before** the tx.
- **`DeveloperTakeoverService` (`:91-96,274-295,356-451`) is the cancellation template** — the scan-and-flip inside the prep tx, the post-commit `runnerAdapter.cancel` for previously-`RUNNING` rows, and the `Optional.empty()`-means-already-terminal idempotent skip. Pause diverges on the scan set and does not delete the context bundle (Reconciliation 5).
- **⚠️ The DB status flip — not `docker stop` — is what makes pause hold.** `runnerAdapter.cancel` is best-effort and may no-op (unknown id, already exited). A `cancelled_for_pause` row is invisible to `DEQUEUE_SQL` (`where status='queued'`) and to `ACTIVE_STATUSES = {pending, running}` (timeout/stale/orphan scans, `pollActiveExecutions`, `recoverOnStartup`). That invisibility is the whole mechanism.
- **⚠️ Prep-tx race with the worker pool.** `markCancelledForPause` uses `findByPublicIdForUpdate` (row lock) while `DEQUEUE_SQL` uses `FOR UPDATE SKIP LOCKED`. If a worker leases a `queued` row the instant pause runs, our flip blocks, then observes `previousStatus == RUNNING` and correctly routes that rex id into the post-commit `docker stop` list. Both orderings are safe; do not add extra locking.
- **⚠️ No new transition-table wildcard.** The table has no `*→X` mechanism — `TakenOver`/`Reconciled` are hand-enumerated on every source row (`WorkflowTransitionTable.java:32-173`). Pause's edges are likewise hand-enumerated. `assertCoversAllStates` (`:175-182`) requires every state to have a rules entry.
- **State machine.** `PAUSED` exists (`WorkflowState.java:49`) but nothing has ever written it — pause is the first writer. `assertTransitionAllowed` (`:192-237`): `reason` required only for `→TAKEN_OVER`/`→RECONCILED`; a non-null `failureCategory` is rejected on every edge except `{EXECUTING,INVESTIGATING}→FAILED`, so pause and resume both pass `null`.
- **`interventionMarker`.** `WorkflowTransitionService` sets it `true` only for `→TAKEN_OVER`/`→RECONCILED` (`:334`), so pause's own `WORKFLOW_STATE_CHANGED` carries `false`. The separately-minted `recovery.paused` event sets `interventionMarker=true`, mirroring `recovery.resumed`.
- **`RecoveryActionSnapshot`** (12 components incl. `reviewerRole`): tests seed these directly (see `RecoveryLoggingContractTest.recoveryActionSnapshot` / the `resumeActionSnapshot` helper 4.5 added when it tightened the replay guard). Reuse `resolveConcurrentResumeReplay` (`:1257-1304`) as the template for `resolveConcurrentPauseReplay`.
- **Deferred note carried from 4.5:** `retry`'s Step-1 replay STILL lacks the actionType guard (4.5 fixed only resume's). Pause must NOT copy retry's Step 1. Fixing retry is out of scope here.
