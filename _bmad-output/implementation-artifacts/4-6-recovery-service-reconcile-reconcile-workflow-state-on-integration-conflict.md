# Story 4.6: `RecoveryService.reconcile` вЂ” Reconcile Workflow State on Integration Conflict

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Workflow Owner facing a detected integration conflict (e.g. a GitHub PR merged externally while the workflow still expected it open),
I want `RecoveryService.reconcile(workflowRunId, conflictId, resolutionDecision, actor, idempotencyKey)` that applies an explicit operator-chosen resolution to a detected conflict вЂ” never a silent overwrite per NFR19,
so that FR35 (workflow owners can reconcile workflow state when an integration conflict is detected) is wired with a typed reconcile path that requires explicit decision input and closes the `integration_conflicts` row produced by story 4.17.

## Context & Central Reconciliation (READ FIRST)

**This is the SIXTH story of Epic 4 and the SECOND of the "Recovery Service Extensions" slice (4.5вЂ“4.9). It is a BACKEND-ONLY application-service story: add a `reconcile(...)` method to the existing `RecoveryService`, backed by a new `WorkflowCommandService.reconcileWorkflow` transition (to the terminal `Reconciled` state), the reuse of the already-registered `recovery.reconciled` event, a `recovery_actions` row (`action_type='reconcile'`), a new `reconcile_conflict` allowed-action surfaced by conflict existence, and the resolution-write that closes the `integration_conflicts` row (story 4.17). It has NO REST endpoint (story 4.11), NO CLI command (story 4.11 AC6), and NO frontend (stories 4.22/4.23).**

**Mirror `RecoveryService.resume` (`RecoveryService.java:621-917`) вЂ” it is the exact structural twin** (single governed action, `findLatestTransitionToState`-style event linking, REQUIRES_NEW prep tx, post-commit best-effort side-effect, full idempotency contract). Story 4.6 differs from 4.5 in five ways: (a) it takes two extra inputs вЂ” `conflictId` + `resolutionDecision`; (b) it reads/resolves a row in the `integration_conflicts` table (4.17) rather than acting purely on the run; (c) it transitions to the TERMINAL `Reconciled` state (no runner re-dispatch); (d) its post-commit side-effect is an integration-link alignment/re-push (not a runner enqueue); (e) it reuses the already-registered `recovery.reconciled` event (no new event type).

**Read the seven Headline Reconciliations before coding вЂ” the epic AC text drifts from live code and these bindings win.** The dependency stories are DONE and verified: **4.17** (the `integration_conflicts` producer) merged `done`; **4.5** (the `resume` twin) merged `done`; **4.28** (scope-lift) merged `done` вЂ” so `RECOVERY_SERVICE_IS_SCOPE_PROTECTED` is GONE and `reconcile` is already named on ADR 0033's sanctioned allow-list (`RecoveryService.java:57-64`). There is **no scope-lock to widen** (a hard drift from 4.5, which had to widen it).
