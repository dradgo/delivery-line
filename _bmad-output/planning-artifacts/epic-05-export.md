## Epic 5: Shareable Run Export & Team-Visible Review

A pilot user exports a redacted, shareable run report a teammate can inspect without access to the originating machine — secrets, tokens, user identifiers, and local paths removed. Retention policies govern how long run history and artifacts persist and what happens when tickets are closed, archived, or removed from the source system. Surfaces pilot-measurement data (AR34b) via CLI reports + exported runs so pilot teams can answer the PRD's success-criteria questions: did median cycle time improve vs baseline, did rework rate decrease using the tagged review-feedback taxonomy, and what fraction of eligible low-risk tickets ran through the governed workflow.

### Story 5.1: `RunExportService` — Composition + Redaction + Classification

As a backend developer composing the export pipeline,
I want `RunExportService.export(workflowRunId, options) → ExportBundle` that gathers all run data (workflow events, artifacts, approvals, runner executions, recovery actions, integration links, measurement data, context bundles) into a typed `ExportBundle`, applies redaction via `RedactionPolicyService` (story 1.10) on every text field, and asserts every output element carries a `DataClassification` registry value (story 1.4),
So that AR20 (RunExportService with deterministic structure + redaction tests) is wired and NFR10 + NFR11 (private vs shareable separation) are enforced at composition time.

**Acceptance Criteria:**

1. **Given** the `application.export` package, **Then** `RunExportService` exists with method `export(workflowRunId, options: ExportOptions) → ExportBundle`; `ExportOptions` carries: `includeRunnerLogs: boolean` (default true — but logs only flow if their classification permits per story 3.6 AC9), `includeContextBundles: boolean` (default true), `includeMeasurementData: boolean` (default true), `redactionLevel: 'standard' | 'strict'` (standard = default policy from story 1.10; strict = additionally redacts ticket summaries + reason text strings beyond a documented length, suitable for cross-org sharing).
2. **Given** the typed `ExportBundle`, **Then** it carries: `runMetadata` (id, current state, ticket reference, repository reference, PR reference, created_at, completed_at?), `events: List<EventEntry>` (workflow events with classification per entry), `artifacts: List<ArtifactEntry>` (metadata + payload references — payload bytes embedded only when classified `shareable-redacted` or `shareable-full`), `approvals: List<ApprovalEntry>`, `runnerExecutions: List<RunnerExecutionEntry>`, `recoveryActions: List<RecoveryActionEntry>`, `integrationLinks: List<IntegrationLinkEntry>`, `measurementData: MeasurementSummary?` (per story 5.7; null when `includeMeasurementData=false`), `contextBundles: List<ContextBundleEntry>?` (per `includeContextBundles`), `exportMetadata` (export timestamp, exporting actor identity, redaction-level used, total redaction count, source DeliveryLine version).
3. **Given** classification per `DataClassification` registry (story 1.4), **Then** every element in the bundle carries a `classification` field; the export bundle's overall classification is the most-restrictive of all element classifications (e.g., one `local-only` element forces the bundle to `local-only` — which then refuses to export per story 1.10 AC8 unless the element is downgraded via redaction or excluded via `ExportOptions`).
4. **Given** classification-driven inclusion gating per story 3.6 AC9, **Then** runner-log entries classified `local-only` are EXCLUDED from the export by default (cannot become `shareable` by export inclusion alone — explicit `RedactionPolicyService` re-classification required); a documented `EXPORT_CLASSIFICATION_VIOLATION` error fires if an attempt is made to include `local-only` content without prior re-classification.
5. **Given** redaction-on-export per story 1.10 AC7 (double-gate), **Then** every text field in the bundle (event reasons, artifact metadata, runner output references, recovery-action reason texts, comment bodies) passes through `RedactionPolicyService` before serialization — even though source-side redaction (story 1.10 AC7 capture-time) should have caught secrets, the export pass is defense-in-depth; each redaction is counted in `exportMetadata.totalRedactionCount` for monitoring.
6. **Given** sensitive-field handling per NFR10, **Then** the following fields are ALWAYS subjected to additional sanitization on export regardless of source-side redaction: actor email addresses (replaced with `actorIdentity` opaque ID), absolute filesystem paths in `storage_ref` (replaced with relative paths under `{DELIVERYLINE_HOME}` placeholder), local hostnames in URL fields (replaced with `localhost` placeholder); a contract test asserts these specific transformations always apply.
7. **Given** integration link classification per story 3.15 AC7, **Then** GitHub PR refs + branch names + commit SHAs (classified `shareable-redacted`) are included; Linear ticket references (per story 1.14 + story 3.16 — pilot org's internal ticket IDs) included as `shareable-redacted` (the tickets aren't secret per se but operators should know the data carries org-internal references).
8. **Given** the architecture's append-only history rule (NFR4 + NFR32) preserved through export, **Then** the bundle is read-only; `ExportBundle` exposes no setters; the act of exporting is logged as an `export.created` workflow event (added to event-type registry per story 1.4 drift test) on the source run with `details.exportFingerprint` = SHA-256 of the bundle's deterministic JSON serialization (story 5.2) — supporting later "did anyone export run X?" audit queries.
9. **Given** ArchUnit (story 1.11), **Then** `RunExportService` lives in `application.export`; only this service may compose `ExportBundle`; controllers + adapters consume the typed view via the service; the service depends on `WorkflowInspectionService`, `ArtifactService`, `RedactionPolicyService`, `IntegrationLinkService`, `RunnerLogCaptureService` (story 3.6) for read-only reads — never on persistence repos directly.
10. **Given** the test suite, **Then** tests cover: happy-path export of a complete run produces well-formed bundle, classification-driven inclusion gating (local-only logs excluded by default), `EXPORT_CLASSIFICATION_VIOLATION` raised on illegal inclusion attempt, redaction-on-export adversarial fixtures all caught, sensitive-field transformations (email → actorId, abs paths → relative, hostnames → localhost) applied, `export.created` event appended to source run, `redactionLevel='strict'` further redacts ticket-summary + reason-text strings, `includeRunnerLogs=false` / `includeContextBundles=false` / `includeMeasurementData=false` produce bundles with those sections absent.

### Story 5.2: Export Bundle File Format + Schema (JSON + Markdown)

As a backend developer producing export files + a teammate reviewing them off-machine,
I want the `ExportBundle` from story 5.1 serialized into two complementary formats — a deterministic JSON file (`export.v1.json`, machine-readable + scriptable) AND a human-readable Markdown companion (`export.md`, structured Markdown view) — both bundled in a single `.zip` archive with deterministic structure for hash-stable golden-file testing,
So that AR20's deterministic-structure requirement is met (NFR41 reviewer can inspect status/artifacts/decisions/failures/next-action without access to originating machine) + scripts can consume JSON while humans can read Markdown.

**Acceptance Criteria:**

1. **Given** the export ZIP archive, **Then** its layout is deterministic: `/export.v1.json` (structured machine-readable representation of the `ExportBundle`), `/export.md` (human-readable Markdown rendering), `/artifacts/{artifactId}/v{version}/{filename}` (embedded artifact payloads where classification permits per story 5.1 AC4), `/manifest.json` (file inventory + checksums + total bundle size for integrity checking), `/README.md` (one-page explanation of what this export contains + how to read it).
2. **Given** the `export.v1.json` schema, **Then** it is documented as JSON Schema Draft 2020-12 at `backend/src/main/resources/export/export.v1.schema.json` (parallel to runner-contracts schemas from story 1.6); the schema is published in the documentation; future schema versions follow semantic compatibility rules per the runner-contract pattern (story 1.6 AC9).
3. **Given** the `export.md` Markdown format, **Then** it follows a stable section layout: **Run Summary** (metadata table — runId, ticket, repo, PR, state, dates, exporting actor, redaction level), **Timeline** (chronological events with actor + reason + linked-artifact references), **Approvals** (PM + Developer approvals with reviewer-role + decision + reason + version-binding info), **Artifacts** (table of artifacts produced — type, version, classification, status, link to embedded payload), **Recovery Actions** (any retry/resume/reconcile/rerun/pause/classify actions taken + outcomes), **Integration Linkage** (Linear ticket + GitHub PR refs with state at export time), **Measurement Data** (if `includeMeasurementData=true` — cycle time, rework rate, runner durations), **Export Metadata** (footer — export timestamp, redaction count, classification, source version).
4. **Given** deterministic serialization for hash-stable golden-file testing, **Then** the JSON file uses sorted-keys serialization (Jackson or equivalent with stable ordering), the Markdown file uses consistent heading levels + tables, and the ZIP archive uses sorted-entry-name ordering — same input bundle produces byte-identical archive across two export invocations (verified by SHA-256 hash comparison in tests).
5. **Given** classification labeling in both formats, **Then** every artifact + event entry in `export.md` is annotated with its `DataClassification` value visibly (e.g., `*[shareable-redacted]*` suffix); the JSON includes `classification` field on every entry; reviewers see clearly what level of trust to apply to each piece.
6. **Given** redaction transparency, **Then** `export.md` includes a "Redaction Notes" section listing the count of redactions applied + the redaction-level used (`standard` / `strict`) — reviewers know how aggressively the export was scrubbed; raw redacted-token placeholders (e.g., `[REDACTED_LINEAR_API_KEY]`) appear in the body content where redaction triggered.
7. **Given** README.md content, **Then** it is a static file (auto-included from a backend-managed template) explaining: what the bundle contains, how to read the JSON + Markdown files, what the classification labels mean, how to verify the bundle's integrity via `manifest.json` checksums, who to contact about the source run (the exporting actor + the originating DeliveryLine instance ID).
8. **Given** integrity per `manifest.json`, **Then** it lists every file in the archive with SHA-256 checksums + total bundle byte size + creation timestamp + bundle-version reference (`export.v1`); a teammate can verify the bundle was not tampered with by re-computing checksums.
9. **Given** large-bundle handling, **Then** when total bundle size exceeds a configurable threshold (default 50 MB — `application.yml` `deliveryline.export.size-warning-threshold-mb`), the export emits a WARN log + adds a "Large bundle" note to `manifest.json`; bundles exceeding a hard cap (default 500 MB — `deliveryline.export.size-hard-cap-mb`) fail with `EXPORT_BUNDLE_TOO_LARGE` and require operator decision to either reduce scope (drop runner-log inclusion, drop context bundles) or override.
10. **Given** ArchUnit (story 1.11), **Then** the JSON serializer + Markdown renderer + ZIP packager all live in `application.export.formatters`; only this package may produce export-format files; the formatters consume the typed `ExportBundle` from story 5.1 — never query persistence directly.
11. **Given** the test suite, **Then** tests cover: golden-file hash comparison across two consecutive exports of same input (asserts byte-identical output), JSON conforms to `export.v1.schema.json`, Markdown sections render correctly per fixture run, classification labels appear on every entry in both formats, manifest checksums match actual file checksums, large-bundle warning + hard-cap rejection, README.md content present, ZIP archive deterministic ordering.

### Story 5.3: Adversarial Redaction Enforcement on Exports

As a security-conscious backend developer + workflow owner who must trust exported bundles,
I want the adversarial redaction fixture set from story 1.10 + story 3.6 extended with **export-specific scenarios** (full run bundles deliberately seeded with secrets across all element types — events, artifacts, runner executions, context bundles, measurement data) + a CI gate that fails on any single passing-secret in any export bundle,
So that NFR10 (shared/exported run artifacts must redact secrets/private tokens/local machine paths by default) is mechanically enforced — pilots can't accidentally ship a bundle containing a real API key.

**Acceptance Criteria:**

1. **Given** the existing adversarial redaction fixture set from stories 1.10 AC4 + 3.6 AC10, **Then** this story extends it with **export-specific scenarios** under `backend/src/test/resources/export-redaction-fixtures/`: at least 5 complete fixture runs deliberately seeded with secrets across all bundle element types (events with secret-containing reasons, artifact payloads with embedded secrets, runner-execution stdout with auth-header leaks, context bundles with path-leaks, measurement data with hostname leaks).
2. **Given** the CI gate `export-redaction-verify` (defined in story 5.10 + extending story 1.21 AC1's CI tier order), **Then** it: (a) generates an export for each adversarial fixture run, (b) parses the resulting bundle JSON + Markdown + embedded payloads, (c) scans every text field against the credential-pattern regex set (Linear API key prefix, GitHub PAT shapes, SSH key blocks, .env-style KEY=VALUE secret names, Authorization headers, URL query secrets, absolute-path username leaks, process-env leakage), (d) **fails the build on any single match** — single passing secret = build-blocking failure (mirrors story 2.27 AC7 sanitization regression policy).
3. **Given** the property-based generator from story 1.10 AC6 (unknown-shape secrets), **Then** this story's CI gate also runs property-based scans on a subset of generated bundles — high-entropy values inside fields not in the standard allowlist trigger a WARN; the generator parameters are tuned to balance coverage vs CI time budget (documented in fixture README).
4. **Given** sensitive-field transformations from story 5.1 AC6 (email → actorId, abs paths → relative, hostnames → localhost), **Then** the CI gate additionally asserts these transformations always apply: a fixture deliberately containing `alex@dradgo.com` in an event reason field is exported with `[ACTOR_ID:act_abc]` substitution; absolute path `C:\Users\alex\projects\foo\bar.md` is exported with `{DELIVERYLINE_HOME}/projects/foo/bar.md`; hostname `192.168.1.42` is exported with `localhost`.
5. **Given** redaction-level coverage, **Then** the gate runs each fixture under both `redactionLevel='standard'` and `redactionLevel='strict'` (story 5.1 AC1) — verifying strict mode redacts additional content beyond standard (e.g., long ticket-summary text, long reason-text strings).
6. **Given** failure diagnostics on gate failure, **Then** the CI report identifies: which fixture's export failed, which credential pattern was matched, in which file (JSON / Markdown / embedded payload), and at which line — operators can immediately locate the offending non-redacted content.
7. **Given** the foundation gate (story 1.23) widening per stories 2.27 AC7 + 2.28 + 3.8 + 3.35 + 4.26, **Then** this story extends the gate again: `export-redaction-verify` job's success is required for foundation-gate PRs; failure blocks merge.
8. **Given** ongoing fixture maintenance, **Then** the fixture set is documented as a living artifact (parallel to story 1.10 AC9): adding a new credential format triggers an update to BOTH the source-side fixture (story 1.10) AND this export-side fixture set; a CI lint check asserts both fixture sets reference the same credential-format catalog.
9. **Given** a metadata-spoofing test (parallel to story 1.10 AC10), **Then** an adversarial fixture deliberately classifies a secret-containing payload as `shareable-full` to test the re-validation gate from story 5.1 AC4; export must downgrade the classification + redact, never trust the claimed classification.
10. **Given** the test suite, **Then** unit tests cover: each credential-pattern type is detected in exported JSON, Markdown, and embedded payloads; transformation rules apply correctly per AC4; strict mode applies additional redactions beyond standard; metadata-spoofing fixture is downgraded; failure diagnostic output identifies offending fixture + pattern + location.
