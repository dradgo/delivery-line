## Epic 3f: Complex Ticket Flow

The governed workflow moves beyond the single linear *one-ticket → one-run → one-spec → one-plan* path that Epics 1–3e assume. At the **specification-approval** or **implementation-review** gate, an operator who finds the scope too large can **split** the run into smaller subtasks. An LLM proposes the decomposition (with proposed inter-subtask dependencies); the operator **approves** it, **continues as one ticket**, or **re-proposes with feedback** — a governed loop that mirrors the spec-rejection / clarification-incorporation feedback pattern. On approval the system creates one **child run** per subtask — minting a **source sub-ticket** where the ticket connector supports it, otherwise proceeding **internal-only** — preserving **parent→child lineage** and terminating the parent in a new `Split` state. Child runs can carry **execution dependencies** so a dependent run holds in an explicit `WaitingForDependencies` state until its prerequisites complete. The Run Review Queue gains **per-project attribution and a project filter** so the resulting portfolio of runs stays navigable.

**Why this epic exists (net-new capability):** Epics 1–3e bake in a 1:1 ticket↔run↔lineage shape (NFR16: "one governed run must map to one ticket … unless a human explicitly reconciles the record"). Real pilot tickets are frequently too coarse to spec or implement in a single pass, yet there is **no governed way to break one down without losing lineage**, **no way to sequence** the resulting work, and — per story **3c-9 AC6**, deferred as backend-blocked — **no way to see or filter runs by project** in the queue. This epic adds those three capabilities as **new product scope** (FR70/FR71/FR72). It is **not** an activation of deferred Epic-1/2 work (contrast Epic 3e, which only activated a deferred front-half); the split path explicitly invokes the NFR16 "human explicitly reconciles" escape hatch.

This is a **complex-ticket-flow** epic, not a clarification or per-step-execution feature — it does not fit Epic 3d or 3e. It is **inserted between Epic 3e and Epic 4** purely for sequencing (avoids renumbering E4–E6). Source: this sprint-change-proposal.

**Prerequisites & reused substrates (all done):**
- **Advisory-reviewer channel** (3d-2 `RunnerStage.REVIEW`, `enqueueReviewerIfConfigured`, `step_reviews`, `GET /reviewer-verdict`, Verdict Panel; extended to the spec gate by 3e-3) — the split **proposal** is generated by a reviewer-style LLM call that reads the spec/plan and emits a structured decomposition.
- **Batch-submission fan-out** (story 3-18 `WorkflowBatchSubmissionService`) — best-effort, **non-transactional**, per-child idempotency-keyed submit; the split **commit** reuses this shape (one independent submit per child).
- **Ticket-source abstraction** (story 3-32 `TicketSourceAdapter` + `TicketSourceCapabilities`) — the new `createSubticket` capability is added behind a capability flag; the **internal-only** fallback fires when the connector cannot create tickets.
- **Soft-hide/archive** (3d-8) and **`cancelled_for_takeover`** (story 3-22, V15) — precedents for the parent's terminal disposition and a new terminal workflow state.
- **Run creation + dispatch seams** (`WorkflowRunCreatePort.create`, `WorkflowOrchestrationService.dispatchSpecGeneration`) — child runs are minted here; dependency gating is the one place auto-dispatch is suppressed.
- **Project read side** (3c-6/3c-7 `projectId` on runs) — 3f-6 surfaces it on the run-list read model and adds the `/workflows` `projectId` filter.

**ADR (proposed):** `docs/adr/0029-complex-ticket-flow.md` — records (a) the parent→child lineage model (`parent_run_id` + the `Split` terminal state) and how it satisfies the NFR16 "explicit reconciliation" escape hatch; (b) the run-dependency DAG model (`run_dependencies`, cycle guard, `WaitingForDependencies` gate, release-on-completion, failed-prerequisite policy); (c) the split-proposal structured channel (reviewer-style, persisted, three-action loop). Author alongside story 3f-2.

### Story List (6 stories)

```
Foundation
3f-1   Ticket-source sub-ticket creation capability
3f-2   Parent→child run lineage + terminal Split state
3f-3   Run-dependency graph + WaitingForDependencies gating

Split (the operator-facing flow)
3f-4   LLM split-proposal channel + three-action feedback loop
3f-5   Split commit fan-out (subtickets/children + lineage + dependencies + parent termination)

Portfolio visibility
3f-6   Run Review Queue project attribution + project filter
```

> Stories 3f-1, 3f-2, 3f-3, and 3f-6 are largely independent foundations. 3f-4 (proposal) depends on the reviewer channel (3d-2/3e-3 done). 3f-5 (commit) is the integration story — it depends on 3f-1 (subticket capability), 3f-2 (lineage + Split state), 3f-3 (dependency edges + gated dispatch), and 3f-4 (the approved proposal). Detailed, reconciled implementation stories live at `{implementation_artifacts}/3f-1..3f-6-...md`.

### Story 3f-1: Ticket-Source Sub-Ticket Creation Capability

As an operator splitting a run,
I want the system to create source sub-tickets for the subtasks when the project's ticket connector supports it,
So that each child run is backed by a real, linked ticket in the same source system as the parent — and where the connector cannot create tickets, the split still proceeds internal-only.

**Acceptance Criteria:**

1. **Given** the `TicketSourceAdapter` port (story 3-32), **Then** it gains `CreateSubticketResult createSubticket(TicketRef parentRef, SubticketDraft draft)` and `TicketSourceCapabilities` gains `supportsTicketCreation` (default `false`); adapters that cannot create tickets keep the default and the method need not be implemented (capability-gated at the call site).
2. **Given** the Linear adapter (the first-release reference kind), **Then** it implements `createSubticket` (sub-issue under the parent) and reports `supportsTicketCreation=true`; GitHub/GitLab adapters report `false` for now (additive later) — verified by an adapter capability contract test.
3. **Given** a created sub-ticket, **Then** the adapter posts a parent-link back-reference (reusing `postGovernedRunComment`) so the parent ticket records the split + child references; the child carries a deterministic external reference returned to the caller.
4. **Given** idempotency, **Then** `createSubticket` is keyed so a replayed split does not create duplicate sub-tickets (idempotency key derived from parent run + subtask ordinal — consumed by 3f-5).
5. **Given** redaction (story 1.10), **Then** subtask titles/descriptions sent to the connector pass the same content posture as any outbound artifact; nothing secret is logged (ids/lengths only).
6. **Given** tests, **Then** coverage asserts: capability flag drift; Linear `createSubticket` happy-path + parent-link comment; a `supportsTicketCreation=false` adapter is never called (caller skips to internal-only — proven in 3f-5); idempotent replay; `application.*` ≥80% coverage.

### Story 3f-2: Parent→Child Run Lineage + Terminal `Split` State

As an authorized user,
I want a split to preserve the relationship between the original run and its subtasks, with the original run ending in an explicit terminal state,
So that the governed history shows that one run was decomposed into several, with full lineage — satisfying NFR16's "human explicitly reconciles the record" escape hatch rather than silently breaking the 1:1 invariant.

**Acceptance Criteria:**

1. **Given** the next-free Flyway head, **Then** an additive `parent_run_id` (nullable text FK → `workflow_runs.public_id`) is added to `workflow_runs` and indexed; replay-safe; in `FlywaySchemaContractTest`. Existing rows stay `NULL` (parity — no lineage).
2. **Given** the `WorkflowState` registry, **Then** a new **terminal** state `SPLIT` (`split`) is added (mirroring `cancelled_for_takeover` from story 3-22): registry value + `current_state` CHECK widening (Flyway) + state-machine entry (legal transitions **into** `SPLIT` from `WaitingForSpecApproval` and `WaitingForReview`; none out). Drift-tested against the DB CHECK + API schema.
3. **Given** the read model, **Then** `WorkflowRunSnapshot` / run summary views expose `parentRunId` and (for a parent) the child run ids; the relationship is queryable by parent and by child (consumed by FE in 3f-5).
4. **Given** a new `WorkflowEventType SPLIT("workflow.split")`, **Then** it is appended to the parent on termination and mirrored into both fixture sites (OpenAPI byte-identical), carrying `childRunIds` via allow-listed detail keys (ids only, count bounded).
5. **Given** intake (`WorkflowCommandService.submit` / `WorkflowRunCreatePort.create`), **Then** the create seam accepts an optional `parentRunId` so a child run records its parent at creation (default `null` = top-level run, byte-identical to pre-3f).
6. **Given** tests, **Then** coverage asserts: Flyway/registry/CHECK/state-machine drift for `SPLIT`; `parent_run_id` round-trips; transition into `SPLIT` legal only from the two gates; `workflow.split` event drift; parity (a normal top-level submit is unchanged); `application.*` ≥80% coverage.

### Story 3f-3: Run-Dependency Graph + `WaitingForDependencies` Gating

As an operator,
I want to declare that one run can only start after other runs complete,
So that I can sequence decomposed work (e.g. "Task 3 starts only after Task 1 and Task 2 complete") and the system holds dependent runs until their prerequisites are done.

**Acceptance Criteria:**

1. **Given** the next-free Flyway head, **Then** an additive `run_dependencies(run_id text FK, depends_on_run_id text FK, PK(run_id, depends_on_run_id))` join table is created; replay-safe; in `FlywaySchemaContractTest`. A self-edge (`run_id == depends_on_run_id`) is rejected by CHECK.
2. **Given** a new non-terminal `WorkflowState WAITING_FOR_DEPENDENCIES("waiting_for_dependencies")`, **Then** it is added (registry + `current_state` CHECK + state-machine: a run may enter it at creation and leave it to `Investigating` on release); drift-tested. A run with **no** dependencies never enters this state (parity).
3. **Given** dependency declaration, **Then** a `RunDependencyService` writes edges with an **acyclic guard** (declaring an edge that would create a cycle throws `RUN_DEPENDENCY_CYCLE`, a new three-sites error code); edges are only declarable while both runs are pre-execution (consumed by 3f-5 at commit; a standalone REST/CLI declare path is provided for non-split use).
4. **Given** gated dispatch, **Then** a run created **with** unmet dependencies is parked in `WaitingForDependencies` and **not** auto-dispatched (the one place `dispatchSpecGeneration` is suppressed at creation); a run with all-satisfied (or zero) dependencies dispatches normally.
5. **Given** a release resolver, **Then** when any run reaches `COMPLETED`, a `RunDependencyReleaseService` finds its dependents and, for each whose **every** prerequisite is now `COMPLETED`, transitions it `WaitingForDependencies → Investigating` and dispatches it (idempotent, best-effort, swallows + logs `RuntimeException` so one stuck dependent never strands the completing run's callback).
6. **Given** a **failed** prerequisite, **Then** dependents remain in `WaitingForDependencies` (they are **not** released and **not** auto-failed) and the blocked state + the failed blocker are operator-visible; no cascade-cancel in this epic (documented forward option).
7. **Given** the read model + FE, **Then** a run view exposes its prerequisites and its blocked-on status; `WaitingForDependencies` renders as an explicit waiting state (not "stuck"); allowed-actions for a `WaitingForDependencies` run are view-only (no spec/plan actions yet).
8. **Given** tests, **Then** coverage asserts: Flyway/registry/CHECK/state-machine drift for `WaitingForDependencies`; cycle guard (`RUN_DEPENDENCY_CYCLE`); a dependent parks and is **not** dispatched; completing the last prerequisite releases + dispatches it (IT); a failed prerequisite leaves it blocked; zero-dependency parity; `application.*` ≥80% coverage.

### Story 3f-4: LLM Split-Proposal Channel + Three-Action Feedback Loop

As an operator at the spec or implementation-review gate,
I want an LLM to propose how to split the current run into smaller subtasks (with suggested dependencies), and to approve, decline, or re-propose-with-feedback,
So that I get governed assistance decomposing oversized scope without surrendering the decision — and I can iterate the proposal until it is right before any runs are created.

**Acceptance Criteria:**

1. **Given** allowed-actions (2.14), **Then** three new actions are added (registry + placeholder + pin drift): `REQUEST_SPLIT("request_split")`, `DECLINE_SPLIT("continue_as_single")`, `REPROPOSE_SPLIT("repropose_split")` (plus `APPROVE_SPLIT`, owned by 3f-5), surfaced for the gate role (product_reviewer at `WaitingForSpecApproval`, developer at `WaitingForReview`) as an **advisory overlay** at the existing gate — **no** new gate state (the parent stays parked at its gate until approve).
2. **Given** `REQUEST_SPLIT`, **Then** a reviewer-style LLM call (reusing the 3d-2 `RunnerStage.REVIEW` substrate over the spec/plan artifact) produces a **structured split proposal** — `subtasks[] {ordinal, title, scope}` + `dependencies[] {fromOrdinal, toOrdinal}` — emitted via a fenced ` ```split ` JSON block from both `runner.mjs` entrypoints (byte-identical, OpenSpec fence-split precedent) + both offline mocks emit a deterministic 2-subtask, 1-dependency proposal.
3. **Given** the proposal must survive until the operator acts, **Then** it is **persisted** against the run (a `split_proposals` row or the generic `step_reviews` payload — chosen in the story to avoid a new table where the verdict store suffices) and surfaced in the gate Decision Bar via a new **Split Proposal Panel** (proposed subtasks + dependency edges, editable selection deferred — whole-proposal actions only).
4. **Given** `REPROPOSE_SPLIT`, **Then** the operator's free-text feedback re-runs the proposal call with the feedback materialized as a **redaction-policed referenced input** (reusing the `priorFeedbackReferences` bundle mechanism from spec-rejection / 3e-2 — never inlined past the 2KB cap); a `split_proposal_loop_count` is tracked (mirroring `spec_rejection_loop_count`) for distinct idempotency keys + an escalation-marker safety valve.
5. **Given** `DECLINE_SPLIT` ("continue as one ticket"), **Then** the proposal is dismissed, the parent stays at its gate, and the normal gate actions (`approve_spec`/`reject_spec` or `accept_implementation`/`reject_implementation`) resume — byte-identical to a run that was never split-proposed.
6. **Given** REST + CLI, **Then** `POST /workflows/{id}/split/request`, `/split/repropose`, `/split/decline` + CLI parity drive a `SplitProposalService`; `GET /workflows/{id}/split-proposal` serves the current proposal; OpenAPI + `schema.d.ts` regenerate (NOT byte-identical).
7. **Given** redaction + provenance, **Then** the proposal input (spec/plan + feedback) and output pass the redaction/secret-fixture gate; the proposing model identity is recorded (self-vs-producer flagged like 3d-2).
8. **Given** tests, **Then** coverage asserts: the 4 new AllowedActions drift; runner fence-split (parses / absent omits / malformed non-fatal, both runners); proposal persists + is served; re-propose carries feedback + bumps loop count + honors escalation marker; decline restores normal gate actions; redaction fixture over the feedback file; OpenAPI/`schema.d.ts` regen; `application.*` ≥80% coverage.

### Story 3f-5: Split Commit Fan-Out

As an operator who approved a split proposal,
I want the system to create the subtasks — as real sub-tickets where possible, otherwise internal-only — wire their dependencies, and end the original run,
So that the decomposition is committed as governed child runs with preserved lineage, on a best-effort basis that never half-terminates the parent.

**Acceptance Criteria:**

1. **Given** the `APPROVE_SPLIT("approve_split")` action (gate role, over a current proposal), **Then** `SplitCommitService.commit` runs **best-effort + non-transactional** (the story 3-18 pattern): each subtask is processed in its own transaction so one subtask's failure does not poison the rest.
2. **Given** per subtask, **Then** the commit: (a) creates a sub-ticket via `TicketSourceAdapter.createSubticket` **iff** `supportsTicketCreation` (3f-1), else proceeds **internal-only** linking the child to the parent's ticket; (b) mints a child run via `WorkflowRunCreatePort.create` in the parent's `projectId` with `parentRunId` set (3f-2); (c) records the proposed dependency edges (3f-3).
3. **Given** dependency-gated dispatch, **Then** a child with **no** unmet dependencies dispatches its spec generation immediately; a child **with** dependencies is parked in `WaitingForDependencies` (3f-3) — e.g. spec=Task1/Task2 dispatch, Task3 (depends on 1+2) parks.
4. **Given** the parent-termination guard, **Then** the parent transitions to terminal `SPLIT` (3f-2) + appends `workflow.split` **only if ≥1 child run was created**; if **zero** children were created (every subtask failed), the split aborts, the parent stays at its gate, and a clear error is returned — the parent is never left half-terminated.
5. **Given** idempotency, **Then** the commit is keyed (parent run + proposal id) and per-child keyed (parent + ordinal) so a replayed approve neither double-creates sub-tickets/children nor double-terminates the parent.
6. **Given** the result + FE, **Then** the response reports per-subtask outcome (created / failed-internal-only-fallback / failed); the FE Split Proposal Panel (3f-4) shows the commit result and links parent→children; the new lineage renders in the run view (3f-2 read model).
7. **Given** a connector with no creation support, **Then** the whole split still succeeds internal-only (children link to the parent ticket) — proving the 3f-1 capability fallback end-to-end.
8. **Given** tests, **Then** a full IT proves request→(re-propose)→approve → N children created (mixed sub-ticket + internal-only) with lineage + dependency edges, the dependent child parked while others dispatch, parent → `SPLIT`; the **zero-child guard** (all subtasks fail → parent untouched); idempotent replay; `application.*` ≥80% coverage.

### Story 3f-6: Run Review Queue Project Attribution + Project Filter

As an authorized user,
I want to see which project each run belongs to in the Run Review Queue and filter the queue by project,
So that with multiple projects (and split-fan-out multiplying run counts) the queue stays navigable — completing the queue-scoping that story 3c-9 deferred.

**Acceptance Criteria:**

1. **Given** story 3c-9 AC6 was deferred as backend-blocked (run list DTOs carry no project field; `/workflows` has no `projectId` filter), **Then** the run-list read model + the queue run DTO gain the run's `projectId` + project name/slug (resolved from the existing `projectId` FK on runs, 3c-7) — no new persistence.
2. **Given** the `/workflows` list endpoint, **Then** it accepts an optional `projectId` (slug or `prj_` id) filter that scopes the returned runs to that project; absent → all projects (byte-identical to pre-3f-6); an unknown project id → `PROJECT_NOT_FOUND` (existing code, no new error code); OpenAPI + `schema.d.ts` regenerate.
3. **Given** the Run Review Queue UI (Epic 2/3c-9), **Then** each queue item shows its project attribution and a **project filter control** (reusing the 3c-9 project selector) scopes the queue; the filter composes with the existing archived/state filters; selection persists per the existing queue-state pattern.
4. **Given** accessibility, **Then** the filter control + project column meet WCAG 2.1 AA and are axe-clean; the announcer reflects filter changes (the `useLiveAnnouncement` one-commit-lag pattern is honored — assert via `waitFor`).
5. **Given** performance, **Then** the project-scoped list query stays within the NFR25/NFR26 read-path budgets (indexed on `project_id`, already present from 3c).
6. **Given** tests, **Then** coverage asserts: run DTO carries project attribution; `/workflows?projectId=` scopes results + unknown id → `PROJECT_NOT_FOUND`; no-filter parity; OpenAPI/`schema.d.ts` drift; FE Vitest (filter scopes the rendered queue) + axe; `application.*` ≥80% coverage.

### Cross-Cutting Notes

- **Foundation-gate widening:** the new `AllowedAction`s (3f-4 `request_split`/`continue_as_single`/`repropose_split`, 3f-5 `approve_split`), the new `WorkflowEventType` (`workflow.split`), the new `WorkflowState`s (`SPLIT` terminal, `WaitingForDependencies` non-terminal), the new error code(s) (`RUN_DEPENDENCY_CYCLE`, three-sites), the `parent_run_id` + `run_dependencies` schema, the `supportsTicketCreation` capability, and the additive split-proposal runner-contract fields are drift-tested at the existing gates — folded into each story, no separate gate story.
- **NFR16 reconciliation:** the split path is the first feature to legitimately break the 1:1 ticket↔run shape; ADR-0029 documents it as the "human explicitly reconciles the record" case NFR16 already permits (the operator's `approve_split` is the explicit reconciliation).
- **Documentation:** a `docs/complex-ticket-flow-walkthrough.md` (split a run → review/re-propose the proposal → approve → child runs + dependencies → portfolio queue filter); new vocabulary (`split`, `subtask`, `child run`, `run dependency`, `WaitingForDependencies`) confirmed in `docs/glossary.md` against NFR43 (minimize new concepts — justify each).
- **FRs covered:** **3f-1..3f-5** deliver **FR70** (split/decompose, lineage-preserving) and **FR71** (run dependencies / sequenced execution). **3f-6** delivers **FR72** (queue project attribution + filter) and completes the deferred story-3c-9 AC6. This epic introduces **new PRD scope** (FR70/FR71/FR72) — it is not an activation of deferred work.
- **Forward options (out of scope):** cascade-cancel of dependents on a failed prerequisite; GitHub/GitLab `createSubticket`; per-subtask proposal editing in the Split Proposal Panel; true purge of split-parent records (Epic 5 owns purge).
