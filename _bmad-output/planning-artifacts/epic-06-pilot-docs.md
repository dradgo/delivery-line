## Epic 6: Adoption Polish & Pilot Documentation

A pilot user can follow documented setup, a low-risk ticket happy-path tutorial, and a failed-run recovery walkthrough to run their first governed ticket end-to-end without live assistance — proving the PRD's pilot-success criterion. Hardens concept vocabulary, minimizes friction in first-run onboarding, and closes out the NFRs that define pilot-readiness.

**Documentation-as-incremental-milestone model (per refinement R2):** Each feature epic (E1–E5) owns its own tutorial/walkthrough increment as stories inside that epic (`docs/quickstart.md` from story 1.22, `docs/pm-loop-walkthrough.md` from story 2.29, `docs/execution-walkthrough.md` from story 3.36, `docs/failed-run-recovery-walkthrough.md` from story 4.27, `docs/exported-report-walkthrough.md` from story 5.12). Epic 6 is the final **consolidation and pilot-readiness audit** pass — verify end-to-end tutorial flow, tighten concept vocabulary, run pilot-onboarding dry-runs, close NFR42/NFR44/NFR45 gaps. This prevents Epic 6 from becoming a cliff that blocks pilot launch and keeps documentation co-located with the features it describes.

### Story 6.9: Localhost REST Binding + Workflow Read Endpoints

As a pilot installer or future UI (Epic 2),
I want the Spring Boot REST server bound strictly to localhost with initial read endpoints `GET /api/v1/workflows`, `GET /api/v1/workflows/{workflowRunId}`, and `GET /api/v1/workflows/{workflowRunId}/events`,
So that Epic 2's React review UI can consume the same application services the CLI uses and REST is proven safe-by-default (fail-closed on non-loopback binding attempts) without requiring local auth tokens in Phase 1.

Note: this story was intentionally moved out of Epic 1 and deferred into Epic 6 so the localhost REST/OpenAPI baseline can be implemented later without blocking the current CLI-first foundation sequence.

**Acceptance Criteria:**

1. **Given** the `adapters.rest` package, **Then** `WorkflowController` exposes three read endpoints: `GET /api/v1/workflows` (list with optional filters), `GET /api/v1/workflows/{workflowRunId}` (single run detail), `GET /api/v1/workflows/{workflowRunId}/events` (event history for a run) — all calling `WorkflowInspectionService` (story 1.15 wires the service methods already used by CLI `status`/`history`).
2. **Given** REST response bodies, **Then** JSON uses `camelCase`, timestamps serialize as ISO-8601 UTC (`2026-04-24T14:32:15Z`), IDs carry their registered public prefixes (`run_`, `evt_`, etc.), and response DTOs are direct resource shapes (not a generic `{data: ...}` envelope) per architecture format patterns.
3. **Given** localhost-only binding, **Then** `application.yml` configures `server.address=127.0.0.1` by default; an explicit unsafe development override (`deliveryline.rest.bind-address=0.0.0.0` + `deliveryline.rest.unsafe-network-bind=true`) is required to bind non-loopback and emits a WARN-level log on startup.
4. **Given** a non-loopback bind attempt without the unsafe override, **When** the app starts, **Then** startup fails fast with `DOCTOR_REST_BIND_UNAVAILABLE` error code and clear remediation in the message.
5. **Given** the CI matrix and smoke tests, **Then** a bundled-jar smoke test launches the backend, asserts REST binds to `127.0.0.1:8080` (or configured port), issues a `GET /api/v1/workflows` and validates response schema, then shuts down cleanly.
6. **Given** OpenAPI via `springdoc-openapi`, **Then** the spec is served at `/v3/api-docs` (JSON) and Swagger UI at `/swagger-ui.html` — both localhost-bound; the OpenAPI doc is committed in `backend/src/main/resources/openapi/` as a reference snapshot and regenerated in CI to detect drift.
7. **Given** Problem Details error responses (story 1.8), **Then** the REST endpoints emit `application/problem+json` for 4xx/5xx — tests assert stable error codes for missing runs (`RUN_NOT_FOUND`), malformed IDs (`INVALID_ID_PREFIX`), and inspection timeouts.
8. **Given** performance targets (NFR25/26/27), **Then** REST `GET /workflows/{id}` returns within 2 seconds and `GET /workflows/{id}/events` returns within 5 seconds for pilot-size runs — contract test enforces against seeded fixtures.
9. **Given** read-only scope in this story, **Then** all mutation endpoints (approve-spec, reject-spec, retry, etc.) are absent from `WorkflowController` — Epic 2+ stories add them through the shared command model (story 1.7).
10. **Given** `correlationId` from story 1.19, **Then** every REST request carries the ID through the handler and stamps it on response headers (`X-Correlation-Id`) and Problem Details `instance` field.
