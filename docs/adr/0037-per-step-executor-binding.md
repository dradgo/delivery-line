# ADR 0037 — Per-Step Executor Binding

**Status:** Proposed (2026-07-19) — to be confirmed on merge of Epic 3m stories 3m-4/3m-5
**Driver:** Epic 3m (Configurable Workflow Definitions + BMAD-Method Preset), story 3m-1 (spike). Each step of a configurable definition must run on an operator-chosen executor — "configurable executors per step" is the epic's headline. This ADR fixes **what an executor binding is, how a runner "becomes" a BMAD agent, how the binding resolves at dispatch, and how BMAD's feedback loops are expressed.** It is the executor-side companion to ADR [0036](0036-configurable-workflow-run-model.md) (the run-model).

## Context

Epic 3d already made the *executor* of a stage configurable: the runner-kind registry (`org.dradgo.domain.registry.RunnerKind`: `claude`/`codex`/`manual`) is selectable per project/stage, per-project credentials are stored encrypted (`project_credentials`, ADR [0013](0013-credential-encryption.md)) and resolved via `org.dradgo.application.project.ProjectConnectorResolver`, and reviewer models ride that same credential model (ADR [0026](0026-per-step-advisory-reviewer-model.md)). Epic 3m generalizes this from the fixed stages to *arbitrary definition steps*, and adds one new axis: a step must be able to name **which BMAD agent** the runner acts as.

Two live-codebase facts (confirmed during the 3m-1 spike, `runners/RUNNER_CONTRACT.md` + `runners/claude/README.md`) make the "runner becomes a BMAD agent" mechanism concrete and low-risk:

1. **The runner images already carry Claude Code's skill-discovery mechanism.** Story 3a-7 vendored the `obra/superpowers` skills collection into the image and exposed it on Claude Code's personal-skills dir — `~/.claude/skills/<skill>/SKILL.md` (confirmed against CLI `2.1.149`), Codex `~/.agents/skills/`. Skills are static files `COPY`'d in (no network, offline-safe). The **BMAD agents are themselves Claude Code skills** (`.claude/skills/bmad-*/`), so "make a runner act as the architect" = vendor `.claude/skills/bmad-*` the same way superpowers is vendored, and get the headless prompt to activate the named skill.

2. **A prompt-augmentation seam already exists.** The OpenSpec 3a-8 layer (`DELIVERYLINE_RUNNER_OPENSPEC=true`) has the entrypoint append a "prompt delta" to the generated prompt, gated on a backend-injected env flag — without any change to the frozen `context-bundle.v1` schema or the runner↔backend mount contract. A `bmad_role` is the same shape: an env flag naming the BMAD skill, driving a prompt nudge.

The one genuinely unproven thing — **does a skill reliably *fire* in a single-prompt headless run (`claude -p`, no human, no slash command)?** — is not new to Epic 3m. It is the *same* open question stories 3a-6 (OpenSpec) and 3a-7 (superpowers) hit and explicitly deferred: *"Whether a skill fires in a single-prompt headless run … needs a live run (egress + a credential) the offline tier does not have … deferred to real execution (story 3.8)."* The 3m-1 spike inherits that precedent (see the findings note); this ADR records the *binding design*, and the live-activation confirmation is the story's real-run gate.

## Decision

**An executor binding is `{ runner_kind, project credential, bmad_role }`, resolved at dispatch through the existing `ProjectConnectorResolver`. No new credential subsystem. The BMAD role is delivered to the runner as a prompt nudge over a vendored skill, modeled on the OpenSpec 3a-8 seam.**

1. **Binding shape.** Each definition step binds:
   - `runner_kind` — an existing `RunnerKind` (`claude`/`codex`/`manual`). No new kind is introduced (the "generic engine + BMAD role prompt" decision, not a bespoke `bmad-agent` kind).
   - a **per-project credential** — the same `project_credentials` row a normal runner uses (encrypted at rest, ADR 0013), resolved via `ProjectConnectorResolver`. **No new credential subsystem** (mirrors ADR 0026).
   - a `bmad_role` — a nullable selector naming the BMAD agent for the step (e.g. `architect`), drawn from the role-prompt catalog (3m-5).

2. **How a runner "becomes" a BMAD agent (the invocation mechanism).**
   - The `.claude/skills/bmad-*` skills are **vendored into the runner images** exactly as `obra/superpowers` is (static `COPY`, offline-safe, on the personal-skills discovery path). This is a runner-image change owned by 3m-5, mirrored across **both** runner Dockerfiles per the RUNNER_CONTRACT change rule.
   - At dispatch the backend injects a `bmad_role` env flag (working name `DELIVERYLINE_RUNNER_BMAD_ROLE=<skill>`), and the entrypoint appends a **prompt nudge** naming the skill/agent to the generated prompt — the same append-to-prompt mechanism the OpenSpec 3a-8 delta uses, gated the same way (flag absent ⇒ byte-identical legacy behavior). No change to the `context-bundle.v1` schema, mounts, or exit codes.
   - **`manual` is the fallback**, not a lesser path: any phase whose agent cannot be driven reliably headlessly is bound `runner_kind=manual` and parks in `WAITING_FOR_MANUAL_EXECUTION` (3d-3/3d-4). The default gating in the 3m-5 seed encodes the per-phase automatable-vs-manual choice from the spike's real-run findings.

3. **Resolution at dispatch.** A step's per-project credential is resolved at dispatch through an **existing secret-resolution seam**. NOTE — there are **two** live seams and 3m-4 must choose deliberately (this ADR fixes the requirement, not the wiring): ordinary (non-REVIEW) runner dispatch resolves the kind's credential via `RunnerSecretsService.resolveSecretsForRunner` (`DockerRunnerAdapter`), whereas the per-project *reviewer* credential (ADR 0026) resolves via `ProjectConnectorResolver` — and that reviewer path **silently falls back to the host secret** when no per-project credential is set. An executor binding that wants a genuinely per-project credential must therefore either extend `RunnerSecretsService` to honor the binding, or reuse `ProjectConnectorResolver` **with the silent host-fallback explicitly disabled**, so an unconfigured step fails fast with a typed `STEP_EXECUTOR_NOT_CONFIGURED` rather than inheriting the reviewer fallback (never a silent default, never an opaque 500 — [[adapter-exception-to-rest-is-opaque-500]] guarded). `STEP_EXECUTOR_NOT_CONFIGURED` may itself need to split "no binding" from "binding present but no credential for the kind" (precedent: `UNSUPPORTED_CONNECTOR_KIND` vs `DOCTOR_RUNNER_SECRET_MISSING`) — 3m-4's call. A same-model choice across steps is permitted but recorded for provenance.

4. **Preset immutability + per-project override.** The shared BMAD **preset** is a `builtin` definition and is **immutable**. Per-project executor choices for preset steps are stored as **per-project step overrides**, never mutations of the shared preset rows — so two projects can run BMAD with different executors. Resolution precedence is explicit: per-project override → step default. (A custom definition, being project-authored, stores bindings on the step rows directly.)

5. **BMAD loops via rerun-from-step, not native branching.** BMAD's feedback loops (pm↔analyst spec revision, architect rework, dev↔review) are expressed with the Epic 4 `RecoveryService.rerunFromStep` model (ADR [0034](0034-rerun-safe-boundaries.md)): an operator rejects a gated step's artifact and reruns that step, feedback folded into the re-run's context bundle, history append-only (NFR4), the superseded approval invalidated, downstream artifacts superseded by **lineage-graft** (not a column flip). **This is an EXTENSION of ADR 0034, not free reuse:** `rerunFromStep` today accepts a two-value `SafeRerunStep` enum {`investigating`, `executing`} with no step-index, and its approval-invalidation has exactly two kinds (`spec`/`implementationPlan`). Targeting an arbitrary definition step by cursor index requires 3m-3/3m-7 to widen the `rerunFromStep` target (a step index/key, not the 2-value enum), add the transition edges the re-dispatch needs (see ADR 0036), and generalize the approval-kind model to the definition's human gates. ADR 0034's **safety guarantees** (bounded target, approval invalidation, lineage-graft) are the model to preserve; its concrete 2-value surface is not sufficient as-is. **No native branching / automatic loop-back transitions are added in Phase 1.**

## Alternatives Considered

### Alt 1 — A new first-class `bmad-agent` runner kind
**Rejected.** A dedicated kind that natively "knows" the BMAD agents would duplicate the `claude`/`codex` dispatch, secret-injection, and contract machinery, and couple the runner registry to one method. The vendored-skill + prompt-nudge approach reuses the existing runner kinds and the *already-shipped* skill-discovery mechanism, and generalizes to any skill-defined role.

### Alt 2 — Native branching transitions for BMAD loops (per-step `on_reject_goto`)
**Rejected for Phase 1.** Automatic loop-back would require new transition-table edges (the very expansion ADR 0034 avoids) and a branching model the run-model (ADR 0036) deliberately keeps linear. `rerunFromStep` already delivers the operator value (re-run a rejected phase with feedback) with all of Epic 4's governance. A future epic may add native loops; this ADR records why they are deferred and what they would need (per-step reject-target metadata + new generic transition edges).

### Alt 3 — Clone the BMAD preset per project instead of per-project overrides
**Rejected.** Cloning the whole preset per project on first executor-config would fork the preset's step definitions and make a future preset improvement un-inheritable by existing projects. A thin per-project override table keeps the shared preset the single source of the step *sequence* while letting each project diverge only on *executor choice*. (An explicit clone-to-edit remains available in 3m-9 for projects that want a genuinely custom variant.) **Open item for 3m-9:** when a project uses clone-to-edit to fork the preset into a custom definition, whether its existing per-project overrides are copied onto the clone, dropped, or left orphaned is unspecified here — 3m-9 owns that rule.

### Alt 4 — Carry the BMAD role inside the `context-bundle.v1` payload
**Rejected.** The bundle schema is frozen `additionalProperties: false` and the RUNNER_CONTRACT change rule makes schema changes expensive (mirror both runners, bump version, re-validate). The env-flag + prompt-nudge seam (Alt to a schema field) is exactly how stage injection (`DELIVERYLINE_RUNNER_STAGE`) and the OpenSpec layer already work — no schema churn.

## Consequences

- **3m-2 schema:** a `bmad_role` selector column on `workflow_definition_steps` + a per-project step-override table; `bmad_role` values are registered/drift-tested (3m-2/3m-10).
- **3m-5 runner-image change:** vendor `.claude/skills/bmad-*` into both runner images (mirror rule) + wire the `DELIVERYLINE_RUNNER_BMAD_ROLE` prompt-nudge in both entrypoints, gated flag-off-byte-identical (twin of the OpenSpec 3a-8 layer). The `:latest` images do **not** auto-rebuild on merge — a rebuild + `--self-test` is a done-criterion ([[runner-image-stale-causes-exit-20]]).
- **3m-4 binding + resolution:** REST+CLI to set `{runner_kind, credential, bmad_role}` per step (or per-project override); resolution via `ProjectConnectorResolver`; typed `STEP_EXECUTOR_NOT_CONFIGURED`.
- **Live-activation gate:** whether `claude -p`/`codex exec` reliably fires a vendored `bmad-*` skill is confirmed only by a real credentialed run (egress + credential) — the same deferred-real-execution posture as OpenSpec/superpowers activation. The 3m-1 findings note carries the runbook; a documented "not reliably fired ⇒ default that phase to `manual`" is an acceptable outcome, a fabricated confirmation is not.
- **No new credential subsystem, no new runner kind, no bundle-schema change, no native branching** — the binding rides entirely on already-shipped seams.
