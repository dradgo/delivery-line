# Registry Extension Recipe — the sites that must change together

> **Knowledge-capture deliverable (story 3c.13, retro action D1).** This is the
> unwritten lesson that recurred across Epics 1, 2, and 3: adding "just one value"
> to a governed registry is almost never additive-only. Each registry has a
> **contract or foundation test** that goes red until an exhaustive set of mirror
> sites is updated in the same change — and those tests run in the **`mvn verify`
> integration tiers** (the `architecture` Failsafe execution, or `-Pfoundation-gate`
> for the foundation contracts), **not** the fast `mvn test` Surefire tier, so the
> unit tier alone will not catch the gap.

## How to use this doc

When you are about to add a value to one of the registries below, find its recipe,
change **every** site it lists in one commit, and run the named red test before you
push. The recurring failure mode is changing the enum, watching `mvn test` stay
green, and discovering the drift only in CI's `verify` (or foundation-gate) job (or
worse, at runtime).

The registries live under `deliveryline-backend/src/main/java/org/dradgo/domain/registry/`
and `.../application/workflow/commands/`. The governing tests live under
`deliveryline-backend/src/test/`.

### Running the governing tests locally

The governing tests sit in two `mvn verify` integration tiers — know which one
catches your registry (either way, invoke the lifecycle **phase**, not the plugin
goal — a direct `failsafe:` goal crashes the fork on the unsubstituted jacoco
`@{argLine}`):

- **Architecture tier (default `mvn verify`).** `RegistryContractTest` is
  `@Tag("architecture")`, so it runs in the default Failsafe build — it is excluded
  only from the fast `mvn test` Surefire tier, **not** gated behind a profile. This
  is the tier that catches **Recipe 1** (WorkflowEventType) and **Recipe 3**
  (DomainErrorCode) drift:

  ```
  ./mvnw -pl deliveryline-backend -am verify -Dfrontend-maven-plugin.skip=true
  ```

- **Foundation-gate tier (`-Pfoundation-gate`).** Only `@Tag("foundation-gate")`
  tests run here (the profile sets `<groups>foundation-gate</groups>`). This is the
  tier that catches **Recipe 2** (WorkflowCommand → `CommandModelSymmetryFoundationContract`):

  ```
  ./mvnw -pl deliveryline-backend -am -Pfoundation-gate verify -Dfrontend-maven-plugin.skip=true
  ```

See [`../testing/snapshots-vs-assertions.md`](../testing/snapshots-vs-assertions.md)
for the OpenAPI snapshot regeneration flow some of these recipes also touch.

## Recipe 1 — Adding a `WorkflowEventType`

**Registry:** `domain/registry/WorkflowEventType.java` (e.g.
`LINEAR_COMPLETION_SYNC_FAILED("linear.completionSyncFailed")`).

Adding a constant is **not** additive-only. The wire value must be mirrored into two
test fixtures.

**Sites that must change together:**

1. The enum constant in `WorkflowEventType.java` itself.
2. `src/test/resources/contracts/events/workflow-event-types.fixture.json` — append
   the new **wire value** to the `workflowEventTypes[]` array.
3. `src/test/resources/fixture-event-streams/schema/workflow-events-response.schema.json`
   — add the wire value to `properties.eventType.enum`.

**Red test:** `RegistryContractTest`
(`workflowEventTypesUseDotSeparatedLowerCamelAndStayAlignedWithFixture`) asserts the
enum equals the fixture list; the fixture-stream schema validates event-stream
fixtures against its `eventType` enum. `RegistryContractTest` is `@Tag("architecture")`,
so it runs in the **default `mvn verify`** architecture tier — excluded only from the
fast `mvn test` Surefire tier, **not** behind `-Pfoundation-gate`.

**`openapi.json` is NOT auto-derived.** The committed
`src/main/resources/openapi/openapi.json` `eventType` enum is regenerated by hand
(see the snapshot recipe below), but regenerating produces **byte-identical** output
for a WorkflowEventType — so no `openapi.json` change is required for this registry.
(Contrast a `DomainErrorCode`, which *is* in the placeholder manifest — Recipe 3.)

**Watch:** event **detail keys** are a separate concern. Prefer **reusing** an
existing allow-listed `WorkflowEventDetailKeys` value (e.g. `LINEAR_TICKET_REFERENCE`,
`FAILURE_CATEGORY`, `ERROR_CLASS`) over adding a new one, which would also touch the
history schema and its parity test.

## Recipe 2 — Adding a `WorkflowCommand`

**Registry:** `application/workflow/commands/WorkflowCommand.java` is a **sealed**
interface. A new command (e.g. `AcceptImplementationCommand`,
`TakeoverWorkflowCommand`) fans out at **compile time** and at the **foundation
gate**.

**Sites that must change together:**

1. Add the new command type to the `permits` list of the sealed `WorkflowCommand`
   interface — **otherwise the project does not compile.**
2. Add a new `case` to the exhaustive `switch (command)` in
   `application/idempotency/WorkflowCommandFingerprintFactory.java` — also a
   **compile-time** failure (the switch is exhaustive over the sealed type).
3. Add the command class to the hard-coded `Set<Class<?>> EXPECTED_PERMITS` in
   `test/.../foundation/CommandModelSymmetryFoundationContract.java`.

**Red test:** `CommandModelSymmetryFoundationContract` asserts
`Set.of(WorkflowCommand.getPermittedSubclasses()).equals(EXPECTED_PERMITS)`. This is
**foundation-gate only** — the fast Surefire tier compiles and passes; the gate
reddens until `EXPECTED_PERMITS` is updated in lockstep (verified on story 3.20:
`AcceptImplementationCommand` passed the full unit tier but failed
`-Pfoundation-gate verify`).

**Fingerprint field discipline (site 2):** the fingerprint **excludes** free-text
(`reason` / `reasonText`) so that wording edits on the same review replay
idempotently, and **includes** the semantic-identity fields:
`workflowRunId`, `artifactId`, `artifactVersion`, `contextVersion`, `reviewerRole`,
and (for rejections) `taggedFeedback`. Keep the short field names
`artifactVersion` / `contextVersion` (they *are* the expected versions) — the verbose
`expected…` names belong only to the REST DTOs.

**Worked mini-example** — adding `TakeoverWorkflowCommand`:

```java
// 1. WorkflowCommand.java
public sealed interface WorkflowCommand
    permits SubmitWorkflowCommand, /* … */ TakeoverWorkflowCommand { … }

// 2. WorkflowCommandFingerprintFactory.java  (exhaustive switch)
case TakeoverWorkflowCommand takeover -> {
    append(digest, takeover.workflowRunId());
    append(digest, takeover.reviewerRole());
    // reason is intentionally NOT fingerprinted
}

// 3. CommandModelSymmetryFoundationContract.java
private static final Set<Class<?>> EXPECTED_PERMITS =
    Set.of(SubmitWorkflowCommand.class, /* … */ TakeoverWorkflowCommand.class);
```

The note "a service-only command whose REST endpoint is deferred just needs the
`EXPECTED_PERMITS` entry" holds: the contract round-trips only the surfaced commands,
so a command with a later REST story (e.g. 3.20 → REST in 3.23) only needs the
permits-set entry until the endpoint lands.

## Recipe 3 — Adding a `DomainErrorCode`

**Registry:** `domain/registry/DomainErrorCode.java`. Three coordinated edits or CI
goes red.

**Sites that must change together:**

1. The enum value in `DomainErrorCode.java`.
2. `adapters/rest/ProblemDetailsCatalog.java` — `register(...)` an HTTP status,
   title, and retryable flag. Its **static initializer asserts it maps every code**;
   a gap makes the class fail to load, so the `@RestControllerAdvice` can no longer
   map *any* `DomainException` (surfaces as `WorkflowAdapterEquivalenceTest` errors:
   "Servlet Request processing failed: DomainException").
3. `src/test/resources/contracts/openapi/registry-api-schema-placeholders.json` →
   `problemTypeUris` — add
   `"CODE": "https://deliveryline.local/problems/<code-lowercased-hyphenated>"`.

**Red test:** `RegistryContractTest.domainErrorCodesStayAlignedWithProblemTypeOwnershipManifest`
(`@Tag("architecture")` — the **default `mvn verify`** tier, **not** `-Pfoundation-gate`).
Site 2's exhaustiveness is enforced at class-load time; site 3's manifest-drift test is
excluded from the fast `mvn test` Surefire tier, so a plain `mvn test` will not catch a
missing manifest entry — run `mvn verify`.

Unlike a `WorkflowEventType` (Recipe 1), a `DomainErrorCode` **is** in the
placeholder manifest — so site 3 is mandatory here.

## Recipe 4 — Widening a role-scoped enum behind a shared DB CHECK (`RejectionTaxonomy`)

**Registry:** `domain/registry/RejectionTaxonomy.java`. This is the subtlest recipe,
because the failure is **not** a red test — it is a **silently relaxed validation**.

`RejectionTaxonomy` is **one** enum holding two role-scoped subsets: 3 product values
(`MISSING_SCOPE`, `UNCLEAR_SPECIFICATION`, `MISUNDERSTOOD_IMPLEMENTATION`) for
`ApprovalService.rejectSpec` (`reviewerRole=product_reviewer`), and 5 developer values
(`INCORRECT_APPROACH`, `INCOMPLETE_IMPLEMENTATION`, `QUALITY_ISSUE`,
`BREAKS_EXISTING_FUNCTIONALITY`, `OUT_OF_SCOPE`) for
`TechnicalApprovalService.rejectImplementation` (`reviewerRole=developer`).

The `ck_approvals_rejection_taxonomy` and `ck_workflow_events_rejection_taxonomy` DB
CHECK constraints are **shared across both tables** and value-set-wide, not
role-scoped. When story 3.21's `V13__add_implementation_loop_columns.sql` widened
those CHECKs to the 8-value union, the database stopped rejecting a developer value
written on a product (spec) rejection — and `ApprovalService.rejectSpec` had **no
application-level taxonomy guard**, so the DB CHECK had been its only backstop. A
product reviewer could then persist a developer taxonomy value, polluting the
rework metrics keyed on taxonomy.

**The recipe — enforce the role subset in the service layer:**

- Whenever a reject/approval service takes a `RejectionTaxonomy` (or any shared
  role-scoped enum backed by a shared CHECK), enforce the role-appropriate subset
  **in the service**, using `RejectionTaxonomy.isProductValue()` /
  `isDeveloperValue()` (or `developerValues()`).
- Make the subset guard **unconditional** for the command. Do **not** gate it on
  `reviewerRole.equals("developer")` — a non-matching role string would bypass the
  guard entirely.
- Widening the shared CHECK relaxes validation for **every** table/role that shares
  it. Re-audit each sibling path for an app-level guard before widening.

**Why no red test catches this:** the DB CHECK is the only value-set enforcement, and
it is deliberately value-set-wide. Role-scoping lives only in the service layer, so
the only durable guard is the in-service `isProductValue()` / `isDeveloperValue()`
check. Cover it with a service test that asserts a cross-role value is rejected.

## The general shape

Every recipe above is the same pattern: a **governed registry value** has one or
more **mirror sites** (fixtures, manifests, exhaustive switches, hard-coded
expectation sets, DB constraints, app-level guards) and a **gate** that fails when
they drift. The recurring trap is that the gate is often **not** in the default
`mvn test` tier — it is compile-time, class-load-time, `-Pfoundation-gate`-only, or
(worst) a silently-relaxed runtime check. When you touch a registry, change all the
mirror sites in the same commit and run the foundation-gate tier before pushing.
